Time Is an Unreliable Queue

The second wave of agent deployment is not chat — it is cron. Agents that wake on a schedule, do work while nobody watches, and go back to sleep. Teams treat the scheduler as transport, a detail beneath the architecture. But time is a message bus, and a badly behaved one.

The first generation of agents answered questions. The generation now being deployed does chores: every morning it compiles a briefing, reconciles a ledger, sweeps the queues, drafts the report, checks the dashboards. Nothing about this is interactive. The human is not in the loop — the human is asleep. What triggers the work is not a prompt but a tick.

This is a mistake, because the scheduler is not transport. The scheduler is a producer on a message bus that delivers wake-up events, and it is a producer with terrible manners. It will occasionally deliver the same event twice. It will occasionally deliver nothing at all. It will deliver late, after the world the run was supposed to observe has already changed.

On the left, the schedule as written: the clock ticks, one run happens, the work is done. On the right, the schedule as delivered: the same tick arrives twice and two runs race, another tick vanishes into a paused schedule or a dead worker pool, and a third arrives after the world it was meant to observe has moved. Nothing here is exotic. This is what at-least-once delivery over an unreliable channel looks like — and time is one.

The duplicate run: two of you, one world

Duplication is the failure mode schedulers actually ship with. The orchestrator restarts and forgets which jobs it fired; the queue redelivers because the acknowledgment got lost; two instances both hold the schedule during a botched failover. In a classic batch job, a duplicate run wastes some compute and writes the same row twice — annoying, usually idempotent by accident. A scheduled agent is not a classic batch job. Two concurrent copies of the same agent do not merely duplicate a row — they duplicate judgment.

The defense is the oldest concurrency tool in the box: mutual exclusion, with a lease rather than a lock. When a wake event arrives, the run must acquire a lease on the schedule's identity — not on the machine, not on the process, on the logical job — with a heartbeat that renews it and a TTL that releases it if the holder dies. And because leases can expire while a long agent run is still thinking, the renewal must be owned by the harness, not by the model.

The first wake acquires a lease on the logical job and proceeds; its harness heartbeats the lease for as long as the run lives. The duplicate wake finds the lease held and exits. If the holder dies, the TTL releases the lease and the next wake takes over cleanly. Behind the run, every outbound action carries an idempotency key derived from the schedule and the period.

The missed run: silence is a value

The opposite failure is quieter and worse. The schedule does not fire — the worker pool was deploying, someone paused the job during an incident and unpaused the wrong one, the cron expression only means what its author thinks it means in one timezone. A queue that drops a message usually drops it loudly. A scheduler that skips a tick drops it silently. The 04:00 briefing simply does not exist this morning. Nobody notices, because the artifact of a missed run is the absence of an artifact — and absence does not page anyone.

The fix is to make the schedule itself an audited stream, not a hope. Every expected firing is a record: when it should have happened, whether it did, what it produced. A watcher — outside the scheduler, outside the agent — compares expectation against reality on every period. And the moment a gap is detected, the policy question surfaces: does the missed run get backfilled or skipped? A data-sync agent should backfill, because its output is a function of the world and the world still exists. A briefing agent should usually skip, because a stale briefing delivered late is noise wearing the costume of diligence.

The stale wake: revalidate before you act

The third failure is the subtlest. The tick arrives, exactly once, on time — but the plan it triggers was written when the schedule was written, and the world has edited the premises since. The digest agent wakes and finds the source it summarizes changed format overnight; the cleanup agent discovers the queue it drains was migrated and deprecated; the escalation agent finds the ticket it was going to chase was already closed by a human at midnight. An interactive user would notice any of this in a second. The scheduled agent's defining property is that nobody is looking — which means noticing has to be built into the wake itself.

The pattern is wake-time revalidation: a cheap, deterministic preflight that runs before the model is ever invoked. Is the trigger still true? Is the input still shaped like the input? Is the output still wanted? Only after all three checks pass does the agent get to think. This ordering matters for cost as much as correctness: a scheduled fleet that invokes the model first and discovers irrelevance at token forty thousand is burning its budget on runs that should have died in preflight. The cheapest agent run is the one that never calls the model.

A wake event is not a command to run; it is a claim to be evaluated. The protocol: check the lease, check the ledger, revalidate the world, and only then run — with idempotency keys on every outbound action, and the period recorded as complete at the end, so the next wake inherits a truthful ledger instead of an optimistic one.

A schedule is not a promise that work will happen. It is a producer on an unreliable bus, publishing events into a world that changes while they are in flight. The mature position is to treat every wake as unverified input, the same way a good harness treats every tool result: welcome it, check it, and make it prove that this run should exist before letting it touch the world.

The schedule is code

None of this argues against scheduled agents — they are the most economically important shape an agent can take, because they convert intelligence from a service someone must request into a utility that compounds while the team sleeps. The argument is against the casualness. The crontab line, the scheduler rule, the workflow trigger: these are not configuration. They are the top node of the agent's graph, the edge along which every run enters existence, and they deserve the same rigor as every other edge. Five boring mechanisms — identity, leases, ledgers, revalidation, idempotency — together turn a timer into a contract.

The teams that figure this out stop talking about their schedules in the language of convenience ('runs every morning at four') and start talking in the language of semantics: delivery guarantee, overlap policy, gap policy, staleness policy, per-period identity. That vocabulary shift is the tell. It marks the moment a scheduled agent stops being a cron job with a model inside — and becomes what it should have been all along: a small distributed system, waking on an unreliable queue, that happens to think.
