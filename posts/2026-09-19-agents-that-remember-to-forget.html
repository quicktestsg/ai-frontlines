Agents That Remember to Forget

Every agent accumulates context. Tool results pile up, half-finished drafts linger, dead-end explorations stay in the transcript long after they stopped mattering. Most systems never delete anything — and the bet is that the model will somehow ignore the garbage.

There is a strange asymmetry at the heart of agent engineering. On the input side, teams obsess over retrieval — embeddings, rerankers, hybrid search, every technique imaginable to get the right facts into the context. On the output side, nothing leaves. The transcript only grows. A forty-step research agent carries the full text of every page it ever fetched, including the seven it fetched before realizing the search query was wrong. The assumption buried in this design is that context is free. It is not. Every token in the window is re-read, re-attended, re-priced on every single generation step. A useless token is not inert. It is a tax levied on every word the model produces for the rest of the run.

Left: the landfill. Every turn's raw output is retained forever; the window fills with sediment and the model pays for all of it, every step. Right: the ledger. New results enter a bounded working set; stale material is compressed into a re-injectable summary, or deliberately forgotten. The window stays small because the policy — not the model — decides what remains.

Forgetting is a design decision, not a failure

Human memory does not work like a transcript, and this is not a limitation to be pitied but a feature to be studied. A person debugging a problem all afternoon does not retain verbatim memory of every error message they saw at 9am. They retain the conclusion those messages pointed to — the shape of the failure, the hypotheses that were eliminated, the one thread that still looks promising. The raw text is gone; the knowledge extracted from it remains. This compression is not loss in the sense engineers fear. It is the entire point.

Agent systems need the same discipline, and almost none of them have it. The default architecture treats the context window as sacred: everything that entered must remain, because deleting feels like destroying evidence. But there is a difference between evidence and sediment. The tool result that proved the API returns 404 on malformed input is evidence — once, when it happened. Twelve turns later, with the input fixed and the flow working, that same 3,000-token error dump is sediment.

A context window is not an archive. It is a desk. The best desks are not the biggest ones — they are the ones where someone decided what deserves to be on them. Forgetting is the price of focus, and focus is the currency of long tasks.

The value curve of a fact

Not all context ages at the same rate. Some facts appreciate: the user's core goal, stated constraints, ratified decisions — these should survive every compression pass. Some hold steady: schemas, tool APIs — these compress into reference form. And some decay aggressively: superseded search results, replaced drafts, resolved error states. A fact can migrate between classes. The draft that was the current answer becomes a dead draft the moment a better one exists. Nothing announces this. Either the system notices, or the model keeps politely consulting a corpse.

Three classes of context, three fates. Constitution facts hold their value across the whole run and must survive compression intact. Reference facts hold steady and compress well. Operational facts decay fast, cross the keep threshold within a handful of turns, and should be compressed into conclusions or forgotten outright. Most systems treat all three identically. That is the defect.

The three-tier recall architecture

In practice, a workable memory policy resolves into three tiers, and the interesting engineering lives in the transitions. The working set: everything currently in context, raw and unsummarized — small, hot, expensive. The episodic store: compressed records of what happened, keyed by conclusion, retrievable when relevant. The semantic store: durable knowledge that outlives any single run. Facts flow downward under pressure and upward on demand.

Three tiers, two flows. Downward under pressure: sediment compresses into episodic records, repeating patterns promote into durable knowledge. Upward on demand: retrieval pulls knowledge back into context, episodic records re-expand when the current problem rhymes with a past one. The memory is not a place. It is a set of controlled transitions.

Compression is lossy, and that is fine — if the losses are chosen

The standard objection is that summarization loses information, and a lost detail might have mattered. True. But the alternative is not zero loss — the alternative is unchosen loss. A model wading through 150,000 tokens of sediment is not reading everything faithfully; attention is quietly allocated somewhere, invisibly, differently on every run. Attention dilution is lossy compression with no audit trail. A deliberate summarization pass is also lossy, but the losses are explicit, inspectable, testable — and when the summary drops the fact that mattered, the failure has an address. You can fix a policy. You cannot fix a fog.

The practical implementation is smaller than the theory suggests. A budget check at the top of every loop iteration. A summary prompt that is itself engineered carefully: extract conclusions, not chronology; keep numbers and identifiers verbatim; mark unresolved questions as unresolved. A promotion rule at the end of the run: which episodic conclusions showed up three times? Write them to the durable store. None of this requires new infrastructure. It requires a decision: that memory is a managed resource with a policy, an owner, and a budget.

The field's instinct is to reach for bigger windows whenever memory hurts, and the windows will keep growing. But a bigger landfill is not a memory system, and no window size makes sediment useful. The long tasks — the multi-day research runs, the agents that live inside a codebase for a season — will not be won by capacity. They will be won by the teams that treated forgetting as a first-class engineering problem: deliberate, versioned, observable. Remembering everything is what databases are for. An agent's job is to remember the right things — which means, necessarily, choosing what to forget.
