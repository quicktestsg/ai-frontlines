Tools Are Prompts in Disguise

A tool call fails. The team blames the model. They swap in a stronger model. It still fails. The bug was never the model — it was the tool definition, which read like an invitation to do the wrong thing.

A tool call fails, and the first instinct is to blame the model. This is the most common misdiagnosis in agent engineering, and it is almost always wrong. The agent called a tool it should not have, or called the right tool with the wrong arguments. Clearly, the model is too weak. The team picks the next tier up and re-runs the eval. Sometimes the failure rate drops a little. But the underlying problem persists, because it was never in the model. It was in the tool definition.

The model never sees the implementation. It sees a name, a description string, and a schema. Those three things are the entire basis for every decision it makes. A two-word description is not documentation — it is the only instruction the model receives. When the agent sends an email without asking, it is not misbehaving. It is doing exactly what the tool description told it was possible.

Every description is an instruction

The mistake is to think of a tool description the way one thinks of a docstring — a comment for humans, a courtesy. The model does not read docstrings. It reads the description field as an instruction set. When the description says 'send an email,' the model hears: this tool sends emails, and sending emails is an action you are expected to take. There is no hidden layer where the model infers it should confirm with the user first, because nothing in the description suggested confirmation. The model is a text predictor. It predicts the most likely next action given the text it has seen. The tool description said send. So it sends.

This is why rewriting a tool description can change agent behavior more than swapping models. A team ships an agent with a tool described as 'search the database.' The agent searches on nearly every turn, even when it already has the answer in context. The team upgrades the model. The over-searching continues. Then someone rewrites the description: 'Query the product database. Use ONLY when the user asks for information not already present in the conversation. Each call is slow and costs tokens.' The over-searching stops — not because the model got smarter, but because the instruction it was following changed.

The model does not guess what you meant. It executes what you wrote. If your tool description reads like permission to act, the agent will act — eagerly, often, and without asking. The description is the leash. Most teams forgot to attach it.

The model is identical in both columns. The database is identical. The user question is identical. The only variable is the tool description. The vague description produces a chatty, expensive, error-prone agent. The precise description produces a focused, efficient one. This is not a model problem. It is a writing problem. And writing problems do not get solved by buying more parameters.

Parameter schemas are contracts

If the description is the instruction, the parameter schema is the contract — and most schemas are written as if the model were a human who would intuit the right values. A parameter typed as a free string for an email recipient is a contract that says 'put any text here.' The model, asked to send an email to the boss, will happily construct a plausible-sounding address from the person's name if no real address is in context. This is not hallucination in the pejorative sense. It is the model honoring the contract the schema offered: you said any string, I gave you a string. The fix is not to scold the model for inventing an address. The fix is to change the contract — make the recipient an enum of known contacts, or an object with a validated address field.

Every choice in the schema sends a signal. Required versus optional tells the model what is essential and what it can skip. An enum tells it the universe of valid values and implicitly warns against inventing others. A description on a parameter — the field most teams leave blank — tells it what format to use. A date parameter described as 'ISO 8601 string, e.g. 2026-08-02' produces consistent, parseable dates. The same parameter with no description produces a grab-bag of formats — 'August second,' '8/2,' 'next Tuesday' — each one a small failure that compounds downstream. The schema is not boilerplate. It is the most-read documentation in the entire system.

Every tool added to the agent increases the selection problem. The model must read every description and pick the one that best matches the current need. With three well-distinguished tools, this is trivial. With twenty, descriptions start to overlap — 'search documents' versus 'search knowledge base' versus 'query wiki' — and the model picks among near-ties, sometimes wrongly. The fix is not a bigger model that reads descriptions more carefully. It is fewer tools, sharper descriptions, and a routing layer that narrows the menu before the model ever sees it.

Fewer tools, sharper tools

The instinct when an agent needs to do more is to add more tools — one for each new capability. This is how tool menus balloon from three to thirty, and it is how tool-selection accuracy collapses. The model is not a database that looks up the right function by id. It is a language model that reads a menu of descriptions and picks the closest match. Every tool added is another description the model must distinguish, another potential collision, another way to be wrong. The teams with the best-behaved agents tend to have the fewest tools, not the most. They consolidate. They remove tools the agent rarely calls, because a tool that is never used still sits in the menu, still gets read on every turn, still creates collision risk.

Writing a good tool description is a specific skill, closer to technical writing than to prompt engineering. The best descriptions state what the tool does, when to use it, when not to use it, what each parameter means, and what the model should expect back. They include an example. They name the failure modes. They are edited over time, based on what the agent actually did wrong, because a tool description is not written once — it is tuned against real behavior. The teams that internalize this treat their tool catalog as a living document, not a config file. Every agent failure that traces back to a tool is a note on that tool's description, and the description gets rewritten until that class of failure stops.

The highest-leverage editing surface

There is a reason this matters more than it seems. In a traditional system, the API is a fixed interface and the calling code adapts to it. In an agent system, the tools are the interface and the model adapts to them — but the model adapts by reading, not by being told, and what it reads is text that a human wrote. That text is editable. It costs nothing to change. A model upgrade costs money, changes behavior unpredictably, and might break things that worked. Rewriting a tool description costs minutes, changes behavior in a directed way, and is fully reversible. The tool catalog is the highest-leverage editing surface in the entire agent system, and it is the one most teams touch the least, because they are busy chasing the model.

The model is the engine. The harness is the car. The tools are the steering wheel, the pedals, the dashboard — the parts the agent actually uses to interact with the world. A brilliant engine in a car with a mislabeled steering wheel does not go where you want. It goes where the labels point. Before reaching for a stronger model, the disciplined team reads its own tool definitions and asks the only question that matters: if the only thing guiding the agent were these strings, would it make the right call? Because that is exactly the situation. The agent never sees anything else. The tools are not an implementation detail. They are the prompt — and the team that writes them like prompts builds agents that behave like they were told what to do, because they were.
