Speculate, Then Commit: Parallel Branches in Agent Loops

An agent that thinks serially pays for every round-trip twice: once in latency, once in user trust. Modern CPUs run ahead of certainty — they predict branches, execute speculatively, and roll back anything that guessed wrong. The same discipline maps onto agent loops with startling precision.

Watch a trace of any production agent and count the idle time. A model call takes two seconds. Then the loop calls a search tool — eight seconds. Then another model call. Then a fetch. Then a compute step. Then the model again. Every step waits for the one before it, and the user watches a spinner for ninety seconds while the system is doing useful work for perhaps eleven of them. The rest is dead time: network round-trips, queueing, serialization overhead.

The serial loop chains every operation behind the previous one. The speculative harness fans independent calls into parallel lanes, launches a probable branch alongside them, and commits only the lanes that the model actually needed. Same answer, half the wall-clock time — at the price of wasted work on the discarded lane.

Chip designers solved this in 1995

Deep pipelined processors faced the identical problem three decades ago: the instruction at the head of the pipe depends on a branch whose condition will not resolve for many cycles. Stalling until resolution wastes the entire pipeline. The answer was speculation — guess the branch direction, keep executing, and hold the results in a shadow state that is either committed in a single instant or discarded without a trace.

Agent loops are pipelines. The model call is the slow-resolving branch. The tools are downstream instructions. And almost nobody speculates. The irony is that the information needed to speculate is already present: the tool-call sequence is usually predictable from the task, the tools have known latency distributions, and the independence between calls is decidable from their signatures.

A pipeline stall is a design decision. So is a spinner. The user does not care whether the system is waiting because it must or because nobody taught it to guess.

Three primitives of an impatient harness

Speculation in agent systems decomposes into three techniques, each with a different risk profile. The first is parallel fan-out: when the model requests multiple tools whose inputs do not depend on each other's outputs, execute them concurrently and join the results. The second is the hedged request: when a single call has a long tail, issue a duplicate after a delay threshold and take whichever finishes first. The third, and the dangerous one, is speculative branching: while the model is still reasoning, the harness begins executing the tool calls the model is likely to make.

The three primitives, ordered by risk. Parallel fan-out is pure plumbing. Hedged requests double the load but never touch semantics. Speculative branching buys the most latency and carries the only real danger: it must never execute an irreversible action on a guess.

The commit gate: speculation without a rollback plan is just corruption

What makes CPU speculation safe is not the guessing — it is the rename buffer, the shadow state that holds speculative results separately from architectural state until the branch resolves. Agents need the same construct: a hard line between tentative results and committed state. Every speculative tool result lands in a sandbox layer. Reads are safe to warm. Writes sit at the gate until the model's actual decision arrives and either promotes them or drops them.

Speculative work lives in shadow state until the model's decision resolves. Correct predictions promote instantly. Wrong predictions are discarded, and the miss is logged. The accuracy log then decides which speculations the harness is allowed to make next week.

Paying for speed honestly

None of this is free, and the honest accounting matters. Hedging doubles token spend on hedged calls; speculation multiplies it by the branching factor of the predictions. There is a real temptation to hide this cost inside the harness where nobody sees it, and that temptation should be resisted: the trade of compute for latency is a business decision, and it belongs in configuration — per-task latency budgets, per-tool speculation policies, a kill switch when the accuracy log turns sour.

There is also a measurement discipline that must come first, before any speculation is written. Instrument the loop first. Break wall-clock time down by stage, and let the numbers pick the target. Speculation is a response to a specific shape of trace: long stretches where the system is idle because it is waiting on one thing while other useful work sat unstarted. If the trace does not show that shape, speculation is theater. If it does, speculation is the single highest-leverage change available.

Chips got fast by learning to guess. Agents will get fast the same way — but a CPU that mispredicts flushes a pipeline, while an agent that mispredicts can send an email. Speculate on reads. Commit on certainty. And never let the two rules meet.

The deeper point is about where intelligence lives in these systems. The model reasons; the harness paces. Deciding what to compute now, what to compute probably, and what to refuse to compute until certainty arrives — those are not modeling problems, and no model upgrade will solve them. They are scheduling problems, as old as operating systems and as well understood.
