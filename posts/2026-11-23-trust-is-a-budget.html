Trust Is a Budget

Every agent deployment eventually answers 'what is this system allowed to do?' with something binary: a sandbox or the keys. The missing design is capability over time — a budget of trust earned through verified work, spent by failure, and loaned out one tier at a time.

The permission model of most agent systems was inherited from service accounts, and it shows. A service account needs static credentials because it has no behavior. An agent is the opposite: it is mostly behavior, and its reliability is a moving target. Granting it fixed permissions at deploy time is lending money to a stranger and never looking at the account again.

The ladder, not the switch

The first move is to stop thinking of access as a set and start thinking of it as a ladder. Observation, suggestion, reversible action, irreversible action, delegation. The property that makes the ladder real is that each rung has a stated blast radius, and the harness enforces the rung, not the intention behind it.

Five rungs, five blast radii. The harness enforces the rung the agent occupies, not the agent's confidence about which rung it deserves. Promotion is earned per domain — an agent proven at code review has earned exactly nothing in payments.

Evidence is cheaper than trust

What earns a promotion? Not elapsed time, and not success statistics reported by the agent itself. Deposits come from verification the harness controls: a diff that survived independent review, an eval passed on held-out tasks, a watchdog window with zero anomalies, a reversible action whose teardown confirmed the world was left intact.

Verification scales with the action; damage scales with the account. That asymmetry is the entire business case for earning trust before spending it.

Trust as double-entry bookkeeping. Demotion is automatic because being wrong is cheap to detect; promotion requires a human because being right is expensive to prove. A symmetric ledger either traps good agents forever or forgives bad ones instantly.

Decay, or the stale cache problem

The quiet failure mode in every long-running deployment: the permissions were earned by a system that no longer exists. Model updates, tool changes, prompt rewrites — each should trigger partial decay. Decay is not punishment; it is the admission that the ledger describes a relationship between two systems, and one of them changed.

The gate in the loop

Implementation is mundane: the harness intercepts every tool call, consults the ledger, and returns allow, escalate, or downgrade. The critical detail is that escalation is not an error state. Agents punished for asking learn to stop asking — and then make irreversible decisions inside reversible permissions.

The gate sits inside the loop: every tool call is intercepted, checked against the ledger, and returned allow, escalate, or downgrade. Asking must never cost the agent more than guessing, or the ledger stops receiving the signal it exists to collect.

Permissions are loans, not gifts. A capability granted forever at deploy time is a liability that compounds quietly. The teams that run agents in production for years made trust flow in one direction — slowly up, quickly down — and kept the books the entire time.
