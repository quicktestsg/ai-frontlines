The Irreversibility Budget

Every agent eventually graduates from reading the world to writing it — sending the email, merging the PR, placing the order. The moment that happens, the most important property of any action stops being how risky it is and becomes whether it can be taken back.

There is a moment in the life of every agent project when the system stops being a toy. It is not when the model gets smart enough. It is the first time the agent performs an action the world will remember — the first email actually sent, the first row actually deleted, the first dollar actually spent. Before that moment, every failure is a learning experience. After it, every failure is an incident.

Actions are not risky or safe — they sit somewhere on a spectrum of how expensive it is to undo them. Reads cost nothing to undo. Cache writes expire on their own. Database transactions roll back. Emails can only be compensated by another email. Payments require an external refund flow. Deletions of unique data have no path home at all.

Risk is the wrong axis

Most teams, when they first worry about agent actions, reach for a risk taxonomy. They sort tools into low, medium, and high risk. This feels responsible, and it is almost entirely useless, because risk conflates two questions that need separate answers: how likely is the action to be wrong, and what happens when it is.

The uncomfortable part is that reversibility is not a property of the action alone — it is a property of the action plus the harness around it. 'Delete a file' is irreversible on a raw filesystem and completely reversible in a system with trash, versioning, or snapshots. The same nominal action can sit at opposite ends of the spectrum depending on infrastructure the team controls.

An action without a path home is not a tool call. It is a promise the system can never take back — and every agent that makes one is spending from a budget it did not know it had.

Two-phase apply: the universal pattern

There is one pattern that shows up in every serious action-taking system, under different names: two-phase apply. In databases it is prepare and commit. In Git it is stage and commit. In deployment it is canary and promote. In an agent harness it is: the agent proposes, the system disposes.

The agent emits intents, not effects. A gate — deterministic policy, a timer, a human, or a narrow verifier agent — decides which intents become real. Discarded intents cost nothing. Promoted intents are recorded in an undo log: what was the inverse operation, what state is needed to run it, and how long the window stays open.

Compensation is an edge, not an afterthought

Some actions cannot be rolled back, only compensated. The email cannot be un-sent; a follow-up can be sent. The payment cannot be un-made; a refund can be initiated. Compensation is the saga pattern's insight, carried over from distributed transactions: if you cannot undo an action, attach to it a second action that repairs its effects.

A multi-step agent action is a saga: reserve, charge, notify, each step committing before the next. When a step fails, the compensation edges fire in reverse order. The critical design rule: every forward node gets its compensating twin at design time, tested with the same rigor.

Budgeting the irreversible

After all of this infrastructure — staging, gates, undo logs, compensation edges — some actions will remain genuinely irreversible. For these, the honest mechanism is a budget. Each agent session carries an irreversibility budget: how many irreversible actions it may take, per run, per day, per user. The budget defaults to zero.

The deeper point is about what kind of system an agent is allowed to be. A system that can only do reversible things is safe but impotent. A system that can do irreversible things freely is powerful but unshippable. The workable territory is in between, and it is not found by tuning prompts or hoping the model gets more careful. It is built.
