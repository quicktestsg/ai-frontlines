Your Agent Will Be Run Twice

There is a fantasy buried in most agent codebases: that each logical action is performed exactly once. The model decides to send an email, the email is sent, the run ends. In production, that fantasy collapses on contact with reality.

Start with the thing every engineer learns, and then forgets the moment they start building with language models. In a distributed system, exactly-once execution does not exist. It has never existed. The proofs for it are decades old and brutal in their clarity: you can have at-most-once, or at-least-once, but exactly-once requires a global clock and zero-latency failure detection, and the universe does not supply either.

A single decision inside the model fans out into multiple physical executions the moment it leaves the process boundary. A retry from the client, a resume after a crash, a redelivery from a queue — each one re-enters the agent as if it were the original request. Without an idempotency contract, each execution applies its side effects independently, and the real world is left to reconcile the contradictions.

The myth of exactly-once

Most agent code is written as though the run will happen once. The loop calls the model, the model emits a tool call, the tool is executed, the result is appended, the loop continues. There is no notion that this exact tool call might be executed again — by a retry, by a resume, by a second worker that picked up the same job. The code is linear, optimistic, and structurally incapable of surviving repetition.

The disconnect is understandable. When engineers build against a model API, the development experience feels stateless and clean — send a prompt, get a response, done. The messy realities of durable execution, message redelivery, and crash recovery are hidden behind a friendly HTTP call. So teams build agents the way they build scripts: top-to-bottom, fire-and-forget, trusting that each line runs exactly once.

The agent does not get to choose how many times its actions are executed. That number is decided by the network, the queue, the operator, and the user — none of whom consult the agent first. The only thing the agent controls is whether a second execution is harmless. If it is not, the second execution is already a bug, waiting for its invitation.

The idempotency key is the real contract

The fix is old, well-understood, and consistently ignored in agent engineering: the idempotency key. Every side-effecting action the agent takes — every email sent, every record written, every payment initiated, every external API called — must be tagged with a key that uniquely identifies the logical intent of that action. When the action is executed a second time with the same key, the system recognizes that it has already been performed and returns the original result instead of performing it again. The side effect happens once. The execution can happen a dozen times. The key is what reconciles the gap.

Three executions enter the gate carrying the same logical key. The first is applied — the side effect lands, the result is stored against the key. The second and third arrive, present the same key, and are short-circuited: the gate returns the stored result without re-applying the effect. The world sees one email, one charge, one record. The agent's code ran three times. The contract held.

The key has to be derived from the logical intent, not from the physical execution. A common mistake is to key on something that changes every run — a timestamp, a request id, a fresh uuid generated at the top of the handler. That defeats the purpose entirely, because every retry gets a new key and sails through the gate as if it were the first time. The correct key is something stable across retries: a hash of the decision that produced the action, a run-id plus a step-index, a business identifier like an order number that the action is scoped to.

Checkpointing: the agent as a resumable process

Idempotency keys protect individual actions. But an agent is a sequence of actions interleaved with model calls, and the unit of recovery is not the action — it is the run. When a run crashes midway through its fifth tool call, the question is not merely whether that fifth call is idempotent. It is whether the entire run can be resumed from where it left off, without re-doing the first four calls, without re-paying for the model tokens that already produced the reasoning that led here. This is checkpointing, and it is the second half of the contract.

A checkpoint is a durable snapshot of the run's state at a recoverable boundary: the full message history, the variables, the decision about what to do next. Every time the agent completes a step — a model call returns, a tool finishes, a branch is chosen — the state is written somewhere that survives the death of the process. When the run is restarted, the first thing it does is load the latest checkpoint and continue from there, not from scratch. The model calls that already happened are not repeated. The tokens are not re-spent. The side effects that already landed are not re-attempted, because the checkpoint already recorded that they did.

On the left, a crash mid-run means the entire sequence is replayed from step one — every model call re-billed, every side effect re-attempted, guarded only by whatever ad-hoc idempotency the team remembered to add. On the right, each completed step writes a checkpoint. A crash at step three loads the latest checkpoint and resumes exactly where it stopped. The earlier steps are never revisited. Their cost is sunk and their effects are settled. Recovery is cheap, fast, and correct by construction.

The agent that cannot be replayed cannot be debugged

There is a second-order reason this matters, and it has nothing to do with crashes. An agent that produces a wrong result in production must be debugged, and debugging requires replay — the ability to reconstruct the exact sequence of states and decisions that led to the bad output. If the run was never checkpointed, the only artifact left is the final output and whatever logs survived. The intermediate states are gone. The reasoning that led to the fatal tool call is gone. The team is left staring at a wrong answer with no path backward to the moment it went wrong.

The run you cannot replay is the run you cannot explain. The run you cannot explain is the run you cannot trust. And the run you cannot trust has no business touching a customer's money, a patient's record, or a production system that other people depend on.

Build for the second run, because it is coming

The teams that ship reliable agents do not treat idempotency and checkpointing as nice-to-haves bolted on after the demo works. They treat them as the first architectural decision, made before a single tool is wired up, because everything downstream depends on them. Every side-effecting tool takes an idempotency key as a first-class parameter. Every run checkpoints its state after each step, to a store that is not the agent's own memory. Every resume loads the checkpoint and continues, never restarts. The model is consulted only for the steps that have not yet happened. The side effects that already landed are acknowledged, not repeated.

The temptation, especially in the early days of a project, is to defer all of this. The agent works in development. The retry problem has not happened yet. Checkpointing feels like overhead for a system that is still finding its shape. This is precisely when the debt is cheapest to avoid and most expensive to carry. Every side effect added without an idempotency contract is a future incident. Every run that is not checkpointed is a future debugging session that ends in resignation.

The model will make its decision once. The world will execute it more than once. That gap is not a defect in the infrastructure — it is the infrastructure. The agent that survives is the agent designed, from its first commit, for the run that happens twice: the same logical intent, arriving again, and finding that the work is already done, the result is already stored, and the only correct action is to do nothing and return what was already produced. That is idempotency. That is checkpointing. That is the difference between an agent that touches the world safely and one that touches it carelessly, again and again, until something breaks that cannot be unbroken.
