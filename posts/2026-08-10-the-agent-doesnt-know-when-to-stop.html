The Agent Doesn't Know When to Stop

Every agent loop ends. The question is why. Most end because they ran out of tokens, hit a timeout, or the model simply stopped emitting tool calls and returned a string that looked like an answer.

Open the source of almost any agent framework and look for the termination condition. In most codebases, it is one line, buried at the bottom of a while loop: the loop continues while the model emits tool calls, and it stops when the model emits a plain message instead. That single line is doing an enormous amount of quiet work, and almost nobody has examined whether it is doing the work correctly.

There are three families of termination signal. Budgetary: the run hit a token, time, or cost ceiling and was killed — the worst signal, because it says nothing about whether the work is done. Structural: the model stopped emitting tool calls, which usually means it decided the task was complete — but it also fires when the model is confused, stuck, or has simply given up. Semantic: an independent check confirmed that the output meets a defined completion bar. This last signal is the only one that means the work is actually finished, and it is the one almost nobody implements.

The model has no concept of done

This is worth stating plainly, because it contradicts the felt experience of watching an agent work. When a loop terminates and the model writes, the task is now complete — here is the summary, the thing feels finished. It feels intelligent. None of that is what happened. The model predicted tokens. At some point, the highest-probability next token was not a tool-call bracket but a prose token, and the loop interpreted that absence as completion.

The distinction matters because the two cases — the model genuinely recognizing completion, and the model drifting into prose because it ran out of things it could think to do — produce identical signals to the framework. Both look like the model stopped calling tools. The framework cannot tell them apart, and so it treats them the same: it ends the run and returns whatever the model last produced.

The agent's loop terminates on an absence — the absence of a tool call — and reads that absence as presence: the presence of completion. But absence and presence are not opposites in a probabilistic system. The model that stopped calling tools may have finished. It may have given up. It may have forgotten what it was doing. The loop cannot tell, and so it guesses, and the guess is almost always the optimistic one.

The three ways an agent stops wrong

When termination goes wrong, it goes wrong in one of three directions, and the team usually only notices one of them. The first is premature termination: the agent declares the task complete before the work is actually done. The model, partway through a multi-step investigation, emits a summary that sounds authoritative, and the loop ends. The user receives a result that is plausible, partial, and wrong. This is the most dangerous failure because the output does not look like a failure — it looks like an answer.

Three ways the same termination mechanism — the model stops calling tools, and the loop ends — produces different failure modes. On the left, the agent stops after two steps of a seven-step task: premature termination, invisible because the output reads as complete. In the center, the agent loops on verification forever, each pass finding something marginally improvable: non-termination, expensive and eventually killed by the budget. On the right, the agent completes all steps but one step produced a wrong result, and the final verdict never checked: false-done, where the output ships to the user marked as success.

The second is non-termination, and it is the one teams notice first, because it is loud. The agent that cannot decide it is done re-enters its own work: it runs the check, finds something to refine, runs the check again, finds something else, and the loop spins. Every pass produces marginal improvement, and marginal improvement is always available, because no output is perfect and a model asked whether its own work could be better will almost always say yes.

The third is false termination, and it is the most insidious. The agent completes its steps — all of them, in order — and declares the task done. But one of the steps produced a wrong result. The tool returned stale data, the search missed the relevant document, the calculation had an error the model did not catch. The agent never checked whether each step's output was correct; it checked only whether each step's output was present.

The completion bar must be defined before the run

The fix begins with a discipline that feels bureaucratic and is actually load-bearing: writing down, before the run starts, what completed means. Not a vague goal — a checkable condition. The task is done when the database migration has been applied to the staging instance and the test suite passes. The task is done when the email has been sent and the confirmation webhook has been received. These are not aspirations. They are predicates — expressions that evaluate to true or false, and that can be checked by something other than the model's feeling about its own work.

The completion contract separates the moment the model stops working from the moment the run is declared finished. When the model stops calling tools, that is not the end — it is an input to a termination gate that checks two things. Structural: were all the required steps in the plan actually performed? Semantic: do the completion predicates, defined before the run, evaluate to true against the current state? Only when both pass does the run terminate as complete.

The reason this must be defined before the run, and not discovered during it, is that the model is incompetent to define its own completion criteria in the moment. Asked whether it is done, it will almost always say yes — not because the work is done, but because the act of being asked implies that stopping is an option, and stopping is always less work than continuing. The model is biased toward resolution, toward producing an answer and closing the loop, because that is what the training data rewarded.

Every agent that terminates on the model's own judgment is an agent that terminates on the model's desire to be done. And the model always desires to be done. The completion bar exists to protect the run from that desire — to make done a state of the world, not a feeling of the model.

The termination gate is not the model

Once the completion predicates exist, the architecture follows: a termination gate that sits between the model's decision to stop and the run's actual end. When the model stops emitting tool calls, the loop does not end. It hands control to the gate, which evaluates the predicates against the current state of the world. Did the file get written? Does it parse? Does the test pass? If the predicates pass, the run terminates as complete. If they fail, the loop does not end — it re-enters, this time with the failure as feedback.

This gate must not be the same model that did the work, and it should not even be a model at all where a deterministic check is possible. A predicate that asks did the file parse is a function call. A predicate that asks is the answer correct is not a function call — it is a judgment, and judgments should be delegated to the cheapest reliable mechanism: a regex, a schema validator, a test suite, a ground-truth lookup, and only as a last resort an independent model evaluating the output against a rubric.

Stopping is a design decision, not a discovery

The teams that ship agents which stop correctly treat termination as a first-class part of the architecture, designed before the first tool is wired up. They write the completion predicates alongside the task definition, as a contract the run must satisfy. They build a termination gate that is structurally separate from the agent loop, so that the model's decision to stop is always advisory, never final.

The deeper lesson is that termination is not something the agent discovers about its own work. It is something the system decides, according to rules the team wrote, against evidence the system gathered. The agent does not know when it is done. It cannot know — it is a token predictor embedded in a loop, and the loop's job is to supply the knowing that the model cannot. Every agent that terminates correctly terminates because an engineer, at some point, sat down and answered the question the model cannot: what does done look like, how will we know when we see it, and what do we do if we run out of room before we get there.
