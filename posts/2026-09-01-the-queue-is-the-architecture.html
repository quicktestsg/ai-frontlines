The Queue Is the Architecture

An agent is not a request. A request arrives, is answered, and leaves. An agent arrives, thinks for four minutes, calls eleven tools, waits on three of them, gets interrupted, retries, and finally produces something — maybe.

There is a shape of failure that every production agent system eventually hits, and it never looks like a model failure. The logs are clean. The traces are sensible. The model is reasoning well. But the system is dying anyway: p99 latency has tripled, tool calls are timing out in ways they never timed out before, and nobody can point to a single broken component — because no component is broken. What happened is simpler and more embarrassing. The workload grew, and the system had no way to say no.

On the left, every arrival starts immediately and fights for one shared pool; saturation breeds retries, and retries breed saturation. On the right, an admission gate accepts what the system can actually drain, a bounded queue holds the rest honestly, and workers pull at their own pace. Same model, same tools. Only one of these systems degrades gracefully.

Backpressure is information

The deep mistake in most agent designs is treating the system's limits as obstacles to route around, instead of signals to route on. A rate limit from a tool provider is not vandalism. It is the provider telling the system, in the only language both sides share, how fast it can actually be driven. A queue that grows is not a malfunction. It is the system measuring the gap between what is arriving and what can be drained.

A system without backpressure has only two states: fine, and dying — with nothing in between, and no way to tell which one it is in until it is too late. A system with backpressure has a gauge. Gauges do not prevent failure. They make failure legible, and legible failure is the only kind an engineer can actually manage.

The retry deserves special blame, because it is the place where synchronous thinking quietly multiplies the disaster. A tool call times out; the natural instinct is to retry it. But if the timeout happened because the tool is saturated, the retry is not recovery — it is escalation. This is the retry storm, and it is entirely self-inflicted.

Left: every caller owns its own retries, fires them immediately, and collectively amplifies the very saturation that caused the timeouts. Right: the system owns retries — each attempt costs budget, each delay is jittered and exponential, and exhausted work lands in a dead-letter queue where a human can finally see it. Same failure. Opposite consequences.

Not all work deserves the same lane

Once work is queued, a door opens that synchronous designs cannot even see: work can be treated unequally, on purpose. An interactive agent helping a user right now is worth more than a nightly batch job summarizing yesterday's logs. Priority lanes, fair scheduling, and aging policies are not exotic technology; they are one afternoon of work once the queue exists. But they are impossible before it exists.

Interactive work rides the latency-critical lane and never waits behind batch. User-visible work waits visibly, ages upward if it waits too long. Batch fills the gaps. And when a lane is full, the system sheds at the edge — rejecting early, with a signal. Inequality here is not a bug. It is the entire point.

The queue is also what survives

There is a quieter argument for the queue, and it has nothing to do with load. Agents are long-running, and long-running processes die — deploys restart them, hosts recycle them, bugs kill them. In a synchronous design, when the process dies, the work dies with it. A durable queue changes the deal: each step checkpointed to the queue makes death a pause, not an erasure.

None of this requires exotic infrastructure. A managed message service works; so does a table in a database polled by workers, at the scale most agent systems will ever see. What matters is not the technology but the decision: that capacity is finite and worth measuring, that work can wait honestly instead of failing slowly, that retries belong to the system, that some work matters more than others, and that in-progress work deserves to outlive the process carrying it. Five decisions. One queue.
