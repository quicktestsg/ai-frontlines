The Goal Decays in Transit

Watch a long agent run and you will see a pattern that has nothing to do with model quality. The first ten steps are crisp. Then a tool result introduces a tempting adjacent problem, a partial success reframes what 'done' looks like, and by step forty the agent is diligently solving a different problem than the one it was given.

There is a strange comfort in the way short agents fail. They fail loudly — a malformed tool call, a hallucinated fact, a loop that spins in place. The failure is local, visible, and fixable with a prompt change or a guard. Long-horizon agents fail differently. They fail quietly, and often while producing work that looks, examined step by step, completely correct. The syntax is clean. The reasoning chains hold. Every intermediate artifact passes inspection. And yet the final deliverable answers a question nobody asked.

The intended path runs straight; the actual path bends a few degrees at every step. No single step contains the error — each transition was defensible given what the agent could see. Drift is not a mistake anywhere. It is the integral of many small, reasonable deflections.

Drift is not noise — it is compounding

The instinct is to treat drift as randomness: the model wandered, models do that, add more instructions. But drift is not random. It has a direction, and the direction is always the same — toward whatever the context window most recently made vivid. Agents are attention machines, and attention is a recency-biased cache. A forty-step run is a forty-round game of telephone between the original objective and whatever the last tool result happened to emphasize.

This explains the strangest property of drift: it gets worse as the agent gets better. A weak model fails early and fails visibly, which triggers a human to intervene. A capable model survives every local challenge — it solves the adjacent problem, recovers from the refactor, closes the tangential ticket — and each success quietly raises the salience of the tangent. The most dangerous agent is not the one that breaks at step five. It is the one that never breaks.

A goal stated once is a goal that decays. The context window is not a vault; it is a slow dissolve. If the objective is not periodically re-injected — deliberately, structurally, on a schedule the agent does not control — then the run's true objective becomes 'whatever the last three tool results were about.' That is not a misaligned agent. That is an unanchored one.

The beacon pattern: re-anchoring on a schedule

The teams that run long-horizon agents successfully share one structural habit: the goal is re-injected into the context on a schedule, not on demand. Call it the beacon pattern. Every N steps, or at every phase boundary, the harness — not the model — re-states the mission at the top of the working context. This is different from writing a better system prompt. A better prompt optimizes the first injection; a beacon acknowledges that the first injection has a half-life, and schedules the refills.

At each gate, the harness re-injects the mission brief at the top of the working context and runs a cheap alignment check against the stated definition of done. Gates are placed by the team, on a schedule — the model cannot defer, skip, or renegotiate them. Effective drift is bounded by the interval between gates: whatever bends off-course gets caught at the next beacon, not at the post-mortem.

The second half of the pattern is the check itself. Re-injection without verification is just a louder prompt. What gives the beacon teeth is a cheap, mechanical comparison between the current trajectory and the definition of done: a verifier that reads the mission brief and the last few actions, and answers one question — are these actions in service of this brief? The check does not need to be an oracle. It needs to be a tripwire.

The goal is an artifact, not a vibe

Underneath both the drift and the beacon sits the same root cause: most teams never write the goal down as a real artifact. It lives in the first user message, half-prose, half-implication, and everything downstream is interpretation. A mission brief worth re-injecting has to be worth reading: a versioned document with an objective stated as an outcome, constraints stated as testable rules, a definition of done stated as checkable criteria, and a scope boundary that names the tangents most likely to tempt the agent.

The brief is a contract with three properties: it is versioned (every legitimate scope change is a visible commit, not a silent re-interpretation), it is checkable (constraints and done-criteria map to machine-runnable checks), and it is injected (the harness re-states it at every gate). Drift does not disappear — it becomes an auditable event with a timestamp, instead of a surprise in the final deliverable.

There will be an objection: sometimes the goal should change mid-run. The mission was to fix the bug; fixing it properly requires the refactor; the refactor is the right call. True — and this is precisely why the brief is versioned. The answer to 'goals must evolve' is not 'let them evolve silently inside a context window.' It is 'evolve them the way code evolves: as a visible change to an artifact, made deliberately.' The agent can propose an amendment. The harness applies it as a new version. The next gate re-anchors to the new brief.

None of this is glamorous. A versioned mission brief, a gate every few steps, a tripwire check that a small model could run — it looks like project management dressed up as AI engineering. But that is what long-horizon agent engineering increasingly is. The model supplies the intelligence; the hard problems are the ones intelligence cannot solve alone. Short agents need prompts. Long agents need constitutions. The goal that arrives is never the goal that was sent — unless the system was built to carry it.
