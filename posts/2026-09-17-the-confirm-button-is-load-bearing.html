The Confirm Button Is Load-Bearing

Every agent that touches the real world eventually grows a confirm button. A payment, an email, a deploy, a delete — someone decides the agent should not do this alone, and inserts a human. It feels like safety. It is usually a bottleneck wearing a safety costume.

Here is the sequence every team goes through. Version one ships with full autonomy, because the demo needs to be impressive, and the demo never includes the part where the agent emails the wrong client. Version two adds a confirmation step before every consequential action. Everyone relaxes. Then the usage data arrives: forty prompts per user per day, average review time 2.8 seconds, approve rate 99.2 percent. Nobody read anything. The confirm button did not add supervision; it added latency.

The mistake is treating every action as equally worthy of a human. Read-only and reversible actions need no consent — they need logging. Consequential-but-recoverable actions can be batched into a digest. Only the rare, irreversible action deserves an interruption.

Consent is a budget, and nobody budgets it

Teams obsess over the context window budget — every token in, every token out, retrieval trimmed, history compressed. And then they treat human attention as infinite. A person can genuinely evaluate perhaps a dozen consequential decisions in a day before reviews degrade into pattern-matching. Each additional prompt does not add supervision. Past a threshold, it subtracts from the supervision the critical prompts were supposed to get.

The first confirmations of the day receive real scrutiny. By the fifteenth, the human is matching shapes, not evaluating decisions. The curve crosses the rubber-stamp threshold far earlier than teams assume, which means the marginal safety of every additional prompt is negative.

A confirmation prompt is not a safety mechanism. It is a bet that the human will be careful, this time, every time. The system that respects its humans does not spend their carefulness on trivia — it hoards it for the one moment that matters, and builds reversibility for everything else.

Reversibility is the cheaper safety

The deepest lesson of approval design is that the confirm button is what a team builds when it failed to build an undo. Asking 'may I?' before every action is the expensive way to be safe. Building the action so it can be taken back is the cheap way, because it converts catastrophic errors into ordinary ones. The best agent systems are not the ones with the most rigorous approval gates. They are the ones engineered so that almost nothing is truly irreversible.

Left: every action gated by a modal, every modal approved on reflex, safety dissolved by frequency. Right: actions run through a dry-run that shows the exact diff; reversible ones execute immediately; only the genuinely irreversible escalate — and because they arrive once a day, the human actually reads them.

Anatomy of an interruption worth making

When an action does deserve a human, the prompt itself is engineering, not copywriting. A dialog that says 'Approve?' forces the human to reconstruct consequences from memory — so they approve. A good interruption carries the decision, pre-chewed: the exact diff, the recipients by name, the cost in currency, the last time this action ran and how it went, and what happens on timeout. Approve and reject should be asymmetric on purpose. And every approval should leave an artifact.

None of this is a plea for autonomy, and none of it is a plea against it. It is a plea to treat the consent flow as architecture — as real as the tool schema, as budgeted as the context window, as tested as the eval suite. The teams that get agents accepted are never the ones whose agents ask permission the most. They are the ones whose interruptions are so rare, so precise, and so obviously consequential that when the confirm button appears, everyone leans in. That button is load-bearing. Build it like it is.
