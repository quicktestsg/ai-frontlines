The Handoff Is the Hard Part

Every multi-agent demo shows the same movie: a planner delegates, a researcher gathers, a writer drafts, a critic polishes — a swarm of specialists moving like one organism. What the demo never shows is the seam. Between every pair of agents sits a boundary, and crossing it means serializing one agent's entire working state into a message small enough for another context window to swallow. Most of what an agent knows does not survive that crossing.

Start with the single-agent case, because it sets the baseline everything else is measured against. One agent, one context window, one continuous run. Everything the agent learned during the task — every tool result, every discarded draft, every moment of doubt it reasoned through — is still sitting in the context when the next token is generated. The context is the agent's memory, and within a single run, nothing is forgotten.

Now cut the task in two and give each half to a different agent. The moment you do, a physics problem appears. The first agent finishes its half holding a working state: a goal, a partial plan, a set of facts it verified and a set it rejected, a style it was converging toward, three open questions it had not resolved. The second agent starts with none of that. It starts with whatever the first agent chose to say in the handoff message — typically a summary, a few paragraphs, written under pressure to be brief. Everything not written down is gone. Not archived, not compressed — gone, in the precise sense that no downstream decision can ever be conditioned on it again.

Left: a single agent carries its entire working state in context — reasoning, dead ends, constraints and all — right up to the final token. Right: the moment a second agent joins, the full state must squeeze through the handoff, a channel as narrow as a summary. What crosses is what was written.

The summary is not the state

The instinctive fix is to make the handoff message richer: longer summaries, more sections, stricter templates. This helps a little, then plateaus, because it attacks the wrong target. A summary is a lossy compression chosen by the party that does not know what the reader will need. Compression without knowledge of the use is guessing. And the guess is systematically wrong in the same direction every time: summaries keep the conclusions and drop the reasons.

A handoff is not a message between agents. It is an API between two programs that run on different clocks, hold different beliefs, and share no memory. The moment you start treating the handoff with the rigor of an API contract — schema, versioning, backward compatibility, validation on receipt — multi-agent systems stop being a demo and start being software.

The four things that must cross

Look at handoffs that work — in agent systems, but also in the older multi-agent systems that preceded them: human teams — and a pattern emerges. Four categories of information decide whether the receiving agent can continue the work or merely restart it adjacent to it. First, the goal and its constraints. Second, the state of exploration: what has been tried, what it produced, and crucially what was rejected and why. Third, the open questions. Fourth, the artifacts: passed by reference, not retold by mouth.

A handoff contract has four sections: the goal with its constraints, the exploration state including rejected paths, the open questions with guesses labeled as guesses, and artifacts passed by reference. The receiving agent validates the contract before acting on it — because an unvalidated handoff is not a briefing, it is a rumor.

The telephone game compounds

There is a reason the classic failure of multi-agent chains looks exactly like the children's telephone game. Each handoff is a lossy re-encoding, and the losses do not stay constant — they compound. Agent B holds A's summary of the truth. Agent C holds B's summary of A's summary. By the third or fourth hop, the goal has drifted, the constraints have mutated, and the final agent executes with total confidence a task that no longer resembles the one that started the chain. Nothing failed. Every agent did its job.

Top: when each agent retells the task to the next, fidelity decays with every hop — the goal mutates silently, and by the end nobody is working on the original intent. Bottom: when a single structured baton travels the whole chain — agents append their findings to it, never rewrite it — the original intent arrives intact. The difference is not the agents. It is the object they pass.

Design the seam, not the swarm

The practical conclusions are almost disappointingly plain. Prefer fewer agents: every additional hop is an additional lossy boundary, and the cheapest handoff is the one you never needed. Pass artifacts, not descriptions of artifacts. Make the original intent immortal: the user's actual request travels with the baton from first hop to last. Label confidence: every fact in the handoff carries its provenance — verified, assumed, or guessed. And validate on receipt.

None of this is glamorous, and that is the point. The interesting engineering in multi-agent systems was never in the agents — the agents are the part the model providers ship. The interesting engineering is in the seams: the contracts, the batons, the shared stores, the validation that runs when one intelligence hands its world to another. A single agent is a conversation with a very smart system. A multi-agent system is a team, and teams are held together not by the brilliance of their members but by the quality of their handoffs.
