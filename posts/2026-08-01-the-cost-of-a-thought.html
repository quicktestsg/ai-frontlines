The Cost of a Thought

Every token an agent generates is billed. Teams know their accuracy to two decimal places. They know their p99 latency. And most of them cannot answer a single question: what does one completed task cost?

A thought costs money. This sounds obvious, and yet it is the most systematically ignored fact in agent engineering. When a developer writes a function that sorts a list, the function runs in microseconds, costs nothing, and can be called a billion times without anyone thinking about the bill. When an agent reasons about whether to call a tool, that reasoning is a chain of generated tokens, each one priced, each one metered, each one adding to a total that compounds across every step of every run. The agent does not just think once. It thinks at the start, it thinks after every tool result, it thinks when verifying its own output, it thinks when deciding whether to stop. A single task might involve fifteen model calls, each consuming thousands of tokens of context that grow with every step.

A single task is not one API call. The system prompt, the retrieved context, the accumulated tool results — all of it is sent as input on every subsequent model call, because the model is stateless. By the fifth call, the agent is paying to re-read its own entire history.

The stateless tax

Here is the structural reason agent costs surprise people. The model is stateless. It has no memory between calls. Every time the loop runs, the entire conversation — system prompt, user message, retrieved documents, previous tool results, the model's own prior reasoning — must be re-sent as input, because the model starts fresh each time. This means the cost of a token is not paid once. It is paid every step for the rest of the run. A system prompt of twelve hundred tokens is not a one-time cost. Across a ten-step task, it is twelve thousand tokens.

This is the stateless tax, and it changes the economics of everything. Retrieved context is the worst offender. A retrieval step that returns four thousand tokens of relevant passages is useful, but those four thousand tokens are now part of the context window, and they will be re-sent on every subsequent model call for the rest of the task. If the task takes eight more steps, those four thousand tokens become thirty-two thousand. The retrieval that made the answer better also made it eight times more expensive.

The model is stateless, but the billing is not. Every token ever placed in context is billed on every future call until the task ends. The agent does not pay for what it knows — it pays, again and again, for what it has already been told.

The retry cascade

If the stateless tax is the hidden cost of context, the retry cascade is the hidden cost of failure. Agents fail. A tool returns an error. A format is wrong. The model produces output that fails verification. When any of these happen, the agent retries — and a retry is not free. A retry means the entire context, now larger than before because it includes the failed attempt and its result, is sent back to the model. The failed step did not just waste the tokens it generated. It inflated the context for every subsequent step.

The happy path completes in four model calls. One failing step that retries twice adds three calls — but the real damage is that every subsequent step now carries the bloated context from those retries. The same task, the same answer, more than double the cost.

The retry cascade is why the gap between benchmark cost and production cost is so wide. On a benchmark, every task succeeds on the first try. In production, tasks fail. Tools time out. Edge cases produce format errors that trigger retries. The model occasionally decides to re-plan mid-task. The real-world cost per task is not the benchmark cost. It is the benchmark cost multiplied by the average number of attempts, multiplied by the context inflation from each failed attempt. A team that budgets based on benchmark costs will be off by a factor of three to ten.

Cost-per-task is the metric that matters

The fix begins with a metric that almost no team tracks rigorously: cost per completed task. Not cost per API call — that is meaningless, because tasks vary in how many calls they require. Not cost per token — that is the provider's pricing, not the system's economics. Cost per completed task: the total inference spend for one user request, from the moment it enters the agent loop to the moment a final answer is returned, including every retry, every verification call, every re-sent context window. This is the number that determines whether the agent is a viable product.

Every agent lives on this curve. Move left and the task succeeds less often — cheaper but wrong. Move right and success climbs — but the cost to squeeze out the last few percent of accuracy doubles or triples the bill. The engineering challenge is not maximizing accuracy. It is finding the sweet spot: the point where the agent is good enough to be useful and cheap enough to be sustainable.

Once cost-per-task becomes a tracked metric, the engineering decisions change. Context retrieval gets pruned. Verification gets conditional. The model gets swapped per step: a cheaper model handles routing; the expensive model is reserved for reasoning where its capability actually matters. These are not compromises. They are the same kind of engineering tradeoff that every system makes — allocating a finite resource to where it produces the most value. The finite resource just happens to be priced in tokens.

The discipline of cost-aware engineering

There is a discipline that separates teams that ship sustainable agents from those that ship impressive demos and then quietly shelve them. It is not a budget or a spending cap. It is the habit of treating inference cost as a first-class engineering concern — as real as latency, as real as accuracy, as real as the bug count. Every feature is evaluated not just on whether it improves the answer, but on whether the improvement justifies the cost. The system prompt is edited for length, because every unnecessary token is re-billed on every call. The retrieval pipeline is tuned to return less, because less context means less stateless tax. The retry logic is designed to fail fast, because a retry that carries bloated context through five more steps is more expensive than starting over.

None of this is visible in a benchmark. A benchmark measures whether the agent can do the task. It does not measure whether the agent can do the task at a cost that keeps the lights on. That measurement — the one that actually matters for a product — only happens when the team decides that cost is an engineering metric, not a finance afterthought. The cost of a thought is not fixed. It is a function of how the system is built, and the system is built by engineers. Every token saved is a decision. Every token spent is a decision. The teams that understand this build agents that are not just intelligent, but intelligent at a price they can afford. The teams that do not will build something brilliant, watch the invoice arrive, and learn — too late — that intelligence they cannot afford is not a product. It is a very expensive demo.
