The Eval Is the Spec

Somewhere between the prompt and the product, every agent team has to answer a question classical engineering never faced: what does 'correct' mean when the system is allowed to be different every time it runs? Types won't answer it. Unit tests won't answer it. The only artifact that answers it is the eval suite.

In typed software, the specification is not a document. It is embedded in the artifact itself, and it executes. The compiler is an adversarial reader that rejects any program contradicting the types. The test suite encodes intention as assertions and runs on every commit. In these systems, correctness is not an opinion — it is a gate that fires automatically. Agent software has no such gate.

Traditional software embeds its specification in artifacts that execute: types, tests, contracts. Agent software has a prompt — a suggestion to a distribution — and conventions that live in team folklore. The eval suite is the only specification that ever runs. If it doesn't exist, the specification doesn't exist.

The prompt is folklore

Watch how most teams actually change an agent. Someone edits a paragraph of the system prompt, deploys it, tries two or three inputs by hand, and ships. The edit is a hypothesis. The sample size is three. The control group is a memory of how it behaved last week. This is not engineering; it is ritual with a deploy button.

A prompt states what the agent should do. An eval states what the agent may not do — and then runs it a thousand times to make sure. Intention is a suggestion delivered to a distribution. The suite is the distribution's conscience.

Grade the path, not just the destination

The first mistake teams make with evals is grading only the final answer. It feels objective: here is the question, here is the gold answer, compare. But an agent's output is not just its last message — the run is a trajectory through the world, and the world keeps the receipts. Two runs can land on the identical answer while one took four careful tool calls and the other took forty, fired three at production infrastructure, and got lucky. A final-answer eval awards both a perfect score.

Left: a final-answer eval sees only the last node — the detours, the fired-at-production tools, the lucky guesses are all invisible. Right: a trajectory eval asserts every edge — search before claim, verify before write, budget ceilings, forbidden tools. Same answer, different specification.

A distribution, not a number

The second mistake is treating an agent like a function — run it once, record the score. An agent is not a function. It is a distribution over functions, and a single run is one draw. Grade one run and you have measured nothing; you have flipped a coin and written a paragraph about the coin's beliefs. The specification is a set of properties of the distribution — a success floor, a budget overshoot rate, a p95 latency, a worst-case blast radius.

Two systems, identical mean score. System A concentrates its failures near the average — visible, complainable, fixable. System B hides them in a long tail no single run will ever show. An eval that reports a mean grades both identically; an eval that reports worst-of-k and the shape of the tail writes the actual specification.

Golden traces are regression tests

Once the suite exists, it changes what a change even is. Record a handful of exemplary runs and freeze them as golden traces. Now every modification has something to be diffed against: a model upgrade shows which edges changed behavior; a prompt edit shows whether 'be more careful' actually moved the verify rate or just made the prose feel virtuous. A model upgrade without a trace suite is not a migration — it is a re-roll of every behavior the system ever had, accepted on faith.

The spec rots

There is a failure mode waiting here. An eval suite is a snapshot of what the team feared at a moment in time. The product moves; the fears go stale. Agents overfit to the suite — the team optimizes for the cases it grades and quietly abandons the ones it doesn't, which is Goodhart's law wearing an engineering hat. The defense is to treat the eval set like versioned infrastructure: retire solved cases, promote production failures the week they happen, review quarterly.

So the discipline is simple to state and demanding to keep. Write the eval before the prompt, the way serious code is written test-first — because the act of writing the eval forces the question the prompt can postpone: what, precisely, must be true about this system's behavior, and what must never be true? The eval suite is the one artifact that holds all of it to a promise — and if the team never writes it, the promise was never made.
