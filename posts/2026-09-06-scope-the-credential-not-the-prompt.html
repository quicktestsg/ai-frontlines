Scope the Credential, Not the Prompt

Somewhere in a system prompt right now is a line that says 'never delete production data.' That line is not a control. It is a wish. What actually bounds an agent is not what the prompt forbids but what the credential permits.

There is a category of engineering failure that keeps recurring in agent systems, and it almost never gets named correctly. An agent deletes a table it should not have deleted. An agent emails a customer from an address with god-mode permissions. The incident review always says the same thing: the model behaved incorrectly. But that diagnosis is wrong, and it leads to the wrong fix — another paragraph in the prompt, another guardrail expressed in prose. The correct diagnosis is that the agent was over-credentialed. It held a key that permitted the destructive action, and everything after that was probability playing out.

On the left, the prompt guardrail: the agent holds a full-power credential, and safety is a sentence the model is asked to obey. On the right, the scoped credential: a policy-bound, short-lived token issued for one task against one resource. The database itself refuses what the policy forbids — no obedience required.

The prompt is not a security boundary

This should be obvious, and it is not, because the prompt feels like control. It is written in imperative language. It is reviewed in pull requests. It has the texture of a policy document. But a policy document enforced by a language model is a policy document enforced by a next-token predictor with a non-zero error rate on every input it has never seen before. Instructions in the prompt are soft constraints: they shift the probability distribution of the agent's behavior. They do not eliminate any outcome.

Every capability you grant an agent is a bet on the model's worst day, not its benchmark average. Size the credential for the worst day. The prompt handles the average; the token handles the tail.

Least privilege, finally non-optional

Least privilege is the oldest principle in security, and for human systems it has always been aspirational. Agents change the calculus completely, because an agent can do what humans cannot: it can be issued a fresh, narrow credential for every single task. The marginal cost of tight scoping is close to zero, and the marginal benefit is enormous: the blast radius of any failure is bounded by the policy on the token, not by the model's judgement in the moment of failure.

Per-task minting: when a task arrives, a policy is derived from the task itself, a token is minted with a TTL matched to the expected duration, the agent runs inside that envelope, and the token dies when the task does. There is no long-lived secret sitting in an environment variable, waiting for the worst day.

The implementation is unglamorous, which is precisely why it works. The agent runtime holds one long-lived identity — itself — with exactly one permission: the right to mint scoped tokens. Everything the agent does in the world flows through tokens derived from the task description and the resources the plan declares it will touch. When the token expires, the work stops — and that is a feature, not a failure: a stuck loop now has a hard ceiling written in IAM, not in prose.

Escalation is a designed edge, not a prompt plea

The obvious objection: some tasks genuinely need dangerous capabilities. The answer is not to hand the agent the master key and trust the prompt. The answer is to model escalation as an explicit edge in the agent's graph — a transition that requires a human token, an approval, a reason, and a time box. The agent can request the escalation; it cannot grant it.

The happy path runs on a scoped token with no human in the loop. When the task genuinely needs a dangerous capability, the agent emits an escalation request — reason, plan, time box — and a human grants a short-lived wide token that expires in minutes.

Design the blast radius first

Here is the practice in one sentence: before writing the prompt, before choosing the model, write down the worst thing this agent could do if it failed completely, on purpose, at 3am, in a loop — and then size the credential so that worst thing is acceptable.

None of this requires new infrastructure. Every cloud has task-scoped token minting, attribute-based access control, and short-lived credentials; the primitives have existed for years. What is new is that agents make the old aspiration of least privilege finally cheap. The agent will not complain about re-authenticating. It will simply do the work inside the envelope it was given — and when the day comes that it tries to do something else, the database will say no, in a language that is not a suggestion.
