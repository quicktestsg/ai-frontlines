Agents Need Transactions They Can't Have

An agent that only reads is a demo. The moment one writes, it inherits the oldest problem in distributed systems: partial failure. Step three succeeds, step four times out, and there is no rollback button. The discipline that replaces transactions is older and harder: sagas, compensations, and idempotency designed in from the first tool call.

Consider a plan any competent agent might produce: create the customer, charge the card, reserve inventory, send the email, update the CRM. Five tools, four external systems, one timeout on the third call. The customer exists but was never charged. Nothing crashed loudly; the run simply stopped, and the world is now in a state that no single system owns and no single log explains. This is not an edge case of agent engineering. It is the default condition.

A five-step plan interrupted at step four. Each individual system is internally consistent; the composition is not. Nothing rolled back, because nothing could: the tools exposed writes, not transactions, and the run simply stopped between them. The inconsistency is only visible from where the agent stood.

Retry does not save you — it multiplies you

The instinctive fix is retry, and retry is where agent systems go to die. A timeout is ambiguous: the request may have failed before reaching the server, or the server may have succeeded and the response was lost. The agent cannot tell these apart, so it calls again — and a write that succeeded once now succeeds twice. Naive retry converts transient failures into permanent duplicates, which are strictly worse.

The escape is older than agents by decades: the idempotency key. Every write request carries a unique key generated once, at plan time; the receiving system records the key with the first execution and returns the recorded result for every replay. A tool that writes and does not accept an idempotency key is not safe to retry, and a tool not safe to retry is not safe to hand to an agent — because the agent will retry.

One ambiguous timeout, two worlds. Without a key, the retry duplicates the side effect. With a key, the retry is a no-op: the server replays the stored result and the world stays consistent. The tool contract, not the model, decides which world the agent lives in.

A database gives you atomicity and hides the cost. An agent gives you the cost and hides the atomicity — every intermediate state is real, visible to users, and yours to explain. Agent engineering is distributed systems engineering with the safety nets removed.

Sagas: the plan includes its own undo

Distributed systems that cannot lock the world still need multi-step consistency, and the pattern they converged on is the saga: a sequence of local transactions, each paired with a compensating action that semantically undoes it. Not a rollback — the original effects already happened — but a second, deliberate effect that cancels the first: refund the charge, release the reservation, send the correction email. The plan is not five happy steps; it is five steps with five shadows.

Here is what makes this hard for agents, and interesting: compensation is not mechanical. A rollback reverses bytes; a compensation reverses meaning. Whether 'delete the record' undoes 'create the record' depends on what else touched that record in between. The agent that executes a saga must also reason about its inverse. A step is not 'call the API' but a triple: the action, its compensation, and the evidence needed to run it. A create tool that returns no ID is unusable in a saga — the compensation has nothing to point at.

A saga-executing agent records, for each forward step, the handle returned, the idempotency key used, and the compensation that undoes it. On failure, the cascade runs in reverse. The on-disk ledger is the source of truth — a crashed run is a paused computation that any successor can resume or unwind. Durability, not cleverness, makes the saga survivable.

The ledger is the agent's real memory

Put the pieces together and a shape emerges that serious systems are converging on. Every side effect goes through a keyed, compensable tool and lands in a durable ledger. The context window holds the plan; the ledger holds the truth. A crashed run resumes from the ledger, because memory is gone and the ledger is not. A failed run compensates from the ledger, because compensation needs handles and the ledger has them.

None of this is glamorous, and that is the point. The difference between an agent that demos well and an agent trusted with production is almost entirely this unglamorous layer: keyed writes, planned compensations, durable effects. Transactions made databases trustworthy by making failure invisible. Sagas make agents trustworthy by making failure visible, recorded, and reversible. Agents cannot have transactions — but they can have something better than blind hope.
