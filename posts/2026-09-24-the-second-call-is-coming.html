The Second Call Is Coming

Every piece of deterministic software rests on one quiet assumption: an operation happens exactly once. Agents break this assumption by default — and the question is never whether the second call happens, but whether it was designed for.

There is a class of production incidents that follows agent adoption like a shadow. The agent sends a payment request. The gateway accepts it, but the response drowns in a timeout. The harness retries. The payment executes twice. In every case the postmortem lands on the same line: the tool was not idempotent. And the deeper cause is the same: the team designed their tools for a caller that reads code, when their caller is now one that samples from a distribution.

The harness did the right thing: it retried a call that appeared to fail. The gateway did the right thing: it executed a request it received. Every component behaved correctly, and the user was still charged twice. Exactly-once delivery was never real — it was an abstraction that held only while the caller's memory and the network's behavior were both trustworthy.

The caller changed; the contract didn't

Traditional software engineering spent fifty years building on the exactly-once assumption, and it mostly worked, because traditional callers have two properties agents lack. First, a traditional caller knows what it just did — the instruction pointer moved, a retry is a conscious decision. An agent's knowledge of what it just did lives in its context window, and context windows are lossy by design. Second, a traditional caller executes one path; agents run as graphs with parallel branches and verifier loops that deliberately re-run steps. Neither property is going away. So the fix has to live on the other side of the contract: in the tools.

Idempotency is the art of making the second call free. Not prevented — free. The agent will call twice. Build tools where twice costs the same as once, and the reliability problem dissolves into arithmetic instead of escalating into an incident.

The operation token: name the effect, not the moment

The mechanics are old and battle-tested; payments infrastructure solved this decades ago. Every side-effecting tool call carries an operation token — a stable identifier for the intended effect, generated once when the plan is formed and reused by every retry, every re-issued step, every parallel branch that converges on the same intent. The backend records the token with the outcome. First execution: perform the effect, store the result. Second execution with the same token: skip the effect, return the stored result. The subtlety is what the token names — the effect, not the attempt.

The token is minted once, when the plan is formed. Every duplicate arrival — the retry, the post-compaction re-issue, the speculative twin — carries the same token and converges on the same ledger entry. The effect happens once; the answer comes back as many times as needed. The agent never needs to know that any of this happened.

A grammar, not a checklist

Operation tokens are the verb conjugation, but the full grammar has four cases. Reads are free — never guard them. Overwrites are naturally idempotent — setting a field twice converges. Creates are the dangerous case — 'make a new thing' twice makes two things — so creates get a token or a client-supplied deterministic name. Destroys cannot be saved by tokens alone — deletion is not reversible by re-running; they want soft states, tombstones, and a recovery window.

The four cases, ordered by what a duplicate arrival costs. Reads and overwrites are safe by shape. Creates need identity — a token that names the intended effect. Destroys need time — a window in which a mistake can be walked back. Most agent incidents live in case three; the ones that make the news live in case four.

Design for the rerun, not the run

There is a posture shift here that goes beyond tokens and tombstones. Teams new to agents design for the happy path: one pass, one call per step, done. Teams that have been burned design for the rerun: they assume any step may execute again after the system has already forgotten it ran, and they build tools that answer 'what is the state of this intent' as readily as 'do this thing now'. A well-built agent tool suite is less a set of commands and more a set of convergent operations. The agent's world is one where memory is soft, paths are many, and arrival is at-least-once. Tools built for that world do not need the agent to be perfect — only persistent.
