The Agent Has No Undo Button

Every database built in the last fifty years has a transaction log, a rollback mechanism, a way to say 'that was a mistake, put the world back.' Every agent shipped this year has nothing.

There is a moment in every agent's life when it does something that cannot be taken back. Usually it is small: a file overwritten, a ticket closed, a message posted to the wrong channel. Sometimes it is not small. The pattern is always the same — the model reasoned its way to an action, the action succeeded, and only afterwards did a human notice that the action was wrong. The exit code was zero. The API returned 200 OK. The tool call completed flawlessly, and completed the wrong thing.

This is not a model problem, which is why better models will not fix it. It is a problem in the contract between the agent and the world it acts on. Databases solved this decades ago with transactions. Distributed systems solved it with the saga pattern. These are not exotic ideas — they are the accumulated scar tissue of an industry learning that side effects without recovery plans are not features. They are delayed outages.

Every tool in an agent's inventory sits somewhere on this ladder, and the position determines the recovery strategy: read-only tools need nothing, reversible tools need a delete, compensable tools need a planned inverse action, and irreversible tools need to never run without a gate.

A tool list that lies about consequences

Look at the tool inventory of a typical agent and try to answer one question: which of these calls, if wrong, can be walked back? The answer is not in the list. `updateRecord` — reversible or not? Depends on whether the old value is stored anywhere. The information exists in someone's head. It does not exist where the model needs it, and it does not exist where the harness could enforce it.

The fix is unglamorous and total: every tool gets an effect class, declared in the manifest, enforced by the harness. Read-only tools run freely. Reversible tools run with an auto-generated journal entry. Compensable tools run only if their compensating action is registered at the same time. Irreversible tools are not exposed to the model at all in autonomous mode.

A tool list that does not distinguish a read from a write is not an API — it is a dare. The model will eventually call the wrong tool with complete confidence, and the system will have designed, in advance, its own inability to recover.

Compensation is not undo

For the compensable rung, the industry already has the answer, and it predates agents by decades: the saga. Run the steps forward; if step four fails, run compensating actions in reverse order. It works. It is also widely misunderstood, because compensation is not undo. The order was placed; the order is now cancelled. The state machine is consistent again — but the emails were sent, and every observer of the intermediate state remembers what they saw.

This distinction matters for agents more than it ever mattered for microservices, because agents compose sagas without knowing it. A coding agent's afternoon is a saga. When the task fails at hour three, 'roll it back' has no clean answer unless the harness was journaling every effect as it happened.

The forward path executes real steps; the failure at step four triggers compensations in reverse order. Note the starred step: an email has no inverse, only an approximation. The saga restores consistency of the ledger, not innocence of the world.

The commit gate: make the agent rehearse

The deepest fix is not better rollback — it is fewer things that ever need rolling back. The pattern that keeps emerging in mature harnesses is two-phase execution: the agent first produces a plan in dry-run mode, where every effect is listed in an effects ledger but none is executed; then the plan crosses a commit gate, and only then do real effects run.

This changes the model's behavior, not just the system's safety. A draft is cheap to discard, so the model can explore aggressively in phase one — because nothing in phase one is binding. And when the committed execution fails midway, the ledger is already written. Recovery stops being improvisation and becomes playback — the same plan, walked backwards.

Two-phase execution: the plan runs as a dry-run first, accumulating an effects ledger without touching the world. The gate checks policy and budget — and for irreversible effects, asks a human. On acceptance, the committed run is already journaled, and failure at any step has a pre-registered inverse.

Build the undo before you need it

None of this requires a new framework. It requires three decisions made deliberately: classify the tools; register the inverse of every compensable action when the action itself is written; separate proposing from committing behind a gate that no amount of model confidence can bypass.

The uncomfortable part is that none of it is visible in a demo. A harness with effect classes and commit gates looks identical to a naive loop when everything succeeds. Its value appears exactly once, on the day the agent is confidently wrong about something that matters, and the question is not 'who do we blame' but 'which compensations do we run.'
