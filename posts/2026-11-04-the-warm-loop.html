The Warm Loop

Every agent team eventually has the same conversation. The model is slow, someone says. Buy a faster model, someone else says. But when the trace is pulled apart, the model is rarely the slow part. The slow part is everything the harness does to the prompt between turns — re-sending tokens the provider already computed, re-ordering blocks that were fine where they stood. Latency in agent systems is not a model problem. It is a cache problem.

Start with a fact that is easy to state and hard to internalize: generating a response is two operations, not one. The first is prefill — the provider ingests the entire prompt and computes the internal state for every token in it. The second is decode — the model generates new tokens, one at a time, each conditioned on the state built during prefill. For a chat agent with a long system prompt, tool definitions, and forty turns of history, the prompt can easily run to tens of thousands of tokens while the answer is a few hundred. The arithmetic is unforgiving: most of the compute in a long-context agent call is spent not on thinking, but on re-reading.

Same model, same conversation, same answer. On the left, the harness mutated an early turn, so the provider recomputed twenty thousand tokens of prefill. On the right, the harness only appended, so nearly the entire prompt was a cache hit. The difference is not milliseconds — it is the difference between an agent that feels instant and one that feels broken.

The prompt is a stack, and order is destiny

Once this is understood, the prompt stops being a bag of text and becomes a layered structure whose order is an engineering decision. At the bottom sit the layers that never change: the system prompt, the tool definitions, the persona, the output contract. Above them, the append-only layers: the conversation history, growing at the tail. At the very top, the volatile layer: the current message, the freshly retrieved context. This ordering is not a style preference. It is the difference between a cache that hits and a cache that misses.

The prompt arranged as a ladder of decreasing stability. Frozen content at the bottom, volatile content at the top, and a strict rule between them: upper layers may append, but never rewrite what lies beneath. Every violation snaps the ladder at that point and forces a full recompute of everything above it.

The cache murder list

The failures have a pattern: the timestamp stamped into the system prompt, so every request differs at token four. The dynamic few-shot, so no two requests share a prefix. The mid-history injection of retrieval results, invalidating the entire tail. The reordering of tool schemas every turn. None of these are bugs in the ordinary sense. Each was added for a reason. Together they guarantee that a forty-turn session pays for forty cold starts — and the team concludes the model is slow, when the harness was the one holding the match.

A prompt is not just a message to the model. It is a cache key. Every harness decision — what to include, where to put it, whether it changes next turn — is simultaneously a decision about whether the next request recomputes a hundred thousand tokens or two hundred. Teams that internalize this stop asking 'what should the prompt say' and start asking 'what may move, and what must hold still.'

Pin the session, warm the replica

There is a second half to warmth, and it lives outside the prompt. The key-value cache is per-replica: the state from a request lives on the specific machine that served it. A naive load balancer sprays requests across the fleet for utilization — correct for stateless web traffic, quietly catastrophic for agents. The fix is session affinity: route all requests in a conversation to the same replica, so each turn starts from the warmed state of the turn before it. An agent that takes ten model turns to finish a task is not ten independent requests. It is one conversation, and the infrastructure should treat it that way.

Two routing policies for the same agent loop. Sprayed routing maximizes fleet utilization and minimizes cache hits — every turn lands on a cold replica. Pinned routing keeps the session on one machine, so each turn inherits the computed state of the last. For workloads measured in hours of context, pinning is not an optimization. It is the design.

Put together, the warm loop is a discipline, not a feature. Order the prompt so stability increases toward the bottom. Append, never rewrite. Put time and freshness at the top, where change is cheap. Hash the frozen layers in tests, so a refactor that accidentally reorders a tool schema fails the build instead of quietly doubling latency. Measure cache hit rate the way database teams measure hit rate — as a first-class metric with an owner and a dashboard. Route sessions, not requests. None of this makes the model faster. All of it makes the system faster, often by an order of magnitude on long sessions, without touching a single weight. The model was never the bottleneck. The space between the turns was.
