Agents Have No Undo Button

Software grew up on reversibility. Transactions roll back. Migrations ship with down scripts. Editors have undo buffers decades deep. Then agents arrived, and quietly walked into a world where none of that exists.

Reversibility is the invisible foundation of all reliable software. Databases wrap mutations in transactions so a failed operation leaves the world exactly as it was. Schema migrations pair every up with a down. Even the humble text editor maintains an undo stack that outlives the session. Engineers are so marinated in this idea that they stop noticing it — until they build an agent, and discover that the entire substrate of reversibility was never a property of computation.

Consider what an agent actually is: a loop that turns model decisions into external effects. Each tool call crosses a boundary from the reversible world into the irreversible world, where state lives in other people's systems, where every action is observed, logged, and felt.

Every tool an agent can call sits somewhere on this spectrum. Reads and computation are free to retry. Drafts are still ours to delete. But sending, spending, and deleting live data cross one-way doors. As agent capability grows, agents drift rightward. The architecture decides how far they may go.

The transaction that never was

The deep problem is that agents are, in effect, hand-rolled distributed transactions. A typical workflow agent performs a sequence — create the invoice, update the ledger, send the confirmation email, write the audit record. Each lands in a different system with different consistency rules. No coordinator exists in the agent's world. If call three fails, calls one and two are already real.

A workflow agent commits steps one and two, then step three fails. The database instinct reaches for a rollback — but there is no transaction to roll back. The result is a half-finished transaction with no record of what would need to be reversed.

A responsible agent is not one that never makes mistakes. It is one where every effect can answer three questions before it happens: what did you intend to do, what did you actually do, and what will you do if it turns out you were wrong. An effect that cannot answer the third question has no business being executed.

Write the intent before the effect

The first pattern is borrowed directly from database internals: the write-ahead log. Before every external effect, the agent should append an intent record — what tool, what arguments, what expected outcome, what compensation — to durable storage it controls. The log costs milliseconds. What it buys is a map of every one-way door the agent has ever walked through, in order, with the context needed to reason about reversing each one.

The second pattern is the compensating action — the recognition that in a cross-system world, rollback is not deletion but counter-action. You cannot un-send an email, but you can send a correction. Compensation is weaker than rollback: it does not erase history, it appends to it. And it only works if someone designed it in advance.

Before any effect fires, the agent appends an intent record to a log it controls: the tool, the arguments, the expected outcome, and the compensation. If anything goes wrong, a compensator walks the log backward, issuing counter-actions newest-first. The log is the transaction boundary the external systems never gave you.

Earn the right to cross

The third pattern is gradual — the right to execute irreversible actions is earned per-run, not granted at deployment. A newly deployed agent gets read-only tools, then drafts, then bounded writes within a blast-radius budget that expands with a clean track record and collapses on any compensation event.

Put together, these patterns form the rollback layer: the piece of the harness that lives between the model's decision and the world's mutation. The undo button does not exist, and it is not coming. The only question is whether the harness pretends otherwise, or is built knowing it.
