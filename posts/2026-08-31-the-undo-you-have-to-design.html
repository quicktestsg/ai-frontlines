The Undo You Have to Design

A read-only agent is safe and useless. The moment an agent writes, sends, or spends, it enters a world with no undo button. Reversibility is not a feature — it is an architecture.

Every interactive application ever built has faced the same quiet question: what happens when the user is wrong? Word processors answered with undo stacks. Databases answered with transactions. The entire discipline of human interface design is, in a sense, a giant apology for the fact that people make mistakes, and a promise that most mistakes can be taken back. Agents break this promise by construction.

This sounds like an abstract complaint until you inventory what a capable agent actually does in an afternoon. It edits fourteen files, opens a pull request, sends a message two hundred people read, provisions a server, calls a payment API with a decimal point that may or may not be in the right place. Each action has a blast radius, and the blast radii compound.

Blast radius is not binary — it is a set of concentric rings. Near the center, actions are cheap to reverse. One ring out, reversal costs an afternoon. At the outer ring, reversal is not an engineering operation at all: the message was read, the money moved, the trust spent.

The taxonomy nobody builds

The first step is almost embarrassingly simple, and almost nobody does it: classify the tools. Every tool an agent can call sits somewhere on two axes — how much damage a wrong call does, and how reversible that damage is. These axes are independent, and confusing them is where teams get hurt.

Damage and reversibility are different axes. A version-controlled file edit is high-damage but trivially reversible. A payment is high-damage and effectively irreversible — it belongs behind a gate, a draft, or a human.

Borrow what the databases already know

None of this is a new problem, which is the good news. Distributed systems spent forty years building exactly the machinery an agent needs. The saga pattern is precisely how an agent's afternoon should be structured. Two-phase commit is the draft message, the scheduled send, the staged deploy. Checkpointing is the branch you cut before letting the agent loose.

A saga-shaped agent run. Forward actions on top; compensations below, dashed, running in reverse. The merge sits at the end because it is the step whose compensation is most expensive. The checkpoint strip is the outer safety net.

Undo changes the model's behavior, not just the system's

Here is the part that is easy to miss: reversibility is not just an insurance policy. It changes how the agent reasons. A model operating where every action is final becomes conservative in all the wrong ways. The same model where mistakes are cheap becomes bolder in all the right ways: it tries the refactor, runs the experiment, ships the draft — because the worst case is a revert, and reverts are free.

The practical consequence is that undo design is really environment design. Do not ask how to make the agent more careful; ask how to make carelessness survivable. Wrap the file system in git, the deploy in blue-green, the messaging in a draft-and-approve layer, the payments in a two-phase flow. None of these wrappers make the agent smarter. They make its errors addressable.

The question is never whether the agent will make a mistake. The question is what a mistake costs, and who paid for the machinery that decides. If the answer is nobody, then the users are the undo system — and they will notice, and they will leave. Design the undo. Make errors cheap. Then let the agent be fast.

There is a version of the future where agents are trusted with everything — infrastructure, money, communication — and it does not arrive because the models finally stopped making mistakes. It arrives because the environments around them were engineered so that a mistake is a diff, not a disaster; a revert, not an apology; a checkpoint restore, not a weekend.
