Agents Need to Sleep

Every long-lived agent system eventually faces the same quiet crisis: it runs hot, always on, always accumulating. Context swells. Tool debris piles up. Plans from Tuesday linger under plans from Friday. Nothing is ever removed while the agent is awake.

There is a reason biological brains do not learn online. Sensory streams flood in continuously, but the durable rewriting of memory — deciding what to keep, what to connect, what to discard — happens offline, during sleep, when the flood has stopped. Engineering teams building long-horizon agents keep rediscovering this pattern, usually the hard way.

On the left, the always-on agent: wake, act, act, act, forever — context monotonically growing, nothing ever settling. On the right, the consolidating agent: the same wake-act loop, but with a deliberate sleep phase between runs, where the day's accumulation is compacted and tidied before the next wake.

Hot state rots

Start with the observation that a running agent is a closed system with an intake valve and no exhaust. Every user message enters. Every tool result enters. Every intermediate plan, every retry, every apology for a failed call — all of it enters, and none of it leaves. Engineers respond the only way the live loop permits: they truncate.

The result is memory scar tissue. The truncation kept the last forty messages and the first ten, so the agent remembers how the conversation started and how it is going, but not why it chose the approach it chose. Worse, the things that survive are not the things that mattered — they are the things that happened to be near the boundaries of the window. Selection by position is not curation. It is memory by accident.

A model that forgets by truncation has not been given a memory. It has been given a slot machine: what survives is whatever lands nearest the window's edge. Real memory is chosen, not sampled.

Sleep is a phase, not a hack

The alternative is to give the system a second mode and design it with the same seriousness as the first. The waking mode is the one everyone builds: the live loop, latency-bound, user-facing, doing the work. The sleeping mode is its counterpart: an offline pass that runs when no user is waiting, whose entire job is to transform the residue of waking hours into durable structure.

What does the sleeping pass actually do? Three operations, in increasing order of difficulty. Compress: rewrite the day's transcript into distilled facts. Reorganize: restructure the accumulated distillations. Prune: delete — really delete — the entries that no longer earn their tokens. Every long-lived memory system that works, from databases to brains, does some version of these three.

The sleeping pass transforms the day's raw residue into durable structure. Compress distills the transcript into facts. Reorganize merges, resolves contradictions, and ranks what remains. Prune deletes what no longer earns its tokens.

Waking up wrong: the failure modes of sleep

Consolidation has its own failure modes: amnesia by compression, fossilization, and drift. All three are invisible in the moment — the agent still responds fluently, the context still fits — and all three surface weeks later as behavior nobody can explain.

The defenses are the same disciplines that guard any stateful system. Version every consolidation. Log the diffs, not just the results. Keep the raw transcripts in cold storage — the distilled memory is the working copy; the transcript is the source of truth.

Memory as generations, not a mutable blob. Each night's consolidation produces a named version with a diff against its parent. A guard test inspects the diff and can reject the generation before the agent ever wakes on it. A bad night costs one rollback, not one mystery.

Design the night before it is needed

The pattern generalizes. Anything an agent accumulates during waking hours deserves a corresponding offline pass that settles it. The teams that get this right do not add sleep when the degradation alarms fire. They design the night at the same time they design the day — because an agent's long-run coherence is not a property of its model. It is a property of its lifecycle.
