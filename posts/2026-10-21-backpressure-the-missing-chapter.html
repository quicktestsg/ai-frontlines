Backpressure: The Chapter Nobody Wrote

Every systems-engineering textbook has a chapter on backpressure. Every agent-engineering guide skips it. The agent produces work at machine speed, and everything downstream consumes at its own speed. The difference accumulates somewhere.

There is a pattern to how agent systems fail in production, and it is almost never the model. The demo works: one agent, one user, one task. Then the system meets volume. A hundred concurrent sessions. A batch job told to process a repository. And suddenly the failure is never where anyone looked.

The agent emits work at machine speed. Every consumer downstream has a ceiling. The gap between those two rates does not disappear; it accumulates as queue depth, and queue depth becomes latency, retries, and eventually failure. The dashed arrow — the signal that should travel backwards and slow the producer — is the one piece almost no agent system ships.

Agents are the fastest producers ever built

It is worth being precise about why this problem is specific to agents. A traditional service produces work in proportion to the requests it receives. An agent breaks that coupling. Give one agent a batch goal and it becomes a producer whose output rate is bounded only by its own loop speed and its token budget. Demand and production are decoupled by intelligence itself.

A backend engineer never had to worry that a single HTTP request would autonomously decide to become a thousand. For agent engineers, that is Tuesday. The producer is smart, and that is exactly the problem: intelligence makes the fan-out adaptive, and adaptive fan-out is unmodelable by any static capacity plan.

The failure arrives quietly, which is what makes it dangerous. There is no crash. What changes is invisible: queue depth creeps up, p99 latency stretches, the retry logic starts firing on requests that merely waited too long, and the retries add load, which makes latency worse, which triggers more retries. The model has no perception of the system it is drowning. It only sees its own next step.

Four valves, and the order to open them

When production outruns consumption, there are only four things a system can do with the excess, and every agent architecture should decide — deliberately, in advance — which valve opens at which pressure: block, shed, buffer, or degrade. Most systems pick none deliberately, and therefore get all four at random.

Flow control is not one mechanism but a ladder: buffer the burst, degrade the spike, shed the flood, block only to survive. The valve chosen by accident is always the most expensive one.

The human is the slowest consumer — and the only one that matters

The most important queue in any agentic system is not made of requests. It is made of judgments. The human's throughput is fixed; they will not read faster because the agent produced more. So they adapt: they skim, they batch-approve, they stop checking. Trust is the one consumer whose queue, once overflowed, does not drain on its own.

The fix is to treat human attention as a first-class capacity constraint in the graph. Work that requires judgment is admitted at the rate the judgment supply can bear. A rubber stamp is not a checkpoint.

Credit-based flow control, applied to an agent: the loop holds a fixed budget of in-flight work. Every emitted item spends a credit; every completed item refunds one. The system's throughput converges to the slowest consumer's, by construction.

Make the queue visible, then make it small

Backpressure cannot be designed by intuition. The practical starting point is a single number — work in flight — reported per consumer, with an alert on the slope rather than the value. A deep queue that is draining is healthy. A shallow queue that is filling is an emergency. The value lies; the derivative tells the truth.

None of this is glamorous. There is no benchmark for it, no demo where pacing the loop wins applause — a paced agent looks identical to an unpaced one until the day the unpaced one dies. Intelligence sets the ceiling of what a system could do. Flow control decides whether anyone ever gets to see it. The model writes the work. The pipes decide if it matters.
