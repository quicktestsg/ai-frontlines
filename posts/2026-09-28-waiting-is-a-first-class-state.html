Waiting Is a First-Class State

Every demo of an agent is a conversation: a message goes in, thinking happens, an answer comes out. But agents in production live a different life. They spend minutes waiting for a human to approve a payment. Hours waiting for a batch job to finish. Days waiting for an external event that may never arrive. The thinking is a rounding error. The waiting is the system.

There is a strange gap between how agents are shown and how agents are used. In the demo, the agent is always mid-thought: streaming tokens, calling tools, chaining reasoning steps. Latency is the enemy. Everything is measured in seconds. This picture is accurate for exactly one kind of agent — the chat assistant, the one-shot coding task, the query that resolves inside a single session. The moment an agent touches the real world, the picture inverts.

A conversational agent lives inside one session, and everything it does happens in seconds. A production agent touches humans, vendors, and long-running systems — and its timeline collapses into thin slivers of thinking separated by long deserts of waiting. The deserts are the system.

Three kinds of waiting, three different designs

'Waiting' is not one problem. It is at least three, and conflating them is where most systems go wrong. The first is waiting on a human: the agent needs an approval, a review, a decision that only a person can make. The second is waiting on the world: a file to land, a status to flip, a webhook to arrive. The third is waiting on itself: the agent dispatched a long job and must wait for its own machinery. Three waits, three contracts, three sets of failure modes.

Waiting on a human is an escalation design: timeout, notify, fall back. Waiting on the world is a subscription design: register, verify, deduplicate. Waiting on oneself is a durability design: checkpoint, resume, retry safely. Each has its own failure modes, and none of them are solved by polling harder.

An agent that can only act is a toy. An agent that can act, pause for three days, and come back to finish the job — that is a system. The pause is not dead time between the interesting parts. The pause is load-bearing. It is where state must survive, where timeouts must fire, where the world is allowed to change the plan. Designing the wait is designing the agent.

The sleep loop is a bet against your own infrastructure

The default implementation of waiting, in nearly every agent codebase, looks innocent: run a loop, check the condition, sleep sixty seconds, check again. It is simple, it works in the demo, and it is a quiet disaster in production. The sleep loop holds the agent's entire state in the memory of one process. When that process is redeployed — and it will be — the waiting state evaporates. The approval email arrives an hour later and finds no one home. Or worse: the restart triggers a retry, the retry re-executes a non-idempotent step, and the vendor gets charged twice.

The alternative is to make the wait durable. Instead of a process that stays alive while nothing happens, the agent freezes itself: it serializes its state into durable storage, and exits. Nothing is running. Nothing is being paid for. Then, when the event arrives — the approval, the webhook, the finished job — a fresh process is started, the state is loaded, and the agent continues as if no time had passed. What is new is that the 'state' of an agent is not a tidy set of typed fields; it is a conversation history, a pile of tool results, a partially formed plan. Making that serializable is real engineering.

On the left, the sleep loop: state lives inside one process, polling in a circle, and a single redeploy destroys everything. On the right, the durable pause: the agent serializes itself, exits, and is reborn in a new process when the event arrives — carrying its plan, its context, and its pending decision forward. Waiting costs nothing, and death costs nothing either.

The world changes while you wait

There is a second, subtler failure hiding inside long waits, and it has nothing to do with infrastructure. While the agent is paused, the world moves. The file it was waiting for has been superseded. The price it verified is no longer the price. The user changed their mind and said so — in a channel the agent is not listening to, because it is asleep. An agent that resumes blindly, treating its pre-pause context as gospel, will confidently act on stale facts. The fix is a re-validation step at every wake: before continuing the plan, re-check the assumptions the plan depends on.

None of this argues for cleverness. It argues for humility — the recognition that time passing is itself an event, that a process holding state hostage is a liability, and that the interesting engineering in agent systems is migrating from the thinking to the pauses between the thinking. The models will get faster and cheaper, and the thinking slice will shrink toward nothing. The waiting will not shrink.
