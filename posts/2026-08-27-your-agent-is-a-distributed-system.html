Your Agent Is a Distributed System

The code looks like a single program — a loop, a model, some tools. But the moment the loop reaches outside itself, it becomes a distributed system: state scattered across services, no transactions, every piece able to fail independently.

Read the source of almost any agent and it will look like a program from the 1970s: a loop, some function calls, a variable or two holding state. The loop lives in one file. The model is invoked like a library function. Tools are imported like packages. Nothing in the code suggests geography — no addresses, no nodes, no network topology. And that is exactly the trap. Because underneath that innocent loop, the agent is not one program on one machine. It is a constellation of remote systems, all held together by the thinnest of protocols: text in, text out.

On the left, what the repository suggests: one program, one stack, atomic failure. On the right, what actually runs: a stateless model behind an API, tool services owned by other teams, a shared filesystem, a database — five sources of truth coordinated by text.

The network was there all along

Distributed systems engineering spent five decades compiling a list of hard-won truths: failure is partial, latency is variability wearing a disguise, clocks cannot be trusted, and consistency is a budget you spend rather than a property you own. Every one of those truths applies to agents, and almost none of the discipline that produced them does — because the agent's code hides the network behind abstractions that look local.

A single-process program fails atomically: it either completes or it doesn't. An agent fails like a distributed system — partially, inconsistently, and often invisibly, with the failure surfacing long after the commit.

The context is a replica, and replicas drift

Here is the most useful reframing in agent engineering: the context window is not the world. It is a replica of the world — a materialized view assembled from tool outputs, summaries, and stale reads. The model reasons over the replica and acts on the source. The engineering lives entirely in the window where they disagree.

The world lane commits events continuously; the context lane only learns about them when a tool result happens to carry the news. Between the last sync and the next consequential action sits the divergence window. The fix is borrowed straight from databases: before any irreversible write, re-read and reconcile.

This reframing relocates a whole category of 'hallucinations' from the model's character to the system's consistency guarantees. When an agent asserts a fact that was true at read time and false at act time, that is not the model inventing reality — that is a stale read, and it has the same boring remedies: versioned reads, and reconciliation before consequence.

Partial failure and the exactly-once illusion

The nastiest failures happen in the gap between doing the thing and learning it was done. The tool executes, the side effect commits, the response is lost — and the retry lands the effect twice. Exactly-once execution is an illusion. What exists is at-least-once plus idempotency, and the second half is an engineering obligation.

Top: the default behavior of most harnesses — a lost response triggers a blind retry, and the effect lands twice because nothing remembers the first attempt. Bottom: the same failure with an idempotency key. The retry arrives, the key has been seen, the effect is skipped. The loop never knows anything went wrong. That is the point.

The pattern generalizes: multi-effect flows become sagas, each step paired with a compensation and a durable ledger of intents written before the first effect. The goal is not that the resumed agent has the same context — contexts drift — it is that it makes the same side effects.

Design like the network is real

None of this requires new infrastructure; it requires an admission, followed by old discipline. Treat every hop as remote. Make state reconstructable. Make effects idempotent. Reconcile before irreversible action. Bound the blast radius. These are not compromises imposed on the agent's intelligence — they are the guardrails that make it safe to let the intelligence act at all.

Teams keep describing their product as 'an agent,' singular, as if it were a colleague with a consistent mind. What they built is a distributed system with a language model at its center — and distributed systems do not have minds, they have invariants. The invariants are what the team actually owns.
