The Retried Call Is Not the Same Call

Every agent harness retries. A tool call times out, so the loop calls it again. A fallback ladder fires, so a second provider gets the same request. A subagent sees stale state and decides to redo a step it believes failed. Each retry looks free to the caller. But a retried call is not a replay — it is a second arrival in a world that already recorded the first one.

Retries are the most normal thing in an agent system, and that is exactly the problem. Nobody designs for them, because nobody considers them interesting. The timeout fires, the harness retries, the call succeeds, the trace looks clean. The engineer moves on. What the trace does not show — and what the ledger very much does show — is that the first call did not fail. It timed out from the caller's chair while succeeding at the destination. The payment went through, the email went out, the row was written. Then the retry arrived, and the world, which is obliging and literal, did the same thing twice.

The caller's trace records one successful operation. The destination's ledger records two charges. Both are correct from where they sit. The defect lives in the gap between the two views — a gap the retry crossed without carrying any proof of which intent it belonged to.

A timeout is a point of view

The root confusion is treating a timeout as information about the operation. It is not. A timeout is information about the observation of the operation. The caller knows only that no response arrived within a window; it knows nothing about whether the work happened. The work is Schrödinger's side effect: possibly executed, possibly lost, permanently unobservable from the caller's chair. Every retry policy is built on top of this ambiguity, and every one of them converts it into duplicate executions at some rate.

This is where agents are strictly worse than classic distributed systems. A service-to-service call usually wraps one side effect. An agent tool call, by contrast, is a language model's decision embedded in a loop that may execute it several times across planning, re-planning, fallback, and repair phases. Multi-agent systems multiply the surface again: two subagents given overlapping mandates will independently conclude that the charge still needs to happen. Duplication in agent systems is not an edge case that better models will outgrow. It is a structural property of having many probabilistic reasoners sharing one mutable world.

Exactly-once delivery does not exist. It has never existed. What exists is at-least-once delivery plus a filter that recognizes second arrivals and refuses to repeat the effect. Every reliable system in history — payments, queues, databases — is built this way, and the filter has a name: idempotency. The agent stack is not exempt from this. It is just the last one to find out.

Idempotency is a contract, not a flag

The engineering community talks about idempotency as if it were a boolean attached to a function — idempotent: true, done. This misunderstands the mechanism. An operation is not idempotent because a comment says so. An operation is idempotent because the interface accepts a key that identifies the intent, and the destination remembers what it did with that key. The idempotency key is the interesting part, and it is a design decision with three dimensions: scope, lifetime, and issuance.

The lifecycle of a well-designed key. The key is minted before the first attempt, carried by every arrival, checked at a gate before execution, and answered from storage on second sight. Note what this diagram implies: deduplication is a destination-side responsibility. A caller cannot make an operation idempotent by being careful. The world must participate.

Notice what this demands of the tool contract. The tool definition is no longer just a name, a description, and a JSON schema of arguments. It needs a side-effect column: does this call mutate the world, and if so, what is the idempotency mechanism? The harness needs to know which is which, because the harness is the thing doing the retrying. An agent platform that retries uniformly across all tools is making the most dangerous possible assumption: that every tool is as harmless as a search.

The replay must return the result, not silence

There is a subtlety that separates implementations that work from implementations that merely feel right: when the gate recognizes a key and refuses to execute again, what does it return? The wrong answer is an error — "duplicate request detected" — because the caller, usually a model in the middle of a loop, will interpret the error as a new problem requiring new action. The right answer is the original result, replayed verbatim. A retry is, from the intent's point of view, a request for the outcome — not a request for more work.

Two possible answers when the gate recognizes a key. Returning an error converts a solved problem into an open one, and hands it to a reasoner that will happily improvise around the obstacle. Replaying the stored result closes the loop exactly where the first attempt closed it.

Design the second arrival before it happens
