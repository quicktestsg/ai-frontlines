The Checkpoint Is the Contract

Every long-running agent lives in two worlds at once: a warm world of in-memory state and half-finished thoughts, and a cold world of killed processes and dropped networks. Teams that treat the first world as the real one build agents that cannot be restarted, only re-run.

Watch a long agent run — the kind that takes forty minutes, edits a dozen files, runs the tests, reads the logs, iterates. Where does the run live? In most systems, the honest answer is: nowhere. It lives in the memory of a process. The scratchpad exists as a growing array of messages inside a single HTTP session. The plan exists as tokens in a context window. The decisions — which files were already read, which tests were already run, which fixes were already attempted — exist only as history that will evaporate the instant the process dies.

Left: everything most agents keep in memory — scratchpad, plan, history — all of it lost when the process dies. Right: the same run, checkpointed after every step, restorable in seconds. The difference between the two columns is not infrastructure. It is a decision about what the run is: a process, or a durable object.

Statelessness is not an API trick — it is an architecture

There is a reason inference APIs are stateless. The provider cannot hold a conversation open; the conversation is sent, whole, with every request. Most teams treat this as a quirk of the API and reconstruct the full message history on every call. That is statelessness at the protocol layer — but not at the system layer. The message history itself still lives in exactly one place: the orchestrating process. Move one level up and the same question appears, harder: can the run survive between steps? Can a different process, on a different machine, pick up step fourteen of a run that another machine started? If the answer is no, the system is stateful in the way that matters — it just hides it well.

Designing for real statelessness means accepting an uncomfortable discipline: after every step, the entire run must be serializable into a checkpoint — a complete, self-contained snapshot from which any process anywhere can resume execution. Not a log that needs replaying. Not a memory dump that only makes sense inside the process that produced it. The step loop becomes brutally simple. Load the latest checkpoint. Execute one step. Write a new checkpoint. Repeat. The process becomes disposable — a mere executor — and the run becomes durable. This inversion is the whole game.

The process should be the most expendable thing in the system. Every minute a run's state exists only in memory is a minute spent betting that nothing will ever restart — a bet that fails in every production environment, on every deploy, eventually. The checkpoint is how the run outlives the process that is currently thinking about it.

What a checkpoint must contain — and what it must not

A checkpoint that contains 'everything' is a checkpoint nobody trusts, because nobody knows what is inside it. The format has to be a contract: precise, versioned, intentional. Three things belong in: the facts of the world, the pointers to external artifacts, and the position in the graph. Three things must stay out: live connections, derived state, and secrets. The presence of any of these three is not a minor flaw; it is the difference between a checkpoint and a liability.

The contract has two sides. From the left: the facts, the pointers, and the position — everything a fresh process needs to resume. From the right, nothing crosses: connections are rebuilt, derived state is recomputed, secrets are re-fetched. A checkpoint written to this contract is small, auditable, and portable.

The versioning question is where most checkpoint designs quietly fail. The model gets upgraded. A new tool joins the loop. Six months in, there are checkpoints on disk written by four different schema versions, and the resume path is a minefield of migrations. The fix is the same one databases use: write the version into the artifact, and make old versions readable forever — resuming a run should never require the checkpoint to have been written by the current binary.

Side effects: the half-done step and the twice-run tool

Checkpointing a read-only agent is easy. The hard part arrives the moment the agent touches the world, because a crash can land in the worst possible place: after the tool call was issued, before its result was recorded. Now the world has changed and the checkpoint does not know it. On resume, the agent re-runs the step — the merge was committed twice, the email was sent twice. Every durable agent design has to answer the same question: where, exactly, is the line between 'done' and 'not done'?

Before a mutating step, the checkpoint records intent. After it, the checkpoint records outcome. A crash in between leaves the system in the one state it can reason about — intent without outcome — and the resume path reconciles with the world. The step is never blindly repeated, because the intent record proves it may already have happened.

The checkpoint you can inspect is the run you can debug

There is a dividend to this discipline that has nothing to do with crashes: the checkpoint is the best debugging artifact an agent system can produce. A trace shows what the model said. A checkpoint shows what the run believed — its plan, its scratchpad, its sense of progress, its position in the graph. When a run goes wrong at step 30, the question is never 'what did the model output' but 'what state did the run carry into step 30' — and the checkpoint answers that exactly. Time-travel debugging, which took a decade to arrive for traditional software, is nearly free here.

None of this is exotic technology. It is a decision, made early, about what a run is. A process that executes it — or a durable object that the process merely serves. Teams that make the second choice get to stop praying over their agents. The checkpoint is the contract between the agent's warm, thinking present and its cold, restartable future — and like all contracts, it only protects the teams that wrote it before they needed it.
