Agents Need Checkpoints, Not Retries

Every long-running agent system eventually meets the same moment: a forty-minute run dies at minute thirty-eight, and the only recovery mechanism anyone built is to start over from zero.

The retry culture around agents is worth examining, because it is not an engineering decision so much as an inherited reflex. The mental model comes from HTTP: a request fails, you retry it, the second request is identical to the first. None of those properties hold for an agent run. A run is not a request; it is a session — forty minutes of exploration, tool calls, half-finished refactors. When it dies, everything it did to the outside world survives, and everything it knew about what it did evaporates. The retry begins from a worse position than the original run: the world now contains the first attempt's effects, but the second attempt has no memory of them.

Both philosophies respond to the same crash, but they disagree about what a run is. The retry treats the run as a request — atomic, replayable, identical on the second attempt — so it pays the full cost twice and inherits a world that no longer matches its assumptions. The resume treats the run as a process with durable state: the ledger records every intent and effect up to the crash, recovery rebuilds context from the log, verifies the interrupted step, and continues. The retry's second attempt is a stranger retracing a predecessor's footsteps. The resume is the same traveler, picking up their own backpack.

The run is a ledger before it is a conversation

The central move is to demote the context window from source of truth to cache. What defines a run is an append-only ledger of events, persisted as they happen: the task, each model decision, each tool intent written before execution, each result written after, each side effect with its idempotency key. This is the write-ahead log pattern at agent granularity — journal first, then act — and it buys what it buys in databases. Crash detection becomes trivial: an entry with intent but no result marks the exact seam where the run died. The context window becomes a projection of this ledger — a materialized view that can be rebuilt at any moment and, crucially, compacted. Compaction done from a ledger is re-projection, not the irreversible destruction of the run's only history in exchange for a few thousand tokens of room.

Three artifacts outlive any crash, and only one is usually persisted. The world's changes persist whether anyone likes it or not. The ledger persists only if the harness writes it — and most frameworks treat it as optional logging rather than the run's definition. The context window never persists, and should not: it is derivable. Written this way, compaction is re-projection, crash recovery is log replay plus one idempotency check, and session forking is two projections sharing one prefix.

A context window is a cache that everyone treats as a database. The crash does not destroy the run — it reveals that the run was never stored anywhere.

The obvious objection is determinism: you cannot replay a model call, so how can you replay a run? You cannot, and should not try. The ledger is not recorded for the model's benefit — sampled tokens are logged as opaque facts, not re-sampled. What replay means here is narrower: deterministic reconstruction of the run's context from logged events, followed by exactly one new sampling step at the seam. Rebuild the projection to the last complete entry, find the trailing intent without a result, ask the world — via the idempotency key — whether that intent took effect, then continue. The cost of a crash collapses from 'the entire run' to 'the seam step'. And resumed runs are calm: a resumed run knows exactly where it is, because its ledger told it.

Recovery reads as a four-step procedure once the ledger exists, and every step asks a question with a checkable answer. Detection is a log query. Seam verification is the payoff of writing idempotency keys into intents: the world, not the model, answers whether the interrupted step happened. Rebuilding the context is a pure function of the log — the only determinism recovery needs. Resuming costs one sampling step. The naive path re-buys everything and guarantees nothing; the difference is not model capability or luck, only whether anyone wrote the log.

There is a design boundary worth respecting: checkpointing is a harness responsibility, not a model capability. The temptation is to ask the model to checkpoint itself — 'periodically summarize your progress' — and some products ship exactly that. It is better than nothing and worse than nothing: some state survives, but the survival is probabilistic, the summaries are lossy in unpredictable places, and the mechanism fails precisely when the context is most overloaded. Persistence is not a judgment call; it is plumbing. The harness sees every tool call before and after — it is the one component positioned to journal without being asked. Asking the model to do it is like asking a program to write its own core dump.

The endpoint is a change in what a run even is. Once the ledger is the run and the process is merely its current executor, runs become inspectable while dead, forkable from any checkpoint, auditable end to end — the same artifact a reviewer walks. The economics invert: the worst case becomes a two-minute seam repair instead of a doubled forty-minute run. None of this requires a research breakthrough; append-only logs, write-ahead discipline, idempotency keys, and projections are forty years of systems engineering, sitting in the room while the industry re-invents the retry loop. The crash is not an exception to be retried away. It is a scheduled event.
