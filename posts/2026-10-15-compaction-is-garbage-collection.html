Compaction Is Garbage Collection

A context window is not a shelf. Nothing sits safely in it waiting to be used. It is a heap: every step of a run allocates tokens, most of those tokens die the moment the step ends, and nothing reclaims them. Long-horizon agents fail not because the model is weak, but because the heap fills with dead past.

Runtime systems solved this problem decades ago, and they solved it with a name that every engineer recognizes: garbage collection. Allocate freely, but track what is live, and periodically reclaim what is not. Agent systems need exactly this discipline applied to context, and almost none of them have it. The dominant pattern is the append-only transcript, and it is the equivalent of a program that never frees memory.

Left: a short run, where the append-only transcript happens to fit. Right: a long run on the same window. The dead segments crowd the heap, and the task itself is the first thing pushed out of attention. Nothing deleted the goal. The garbage buried it.

Every token pays rent, and the rent is attention

The naive model of a context window is storage: tokens go in, tokens are available, more is strictly better. The actual model is a spotlight with a budget. Every token in the window competes for attention, and a six-thousand-token dump that was needed once is a tax on every subsequent generation. Long contexts degrade even when they fit: the model does not read the window like a database, it attends over it like a crowd.

This reframes the problem. The question is not 'how do we fit more in' but 'what deserves to stay in.' A context window has a working set, and everything outside it is overhead. Operating systems understood this with paging: keep the working set resident, push the rest to disk. The equivalent for agents is stark: the full transcript lives outside the model, on disk; inside the window lives only the working set, kept small enough that attention stays sharp.

The working set stays nearly flat as a run proceeds: a goal, a handful of decisions, a few live handles. The total context grows without bound, because the append-only pattern never frees anything. The gap between the two lines is the leak, and it is pure attention tax. Compaction's only job is to close that gap.

A context window is not memory. It is attention. Memory can be retrieved later at the same cost; attention spent on the dead past is gone, subtracted from the live task, on every single token the model generates. Context hygiene is not an optimization. It is the difference between an agent that finishes and an agent that forgets what it was doing.

Mark, sweep, compact — with judgment instead of pointers

Garbage collection has three phases, and they translate to context with uncomfortable precision. Mark: determine what is live. Sweep: reclaim everything unmarked. Compact: rewrite the survivors densely. For context, marking is the hard part — a runtime uses pointers, but context has no pointers. Liveness is semantic: this decision is live because later steps may depend on it; this tool dump is dead because the fact it established was already extracted; this failed approach is dead except for one sentence — do not try this again — that must survive. No reference counter can make that call.

This is why compaction cannot be fully automatic, and why systems that treat it as mechanical truncation behave like badly tuned collectors: they free the wrong objects and preserve the wrong ones. A truncator keeps the six-thousand-token dump because it is recent, and discards the two-line decision from step five because it is old. The practical design that emerges in serious systems is a triage pass with three bins — retain verbatim, summarize to a line, drop entirely — with the full original preserved outside the window. You are not deleting; you are paging out.

When the running context crosses a threshold, a triage pass marks by meaning: goal, decisions, and live handles retained verbatim; bulky history summarized to one line each; dead weight leaves the window. Everything swept lands in the on-disk transcript. The kernel that returns is small and entirely live — which is the whole point.

The kernel is a designed artifact, not an accident

What survives compaction deserves to be said plainly: it is a specification. The compacted kernel — the goal, the decisions taken, the IDs and handles, the constraints discovered, the one-line obituaries of failed approaches — is a complete-enough description of the task state that a fresh model instance could pick it up and continue. A good compaction is not the one that shrinks the most; it is the one where the agent's behavior after compaction is indistinguishable from before. That is a testable property, and it can run in CI.

The teams that internalize this stop arguing about prompt tricks and start arguing about information design. What belongs in the kernel? The answer follows a simple principle: keep handles, not contents. A file path is a handle; the file's body is contents. A run ID is a handle; the run's log is contents. The kernel becomes a directory of pointers into rich external memory — small, stable, cheap to attend over — while the bulky truth stays one retrieval away. This is the architecture every large system has converged on: a small, fast, expensive tier holding references, and a large, slow, cheap tier holding bulk. The context window just joined the hierarchy.

And the argument only sharpens as windows grow. A million-token window does not eliminate the heap; it delays the crash and hides the tax. The working set is still a few thousand tokens no matter what the capacity line says. Engineers who treat context as a managed resource get agents that survive long horizons on any window size. The ones who treat it as a shelf get agents that work beautifully in the demo, and drown, somewhere around step forty, in the wreckage of their own transcript.
