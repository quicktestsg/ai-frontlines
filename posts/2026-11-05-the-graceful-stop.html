The Graceful Stop

Every agent gets interrupted. The user hits escape ninety seconds into a task. A budget ceiling trips. A watchdog decides the loop is stuck. Most harnesses treat each of these as an error. But interruption is not exceptional traffic in agent systems — it is normal traffic. The harnesses that survive contact with real users are the ones designed to stop on purpose.

Begin with an uncomfortable observation from any production agent fleet: the median task does not end with a result. It ends with a stop. Users change their minds mid-run and rephrase. Orchestration layers cancel subtasks whose parent already failed. Rate limits pause a pipeline and a supervisor decides to restart rather than wait. Timeout budgets — turns, tokens, wall-clock minutes, dollars — expire quietly and constantly. If the harness's only model of ending is 'the model returned a final answer,' then most endings are handled by whatever code path was never tested. A stopped agent that leaves the world half-changed is worse than no agent at all, because nobody knows which half.

One agent turn, three interruption windows. Stopping during a model call is cheap — the world is untouched. Stopping between turns is nearly free. Stopping during a tool call is where systems die: the request may already be committed on the far side, and the harness cannot know unless the stop was designed in advance.

The stop is a protocol, not an exception

The instinctive implementation — kill the task, catch the exception, log an error — is the wrong shape entirely. A kill answers 'how do I make this stop?' but never 'what was in flight?', 'what did it already change?', 'can it be resumed?'. A well-designed stop is a protocol with phases: quiesce, drain, reconcile, persist. A stopped task becomes structurally indistinguishable from a finished one — it has a record, a reason, and a future.

The same interruption, handled two ways. A hard kill optimizes for latency of stopping and pays for it forever: orphaned effects, phantom tasks, unknown state. The graceful stop costs a few extra seconds and purchases certainty: the system can say exactly what happened, exactly what did not, and exactly where a resume would pick up.

The ledger is what makes stopping safe

Underneath the protocol sits one load-bearing idea: the harness keeps a ledger of intended effects, and tools are designed so the ledger can be checked. Every side-effecting tool should return enough identity to answer 'did it happen?' and 'can it be undone or completed?'. Idempotency keys complete the picture: a tool safe to re-invoke converts resume from a forensic investigation into a retry.

Stopping is not the opposite of running. It is a phase of running. An agent system has two interfaces with the world — the work it does and the way it ends that work — and the second interface is exercised far more often than the first. It is not the edge case. It is the median case.

Resume is the payoff

Everything above converges on a capability that separates toys from infrastructure: the stop-resume cycle. A user interrupts, reads the partial transcript, refines the question, and says continue — and the agent picks up from the last checkpoint with full knowledge of what it already did. Interruptibility even becomes a product feature: the ability to steer mid-run is one of the most visceral advantages agents hold over batch jobs — but only in harnesses where interruption leaves usable state.

A steerable agent run. Checkpoints are written between turns, so a stop always has a known-good point behind it. When the user interrupts and refines, resume returns to the last checkpoint — with the effect ledger ruling out double-work. The cycle turns interruption from a hazard into the interaction model itself.

The practical checklist is short enough to tape to a monitor. Make every stop follow the protocol: quiesce, drain, reconcile, persist. Give every side-effecting tool an identity and an idempotency story. Write checkpoints at turn boundaries. Treat 'stopped' as a legitimate terminal state, with a reason and a transcript. And test the stop paths as rigorously as the happy path — because in production they are not the minority of runs. None of this makes an agent smarter. It makes an agent trustworthy in the dimension that matters most: not what it can do while it runs, but what state it leaves behind when it is told, as it constantly will be, to stop.
