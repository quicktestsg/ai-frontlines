The Harness Outlives the Model

Every agent system is two artifacts stacked on top of each other: a model, which will be obsolete in six months, and a harness — the context assembly, the tool contracts, the eval battery, the recovery paths — which does not have to be. The harness is the asset. The model is the replaceable part.

There is a strange amnesia in the field. Every six to twelve months, a new frontier model lands, and every team rediscovers the same thing: the demo they built on the old model still works on the new one, but differently. Not better in the ways that matter, not worse in the ways they expected — differently. The verbose model becomes terse. The model that loved JSON tolerates YAML. The model that needed three-shot examples to stay on task now gets distracted by them. The surrounding code was never written for 'a model.' It was written for that model. And so the migration begins: prompts rewritten, parsers patched, few-shot recalibrated, evaluations re-baselined. Weeks of work, every cycle, forever. This is not a technology problem. It is an architectural one. The system was built with the dependencies inverted.

Two lifetimes, one system. The harness layer — context assembly, tool contracts, evaluation, recovery — is where knowledge about the task accumulates, and it can live for years. The model layer churns every few months. Architecture that assumes the opposite spends its life rebuilding.

The contract is what survives

What actually lasts across a model migration? Not the prompt — prompts are the most model-coupled artifact in the stack, full of folklore about a particular checkpoint's habits. Not the few-shot examples, which encode one model's error profile. Not the sampling parameters, tuned like a carburetor to one engine. What survives is structure: the context window budget and its allocation policy; the tool schemas with their error taxonomies; the contract that says an output is valid only when it parses, references real entities, and passes a verifier; the eval battery that encodes what 'correct' means for this task. These artifacts are written against the problem, not the model. They are the harness. When the new model arrives, the harness does not need rewriting — it needs running. It becomes the acceptance test for the migration itself.

A prompt is a letter to one model. A harness is a constitution for all of them. The letter expires with its recipient. The constitution is amended, stress-tested, and outlived by nothing.

Four planes of model-independence

Harness engineering means drawing a hard line between two kinds of code. There are four planes where independence is won or lost. Context: whether the window is assembled by policy — budgeted sections, deterministic ordering, retrieval driven by the task graph — or by a prompt's private rituals. Tools: whether tools are contracts with declared failure modes, or functions the current model happens to call correctly. Evaluation: whether the eval suite runs against every candidate model before deployment, the way a migration test guards a database change, or whether it is a slide in a launch review. Recovery: whether retry, fallback, and degradation paths are first-class code, or improvised at the incident.

Four planes, one discipline: every layer is written against the problem, not the checkpoint. Context arrives by budget and policy. Tools declare how they fail. Evals gate every model swap. Recovery is code, not heroics. A model that satisfies the evals can slide into this stack in an afternoon.

The anti-pattern: model-shaped holes

The opposite of a harness is a system with model-shaped holes — logic contoured to one model's exact dimensions. The output parser that handles the specific way this checkpoint mangles markdown tables. The system prompt with a paragraph apologizing for a refusal pattern patched upstream two versions ago. The few-shot example included not to teach the task but to suppress one hallucination. The temperature chosen by grid search over one eval set, never revisited. Each is a hole. They feel like engineering, because they required measurement and effort. But they are debt denominated in the model's currency, and every release devalues them. The tell is simple — try to name the piece of the system that would survive a model swap unchanged. If the honest answer is 'not much,' the system is a hole, not a harness.

Swap day is the audit. On the left, a system of model-shaped holes: the new model does not fit the old contours, and every hole must be recarved by hand. On the right, a harness of problem-shaped contracts: the new model is judged by the eval gates and either passes or does not. One architecture pays a quarter of rework per cycle. The other pays an afternoon.

Pay the harness tax deliberately

None of this is free. A harness is slower to build than a prompt. The first version always ships faster when the context is hand-tuned, the failures are patched ad hoc, and the evals are vibes. That is the harness tax: the upfront cost of contracts, the eval battery, and real recovery code. Teams feel the tax and conclude the harness is overhead. This is the wrong ledger. The tax is paid once; the alternative is a subscription — every model release, every deprecation arrives as weeks of migration work. Six cycles in, the harness team has shipped six upgrades and banked the compounding knowledge of the task in evals and contracts. The prompt team has rewritten the same system six times and learned nothing that survives. The models will keep improving, and that is precisely the argument for the harness: every improvement is only harvestable by the system that can actually receive it.

The discipline is simple to state and rare to practice: write for the problem, verify against the evals, and let models come and go through the gate. Context assembly that follows policy. Tools that declare their failures. Evals with teeth, run on every candidate. Recovery that is code. None of it glamorous, all of it compounding. The teams that internalize this stop asking which model they are on, because it stopped being the interesting question. The interesting question is what their harness knows that no one else's does — because that is the only layer of the stack that is still theirs, and the only one that gets more valuable with every model that arrives.
