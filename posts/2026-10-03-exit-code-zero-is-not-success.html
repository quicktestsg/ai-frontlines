Exit Code Zero Is Not Success

Every agent loop terminates on a signal: an exit code, an HTTP 200, the model's own declaration that it is done. None of these mean the goal was achieved.

Ask what actually ends an agent loop and the honest answer is uncomfortable. Not the goal, usually. A signal ends it. The shell tool returns zero. The API returns 200. The model writes a final sentence and stops emitting tokens. The loop was engineered to treat these signals as terminators, and that engineering is correct. The trouble begins when the same signal is silently promoted from terminator to testimony.

Three heterogeneous signals — a process exit code, a transport status, a model's self-assessment — are flattened into a single boolean the harness treats as ground truth. None of them answers the question the loop actually cares about: did the world end up in the intended state?

Errors are loud. Success is silent.

The asymmetry is structural. Loud failure carries a location, often a cause, always an interrupt. But success produces no event. There is no stack trace for having written the record to the wrong tenant, no exception for having deleted three files when the plan said two. Nothing interrupts a loop that is silently achieving the wrong thing.

The write path is mandatory. The check path is optional.

Look at the tool surface of any agent framework and count. The write path — tools that change the world — is always present, always typed, always documented. The check path — tools that re-read what was written and diff it against intent — exists, if at all, as an afterthought the model is free to skip.

The write path is the product; the check path is the warranty. The acknowledgment answers a question about the request; the fact answers a question about the world. Building the second path costs one extra read per write — the cheapest insurance in the stack, and the one most often omitted.

Make done a predicate, not a mood

The repair is to stop asking the model how it feels and start asking the world how it is. A goal worth automating is worth expressing as a checkable predicate: a state of the world re-derived from observation, independent of the transcript. Done means the predicate holds — not the plan is empty, not the last tool exited zero.

The terminator is no longer a signal from a tool but an evaluation against the goal: act, let the changes settle, read the world back, and test the predicate. If it holds, termination was earned. If not, the loop continues with repair — the failure caught at birth, not three handoffs later.

Done is not the absence of error and not the end of the plan. Done is a property of the world, checked by reading it. Any loop that terminates on a declaration is not finishing tasks; it is filing them.

There is a budget question hiding here. A loop that verifies every write is slower than one that does not. But the unverified loop is not cheaper; its cost is deferred and compounding — silent data corruption discovered by a customer, a deployment reporting healthy while serving stale config. The economics are not close.
