Forgetting Is an Engineering Decision

Long-running agents drown in their own history. Every tool result, every retry, every detour stays in the context window, and the agent that started sharp ends up wading through its own sediment.

There is a failure that arrives quietly in agent systems, never announcing itself as a failure at all. The agent starts a long task — a repository-wide refactor, a multi-day research thread, an operations loop that runs until the job is done. The first hour goes well. Then the context fills. Tool outputs pile up: a file read here, a stack trace there, a search result with two hundred lines of noise. Each one was justified at the moment it entered. Each one stays forever.

Quality is not monotonic in context size. It rises as useful facts accumulate, peaks while the window is still mostly signal, then decays as stale tool output, abandoned plans, and dead-end reasoning fill the frame. More history does not mean more intelligence. Past the inflection point, it means less.

The window is a cache, so give it a policy

The mental model that fixes this is old: CPU caches and operating systems. A context window has all the properties of a cache. It is fast but small. The world is large and slow. Not everything fits, so something must be evicted, and the choice of what to evict determines performance far more than the size of the cache.

The naive patch — pin the system prompt, truncate the middle — is better than FIFO but still treats symptoms. The real design question is: what does each class of content deserve? Instructions deserve to be pinned. Decisions deserve to be promoted. Raw tool output deserves aggressive eviction the moment it has been consumed. Failed attempts deserve fossilization — replaced by a short note that says 'this path was tried and failed,' so the agent does not re-explore it forty steps later.

Left: the accidental policy — truncate the oldest, which is the goal. Middle: keep the recent tail, which forgets the plan and repeats old mistakes. Right: the designed policy — instructions pinned, decisions promoted to facts, raw output evicted on consumption, failures fossilized into warnings. Same window size. Very different agent.

A bigger window does not solve this. It delays the inflection and hides it deeper in the run, where nobody is watching. A million-token context that degrades at step nine hundred is worse than a hundred-thousand-token context that degrades at step ninety — the failure is real in both cases, but only one of them is cheap enough to notice. Forgetting is not the failure. Forgetting randomly is the failure. Forgetting on purpose, by policy, is engineering.

The write path matters more than the read path

Eviction answers 'what leaves the window.' The harder and more consequential question is 'what enters the store beneath it.' Long-lived agents need an external memory — and here most teams make the mirror-image mistake: the store becomes a write-through dump. Every event is written; nothing is read back selectively; retrieval pulls the fifty most semantically similar chunks, which for a long-running task means fifty variations of the same fact.

A memory that works behaves less like a log and more like an editor. Writes are gated: a fact is written once, keyed by what it is about, updated in place rather than duplicated. Reads are query-shaped. And there is a tier between the raw store and the window: a rolling summary, maintained by the agent itself at compaction time. This summary is the agent's self-image — and a summary that drops a constraint reproduces, at the next compaction, the failure the whole architecture was built to prevent. Summaries deserve tests.

Tier one is the live window: pinned rules, recent steps, the facts in play. Tier two is the rolling summary the agent maintains of itself — state, decisions, fossilized failures. Tier three is the cold store: keyed facts and full history, written through a gate and read through queries shaped by the current task. Nothing is lost; almost nothing is resident; the agent remembers by re-membering, on demand.

Forget on purpose

The uncomfortable conclusion is that memory, in an agent, is not a capacity — it is a budget, and it is spent whether or not anyone is allocating it. Every token in the window occupies attention that some other token needed. The agent that remembers everything is not loyal to its history; it is negligent with its attention.

So the practice is simple to state and rare to see. Decide, per content class, what stays resident and what leaves. Pin the instructions. Promote the decisions. Consume and evict the raw output. Fossilize the failures. Gate the writes. Shape the reads. Test the summaries, because they carry the state. And when someone proposes solving context rot with a bigger window, recognize the proposal for what it is: a decision to move the landfill somewhere larger, and to keep adding to it, indefinitely, while calling it memory.
