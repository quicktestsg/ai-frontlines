The Merge Conflict Nobody Scheduled

Every agent ever shipped was designed as if it were the only actor in the world. Its reads are assumptions of stability; its writes are assumptions of exclusivity. Both assumptions hold — right up until the second agent shows up.

Start with the most ordinary agent task imaginable: update a configuration file. Agent A reads the file, reasons about it, computes a new version, writes it back. Flawless — in a universe with one agent. Now run the same task twice. Agent A reads. Agent B reads. Both see the same original. Agent A writes its version. Agent B, still reasoning from the world as it was, writes its version too. The file now contains B's changes. A's changes are not anywhere.

The classic read-modify-write race, replayed by two agents. Both read version 1, both reason from it, both write. The last write wins, the first write evaporates, and no layer of the stack objects — not the tool, not the framework, not the model. The agents are individually competent and jointly destructive.

Humans have etiquette. Agents have nothing.

It is worth pausing on why this hasn't burned everyone already. The honest answer: human teams develop an invisible concurrency protocol. People announce themselves in a channel before touching shared infra. They feel the social cost of a clobbered commit and self-correct. Agents have none of it — and they are proliferating on overlapping schedules.

Two agents, each individually correct, can interleave into an outcome neither would accept. That is not a model failure. That is a concurrency failure, and no amount of reasoning strength fixes it — a smarter model simply loses the update faster.

Three disciplines, all of them old

The repair kit is not new, which is the good news — it is forty years of database engineering wearing a new name badge. First: pessimistic control — leases, exclusive and expiring. Second: optimistic control — version tokens and compare-and-swap commits that fail loudly. Third: commutativity — operations designed so order doesn't matter.

Concurrency control is a menu, not a doctrine. Leases serialize access at the cost of idle agents. Version-checked commits let everyone work and settle conflicts after, at the cost of rework. Commutative operation design removes the conflict structurally, at the cost of thinking about shared state before building it.

The arbiter belongs in the harness

The tempting fix is to tell the models to behave. Add a line to the system prompt: 'other agents may be working here.' This is etiquette simulation, and it fails because the model cannot hold a lock, cannot be woken when a lease expires, and cannot atomically check a version and write — the tool layer performs the write. Coordination is a property of actions, and actions belong to the harness.

There is a design shift hiding here that goes past preventing clobbered files. Once contention is admitted, agents submit intents instead of performing edits, shared state migrates toward append-only stores, and roles emerge: one agent owns the mutable core, others propose changes. The agent framework is absorbing the responsibilities of a scheduler, a lock manager, and a transaction engine — whether its designers noticed or not.

The endgame architecture for multi-agent systems looks less like a shared whiteboard and more like a commit history. Agents emit intents; a serializer orders, validates, and applies them into an append-only, replayable history. Overlapping intents surface as reviewable conflicts instead of silent overwrites.

The uncomfortable summary: the industry is racing to multiply actors while the coordination layer between them remains a polite hope. It will hold for a while, the way a bridge holds past its load limit. The knowledge is not missing — it is waiting, patiently, in the databases, for the agent world to notice that it is multi-tenant now.
