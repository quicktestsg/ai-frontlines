The Tool Result Is Untrusted Input

Every tool result — a search page, a file, an API response, an error message — is data from another system that flows straight into the model's context and is treated as fact. The context window is a writable surface. Anything that can write to it can steer the agent.

There is a moment in every agent run that deserves more fear than it gets. The model decides to call a tool. The harness executes the call. The result comes back — and the harness does the simplest thing possible: it serializes the result and appends it to the conversation. From the model's point of view, this text now has the same status as the system prompt. It is context. Context is what the model trusts.

On the left, the default: tool output is appended to context verbatim, with no validation, no provenance, no size bound — and inherits the trust level of the system prompt. On the right, the disciplined version: every result crosses an explicit trust boundary where it is validated, normalized, and labeled before the model ever sees it.

Context is a writable surface

The mental model most teams carry is that the agent's context is like a function's local variables — private, controlled, owned. The accurate model is closer to a shared document with write access granted to every party the agent has ever talked to. And once written, the model does not naturally distinguish between these voices.

Prompt injection is not a model vulnerability being patched away. It is the structural consequence of running a reasoner over a channel where data and instructions share the same encoding.

This is why the phrase 'the tool result is untrusted input' is not paranoia — it is category correction. A tool result has a source. The source has interests, or bugs, or a cache that is three days stale. Treating that payload as ground truth is a category error equivalent to a 2005 web app concatenating a query parameter into a SQL string.

Four ways a tool result lies

Not every poisoned result is an attack. In practice, tool results mislead agents in four distinct ways, and only one of them is adversarial — which is exactly why a defense aimed only at attackers misses most of the damage.

Injection is the headline risk, but the everyday risks are mundane: error payloads the model treats as content, stale caches that serve yesterday's truth in today's shape, and results so large that the useful signal drowns.

The stale case deserves special contempt, because it is invisible. A cached result arrives in the correct shape, sounding completely authoritative — and it describes a world that has since changed. The agent reads it, believes it, and acts on it, and every downstream step inherits the error with full confidence.

The gate: what a hardened harness actually does

A hardened harness runs every tool result through a gate with four stations. Validate: check the payload against the schema the tool promised. Normalize: strip everything that is not content. Label: attach provenance metadata. Bound: cap the size and summarize the overflow outside the main context.

The gate is boring on purpose. Validate against a schema and turn failures into structured, routable errors. Normalize away everything that is not content. Label every payload with its provenance. Bound the size and summarize the overflow outside the main context.

Two details of this gate are easy to dismiss and should not be. Converting failures into structured errors prevents dead-end improvisation: when the model receives a structured error, it routes. When it receives a wall of HTML from a 502 page, it guesses. Guessing is where hallucinations are born.

Trust is a budget, spend it deliberately

The deeper principle underneath all of this: in an agent system, trust is not binary but budgeted, and the budget is spent through the context window. The harness that assigns tiers explicitly is doing with architecture what a prompt alone can never do reliably: teaching the model who to believe.

None of this will make the news. There is no benchmark for 'agent did not believe a stale cache.' But the pattern is repeating exactly as it did twenty years ago: the systems that get big are the systems that got input handling right first.
