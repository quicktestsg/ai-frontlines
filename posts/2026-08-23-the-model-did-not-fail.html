The Model Did Not Fail

When an agent breaks in production, the incident gets filed against the model — because the model is loud, probabilistic, and cannot defend itself. But most agent incidents originate in the layers around the model: the harness that assembles its context, the tools that feed it, the world that changed underneath it.

The ritual is always the same. A pager fires at two in the morning because an agent returned a confidently wrong answer to a customer. The trace gets pulled up. Someone points at the reasoning step and says the model got confused. A ticket is filed, the label reads model quality, and the investigation ends before it began.

An agent system is not a model. It is a stack. At the bottom sits the world — the live documents, the third-party APIs, the data that was correct when the pipeline was built and is correct no longer. Above it, the tools. Above those, the harness. And at the top, the model: a reasoning engine that only ever sees what the harness chooses to show it.

Left: the funnel every incident descends — symptom, guess, verdict — and the verdict is always the same. Right: the four layers where failures are actually born. The dots mark where real incidents cluster when teams bother to look: the harness and the tools, the two layers written in-house, quietly outproduce the model on defects.

Failure has four addresses

Each layer of the stack has a characteristic way of breaking, and the signatures are learnable. The model layer fails statistically: the plan was wrong, an instruction was misread, a fact was invented. The tool layer fails loudly or dangerously quietly. The harness layer fails invisibly. And the world layer fails without malice. Four layers, four signatures, four very different fixes. None of them is 'switch to a better model.'

Between these signatures sits the single most underused diagnostic in agent engineering: the repetition test. Take the failing input, freeze everything, run it ten times. A model failure is stochastic — it will succeed at least once or twice across ten runs. A harness or tool failure is deterministic — it fails all ten times, identically, because code does not roll dice. Almost no one runs this test. The pager is loud, the sprint is short, and 'the model is having a bad day' is an answer that requires no further work.

A failure that reproduces every single time is not a model failure. Models are stochastic; code is not. Deterministic breakage has a deterministic author — and it is almost never the component that speaks in the trace.

The masquerade

Harness bugs do not look like harness bugs. They look like model behavior, because the model is the only part of the system that narrates. The trace shows what the model said, what tool it called, what it concluded. It does not show that the context assembler silently truncated the tool result to fit a token budget — so the model answered from half a document, and the incident is filed as hallucination.

Anatomy of one 'model failure.' The bug detonates in the harness lane — a truncation, one step before the symptom — and the blast surfaces in the model lane as a wrong number. Every layer the failure crosses launders it into something that looks like a decision. The distance between the ✗ and the ! is the distance the investigation has to travel backwards; teams that stop at the ! learn nothing.

Read the anatomy diagram and notice the geometry, because the geometry is the lesson. The cause sits low in the stack and early in the run. The symptom sits high in the stack and late. By the time the failure reaches the surface, it is wearing the model's face. This is why incident triage must walk backwards, step by step, from the first observable anomaly toward the first divergence from intent — not jump straight from symptom to verdict.

Blame allocation as an engineering discipline

The mature version of this practice is a classification pipeline, run the same way every time, on every incident. Pull the full trace — not the summary, the whole thing. Locate the first anomaly. Map that point to a layer. Run the repetition test. Fix the defect at the layer that owns it, and add the regression test at that same layer. Five steps, none of them clever, all of them cheap.

The classification pipeline. Every incident walks the same path: full trace, first anomaly, layer mapping, then a fix and a regression test at the layer that owns the defect. The compounding is the point — every classified incident builds a map of which layer actually breaks, and the next classification gets faster.

There is a simple audit that reveals how honest a team's taxonomy really is. Take the last fifty incidents labeled model failure, and group them not by label but by where the fix actually landed. A prompt edit is a harness change. A context assembler fix is a harness change. A tool wrapper patch, a schema migration, a data backfill — none of these are model changes, because the model cannot be patched. The ratio of true model failures to borrowed blame is worth tracking as a metric. It measures nothing about the model. It measures the accuracy of the team's self-portrait.

None of this excuses the model. Models genuinely fail — they misread, they confabulate, they plan badly. Those failures are real, they are frequent, and they deserve their own engineering responses. But a team that cannot tell a model failure from a harness failure applies those responses at random. The response is only as good as the diagnosis. The next time an agent breaks, ask the question the ticket is hoping nobody asks: which layer failed — and how did it get the model to take the blame?
