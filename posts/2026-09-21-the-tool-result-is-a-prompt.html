The Tool Result Is a Prompt

Ask a team to show their prompt engineering process and they will produce system prompts with revision history. Ask them to show the shape of a tool result and they will shrug.

There is a strange asymmetry in how agent systems are built. The system prompt — a few hundred tokens, shown once — gets drafted, reviewed, benchmarked, and tuned. The tool results — often thousands of tokens, shown on every single turn — get whatever the underlying library felt like returning.

Three streams feed every model call: the system prompt, the user message, and the accumulated tool results. The first two are engineered. The third — the largest, by far, after a few turns — is usually an accident of whatever the tool felt like returning.

The firehose, the cryptogram, and the shrug

Bad tool results come in three recognizable species. The first is the firehose: the tool returns everything, on the theory that more data is more helpful. A status endpoint returns the full object graph. A file reader returns the whole file when the task needed one function.

The second is the cryptogram: the tool returns something technically accurate but semantically opaque. Error codes with no message. Booleans with no semantics — true of what? The model will fill the semantic vacuum with a guess.

The third is the shrug: the tool returns a result with no affordance for action. It says what is, never what could be done next. The agent is left holding a fact and no handle.

The firehose buries signal in volume. The cryptogram withholds semantics. The shrug withholds affordance. Each failure is invisible in the code review and unmistakable in the agent trace, where it is always misfiled under model error.

Design the return like you design the prompt

The correction is a change of stance, not of tooling. Every tool result should be written as if it will be read by the model — because it will — and written for the decision the model is about to make.

A tool result designed as a prompt: the summary answers the question, references enable precise fetching, caveats prevent confident misunderstandings, and next actions hand the model its options.

This stance also reframes the division of labor between the model and the harness. The model brings reasoning; the harness brings shape. Every moment spent by the model parsing an unstructured blob is reasoning capacity spent on a problem the tool author could have solved once, in code, deterministically.

The system prompt is what the team says to the model once. The tool results are what the system says to the model forever. If only one of them is written with care, the system is talking to the model in its sleep — and the model is listening.

None of this requires new infrastructure. It requires noticing that the boundary of prompt engineering does not stop at the system prompt's closing delimiter. In a multi-turn agent, most of the prompt is written by tools. The model reads everything. The only question is who authored what it reads.
