There Is No SemVer for Weights

Every engineer learns one instinct early: dependencies change, and changes have consequences. So the industry built SemVer — a promise that breaking changes announce themselves. Model weights honor no such promise.

Consider how a normal dependency upgrade goes. A library bumps its major version. The API changed a function signature, renamed an enum, removed a deprecated path. The moment the code runs — or even compiles — the breakage surfaces. The change is loud. It has to be, because the entire contract of the library is expressed in its interface, and the interface is machine-checked.

A model exposes none of that. Its interface is a prompt in and a string out — a contract so loose it fits almost anything. The real contract, the one the product actually depends on, is the output distribution: how often the model chooses the right tool, how it formats results, where it tends to fail. That contract lives in the weights, and the weights are opaque.

Left: a library upgrade breaks the interface, and the breakage is machine-detected within seconds. Right: a weights upgrade preserves the interface perfectly, so every automated check passes — while the output distribution moves invisibly. The louder failure is the safer one.

The version number is the dependency

Here is the uncomfortable detail most teams discover late: model version strings do not behave like version numbers. They behave like pointers. Some providers offer dated snapshots that genuinely pin behavior — a snapshot name is the closest thing weights have to a lockfile. Others expose a floating alias, a name that resolves to whatever the provider currently serves.

The alias is seductive because it feels like free improvement. New weights arrive, benchmarks go up, and the product gets smarter without a single pull request. But improvement is not uniform. A retrain that makes the model better at reasoning can make it worse at the specific format a tool parser expects. Aggregate quality goes up while the product's particular slice of the distribution goes down.

A pinned dependency is a promise you made to your future team: this behavior was verified, and it will not change without a decision. An alias is the opposite — it is a standing permission for someone else's deployment to become your incident.

A product's task success rate under an unpinned model name. Nothing the team shipped changed. Three times, the provider moved the weights behind the same alias. Each one nudged the distribution. Individually survivable, cumulatively fatal: the SLO is breached by a series of events that left no trace in the commit history.

Golden traces are contract tests

If the interface cannot detect behavioral breakage, something else has to. The answer is a corpus of golden traces: real production inputs, recorded at the pinned model version, paired with the outputs the system produced — tool choices, structured fields, refusal patterns, the exact slice of behavior the product depends on.

A golden trace corpus turns a model upgrade from an act of faith into a diff. Run the new weights against every recorded input and compare. Those diffs are the migration guide the provider never wrote — found in an afternoon, in staging, instead of over six weeks in support tickets.

A model upgrade treated the way mature teams treat a database migration: pin what exists, freeze the evidence, replay against the candidate, read the diff, canary, and only then cut over. The dashed edge is the most important one — the explicit decision to do nothing, because the diff said no.

Pin, diff, canary — or schedule the outage

The practical playbook is short. Pin: run production on a dated snapshot, and treat every move off it as a release. Record: sample real traffic into the golden corpus continuously. Replay: every candidate version runs the full corpus in CI. Canary: the new weights take a slice of traffic before they take all of it. This is not exotic discipline — it is dependency management, imported from a world that learned these lessons the hard way.

The deeper point is about what a model is. For a decade, software meant deterministic artifacts whose behavior was identical to their source. Weights break that equivalence: the artifact is the behavior, the source is inaccessible, and the provider controls both. The teams that internalize this stop asking whether the new model is better, and start asking whether it is better on the traces that constitute their product.

Every model call is a dependency resolution. Most teams just haven't noticed that they left the lockfile empty.
