The Cache Is Not an Optimization

An agent loop does one thing more than anything else: it re-sends context. The system prompt, the tool definitions, the retrieved documents, the conversation history — almost all of it is identical from one iteration to the next. And yet most teams pay full price for every byte, every single time.

There is a quiet catastrophe inside almost every agent ever billed. The loop runs. On the first iteration, the model receives the system prompt, the tool schemas, a pile of retrieved documents, and the opening of the conversation. It reasons, it calls a tool, the tool returns a result, and the result is appended. On the second iteration, the model receives the system prompt, the tool schemas, the same pile of retrieved documents, the same conversation opening, plus the new tool result. On the third iteration, it receives all of that again, plus a little more. And so it goes — ten, twenty, fifty times — and at no point does anyone on the team notice that ninety-five percent of what they are sending, and paying for, has not changed since the first call. They are buying the same words, again and again, and the receipt keeps growing.

The prompt cache exists to solve exactly this. When the prefix of a request is identical to a prefix the model has already processed, the provider can reuse the internal computation — the key-value cache built during prefill — instead of recomputing it from scratch. The cached portion is billed at a steep discount, often a tenth of the normal input price, and it returns in milliseconds instead of the full prefill latency. For a single chat message, this is a nice saving. For an agent that loops twenty times over a fifty-thousand-token context, it is the difference between a task that costs a cent and a task that costs a dollar. Same intelligence. Same model. Same answer. Ten times the price, because the prompt was shaped wrong.

On the left, without caching: every loop iteration re-bills the entire growing context, so the cost compounds with each step. On the right, with caching: the identical prefix is reused at a tenth of the price, and only the small delta — the new tool result — is billed at full rate. Same agent, same intelligence, same answer. An order of magnitude less money, and an order of magnitude less waiting.

The cache is a prefix, and prefixes are fragile

Here is the catch that turns caching from a setting into an architecture. A prompt cache is not a content-addressable store. You do not ask it, 'have you seen these words before?' It is a prefix match. The provider holds the key-value cache for a specific sequence of tokens, starting from the very first token, and reuses it only as long as the new request's tokens match that exact sequence, from the start, with no deviation. The moment a single token differs anywhere in the shared region, the cache breaks at that point — and everything after the break is recomputed and rebilled from scratch. The cache is a prefix, and a prefix is only as long as its longest run of identical bytes.

This single property — that the cache extends from the front and shatters at the first difference — is the most consequential and least understood fact in agent engineering. It means that the order of content inside a prompt is not a matter of style or readability. It is a matter of money. Put a dynamic element near the top of the prompt — a timestamp, a per-user identifier, a randomly ordered list, a date in the greeting — and you have just murdered the cache for everything that follows it. The system prompt that could have been reused for ten thousand requests is now recomputed for every single one, because you insisted on writing 'Today is Tuesday' in the second line. The cache does not care that ninety-nine percent of the prompt is unchanged. It only cares that the prefix broke, and once it breaks, it is gone.

On the left, the disciplined layout: everything stable sits at the front — system prompt, tools, examples, retrieved documents — and the cache survives across every request and every loop iteration. Only the conversation tail is billed fresh. On the right, the same content with a single dynamic date string moved to the very top. The prefix breaks immediately. Every token after it — the entire system prompt, all the tools, all the documents — is recomputed and rebilled, on every single call. One line, in the wrong place, multiplied the cost tenfold.

Treat the prompt cache the way a database engineer treats a clustered index. The order of the columns is not cosmetic. It decides what is cheap and what is expensive, what is fast and what is slow, what scales and what collapses under load. The cache is not a setting you flip. It is a property of how you arrange your words, and it rewards the teams who arrange them with intent.

Latency lives in the prefill

The cost is only half the story, and it is the less painful half. The other half is latency, and latency is where users abandon the agent and trust dies. When the model receives a request, it does two things: it prefills — processing the entire input to build the internal state it will generate from — and then it decodes, producing the output tokens one at a time. For a long context, the prefill dominates. Processing fifty thousand tokens from scratch takes real time; the model must attend across every token before it can emit the first output. A cache miss on a large prefix does not merely cost money. It costs seconds — seconds where the user stares at a spinner, wondering whether the agent is thinking or whether it has hung.

A cache hit on the prefix skips the prefill for everything that was cached. The model still processes the new delta, but the heavy lifting — the expensive attention over the giant shared context — was done once and is simply loaded. This is why cache-friendly agents feel instant: their first-token latency is dominated by a tiny delta, not a giant cold start. And this is why an agent that re-sends its full context every loop feels sluggish and expensive even when it uses the same model and produces the same answer. The intelligence is identical. The wait is not. The cache is the gap between an agent that feels alive and one that feels broken.

A cache miss pays the full prefill tax — the model must process every token of the shared context before it can emit a single output. That is the long bar of waiting. A cache hit loads the precomputed state and jumps straight to the delta. The prefill, which dominates latency for long contexts, simply vanishes. The intelligence is identical in both cases. The user only feels the second one.

Architect the prompt like a cache engineer

The teams that internalize this stop writing prompts and start architecting them. The prompt becomes a layered structure, ordered by stability. At the very front: the most static, most reusable content — the system prompt, the tool definitions, the grounding instructions. These should never change between requests for a given agent configuration. Behind them: content that is stable within a session or a task — retrieved documents, the long-running conversation history, reference material. These can be cached within a run even if they vary across runs. And only at the very end, in the suffix, does anything dynamic appear — the latest tool result, the current user message, the timestamp if one is truly needed. The boundary between the stable prefix and the dynamic suffix is the most important line in the prompt, and it is a line almost no team draws consciously.

This discipline compounds with everything else an agent does. Retrieval results should be deterministic in their ordering within a run — a re-ranked list that shuffles on every query shreds the cache from the point of the shuffle onward. Conversation history should be appended, never rewritten or re-ordered. Tool results should be placed at the end of the context, after the stable material, not interleaved into the system prompt. None of these are obvious. All of them are the difference between an agent whose cache hit rate is ninety-eight percent and one whose cache hit rate is zero. And that difference, repeated across a million requests, is the difference between a business and a bonfire.

The deeper lesson is about where leverage lives in an agent system. Most teams hunt for leverage in the obvious places: a smarter model, a cheaper provider, a tighter prompt, a better tool. These all help, at the margins. But the largest lever — the one that moves cost by an order of magnitude and latency from seconds to milliseconds — is not in the model or the prompt's content at all. It is in the shape of the prompt: the arrangement of its parts, the placement of its boundary between stable and dynamic, the discipline of keeping the front identical so the back can vary freely. The cache is not an optimization you bolt on after the agent works. It is a property of the architecture, present from the first design decision, rewarding the teams who respected it and punishing, quietly and expensively, the teams who never knew it was there.
