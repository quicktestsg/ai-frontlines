The Subagent Is a Process

Every few weeks the agent world announces multi-agent systems as a breakthrough. It is a breakthrough the way a rediscovered map is a breakthrough: the territory was charted in 1969. A subagent is a forked context with a private address space, a lifetime, and a result that gets reaped.

Start with the problem subagents actually solve, because it is not the problem their marketing claims. The claim is parallelism — many agents working at once, dividing labor. That is real but secondary. The primary problem is memory pollution. A single context window doing a long task accumulates everything: the plan, the half-finished attempts, the tool outputs nobody needs anymore, the errors that were recovered from. Every token that enters the window stays in the window, and every subsequent inference pays attention across all of it. The context is not a notebook. It is memory that is never freed. By step forty of a research task, the model is reasoning over its own exhaust.

Subagents solve this the same way operating systems solved it sixty years ago: not by cleaning the memory, but by throwing it away entirely. A subagent gets a fresh context — a private address space where the task brief, and nothing else, lives. It thrashes, searches, errs, backtracks, fills its window with garbage. None of that garbage escapes. When the subagent finishes, only its distilled result crosses back to the parent. The messy middle dies with the process. The parent's context stays clean because the child's context was expendable. Isolation is not an organizational pattern. It is garbage collection by homicide.

Left: one context does everything, so everything it ever did stays resident and taxes every future step. Right: the parent forks children with private contexts; each child burns its own window on the messy work, and only a distilled digest crosses back at the join point. The parent never sees the garbage. That is the whole point.

The lifecycle is the contract

Once the process metaphor clicks, the design questions change shape. A subagent needs the same four things a process needs, and a system that omits any of them will fail in the way operating systems failed before they learned these lessons. First, a spawn contract: the brief passed to the child must be complete and self-contained, because the child cannot see the parent's memory. An instruction like 'continue researching what we found earlier' is a segmentation fault — it dereferences memory the child does not have. Second, a budget: CPU time in kernels, tokens and steps in agents. An unbounded child is a fork bomb with a friendly face. Third, a lifetime: the child must know what 'done' means, or it will orbit the task forever. Fourth, a reaped result: a structured return value, not a stream of consciousness. The join point should receive a record, not a confession.

Spawn, budget, lifetime, reap — the four contracts of a subagent, mapped one-to-one onto the lifecycle of a process. The dashed exits matter as much as the happy path: a child that runs out of budget must be killed cleanly and must still report why. An agent system that can only handle children that succeed has not built isolation; it has built optimism.

IPC is where multi-agent systems die

Operating systems history has a precise lesson here: process isolation was solved decades ago, and inter-process communication has been producing bugs ever since. Agent systems are replaying this exactly. Spawning a subagent is easy. Getting information back and forth — deciding what the child needs to know, what format results arrive in, how errors are represented, what happens when two children disagree — is the entire engineering problem. Most 'multi-agent frameworks' are, on inspection, mostly IPC machinery. The agents are the easy part. The pipes are the product.

The failure mode to fear is the group chat. Two agents given a shared conversation become two processes sharing raw memory: each reads the other's half-formed thoughts, responds to them, and the shared context degrades into a mutual pollution spiral that no participant can escape. What looks like collaboration is contention. The fix is the same one kernels chose: structured channels instead of shared memory. Agents should exchange typed messages — claims with sources, results with confidence, errors with context — not streaming their cognition at each other. Loose talk between agents is not richer communication; it is a race condition with vocabulary.

Left: two agents in one shared window read each other's raw cognition — every half-thought permanent, every participant taxed, the conversation itself becoming the pollution. Right: private contexts joined by a typed channel carrying structured messages. The difference is the difference between a system that degrades as it talks and a system that compounds as it talks.

A multi-agent system is not a team of minds. It is a set of disposable contexts connected by contracts. Romance belongs in the demo; isolation belongs in production. The sooner an agent architecture stops pretending its subagents are colleagues and starts treating them as processes — spawned with a brief, bounded by a budget, killed on timeout, reaped for a record — the sooner it stops failing like a group chat and starts failing like a kernel: rarely, loudly, and for reasons you can read in a log.

What the kernel knows that the framework doesn't

There is a counterargument worth taking seriously: models are not processes. A process is deterministic and stupid; a model is stochastic and smart. Why import sixty years of systems machinery for components that can, in principle, negotiate their own coordination? Because principle is not production. In practice, smart components under loose coordination produce emergent behavior that no one designed — conversations that never terminate, handoffs that lose their payload, two agents each certain the other is handling the edge case. Intelligence does not remove the need for boundaries; it raises the stakes of their absence. The kernel's machinery exists precisely because coordinating many actors is hard even when the actors are simple. It does not get easier when the actors are clever. It gets more important.

The practical takeaway is unglamorous. When designing a multi-agent system, spend the minority of time on the agents and the majority on the seams. Define the spawn brief as a schema, not a paragraph. Give every child a token budget, a step budget, and a deadline, and make the kill path a first-class flow that returns a partial result and a reason. Make the join point a parser with validation, not a parent model trusted to read whatever arrives. Log the messages on every channel the way kernels log syscalls — boring, structured, greppable. None of this is exciting. But the systems that survive contact with real workloads are the ones built by people who understood, early, that they were not designing a society of minds. They were writing a scheduler, and the scheduler's job is not to make the processes smart. It is to make their failures small, isolated, and over on time.
