Waiting Is the Work

Agent demos are all motion — tokens streaming, tools firing, answers landing in seconds. But pull the trace of a real long-running agent and the picture inverts: seconds of thinking separated by hours of stillness. The engineering that separates a demo from a system is not in the thinking. It is in the waiting.

Watch an agent demo and you would believe the life of an agent is a river — a continuous flow of reasoning, tool calls, and results, one leading into the next without a gap. Watch a production trace and you discover the truth: the agent's life is a strobe light. Short flashes of genuine cognition — three seconds here, twelve seconds there — separated by intervals of nothing. A batch job queued behind other jobs. A payment webhook that fires when it fires. A human reviewer who reads the request at 9am, after coffee. A database migration that takes forty minutes. The agent does not control any of this. It dispatched the work, and now it must wait for the world to come back.

A real long-running agent, traced across a day. The solid bars are model calls — a few seconds each. Everything between them is waiting: on queues, on external systems, on humans, on rate-limit windows. The fraction of wall-clock time spent actually thinking rounds to zero. Yet almost all engineering attention goes to the thinking.

The three waits

Every wait an agent endures falls into one of three families, and each family breaks systems in its own way. The first is waiting on the world: the agent dispatches work to something outside itself — a build pipeline, a payment processor, an email that must be answered — and control leaves entirely. The second is waiting on itself: the agent fans out subtasks, and the slowest branch sets the pace; one hung retrieval call holds the whole run hostage. The third is waiting on humans: an approval, a clarification, a decision that legally or operationally cannot be automated. Three families, three different physics, and a single-loop architecture that treats them all identically — as a blocking function call — fails at all three in different ways.

Waiting on the world is the most common and the most dishonestly modeled. The engineering temptation is to poll: sleep thirty seconds, check the job, sleep again. Polling feels safe because it is simple, and it is exactly wrong for agents. Every poll is a re-entry into the model — the context must be reconstructed, the state re-read, the reasoning re-established — which means every poll burns tokens, adds latency, and introduces a fresh opportunity for the model to misread its own situation and do something unfortunate. An agent that polls a forty-minute job every thirty seconds performs eighty model calls to learn nothing eighty times. The job completes exactly when it completes. All eighty calls were ceremony.

An agent that cannot wait cannot work. The interesting question about any agent architecture is not how it thinks — every architecture thinks roughly the same way. The interesting question is what happens at the pauses: where the state lives, who wakes the agent up, and what it is allowed to forget while it sleeps.

Left: the polling loop — the agent re-enters the model on every check, rebuilding context and paying for the privilege of learning that nothing happened. The process must stay alive the whole time, so state lives in memory and dies with the pod. Right: the sleep-and-wake pattern — dispatch, persist, suspend; an event or timer resumes the run exactly once, at the moment something actually changed. Same job, same result, one re-entry instead of eighty.

The process will die during the wait

Here is the uncomfortable arithmetic that makes waiting an engineering discipline rather than an inconvenience. Waits are long. Processes are mortal. The longer the wait, the more certain it becomes that something else happens first: a deployment replaces the pod, a spot instance is reclaimed, an operator restarts the service, the laptop closes. For a request that finishes in five seconds, process mortality is a rounding error. For a run that waits five hours for a human approval, process mortality is near certainty. An agent architecture that keeps its state in a live process is therefore an architecture whose state has a life expectancy shorter than its own waits. This is not an edge case. This is the median case, arriving on a schedule.

The answer is not heroic infrastructure. It is a shift in what the unit of execution is. In a well-shaped agent system, the unit is not the process — it is the run, and the run is durable. Each step lands its effects and its state in a store that does not care about process lifetimes. When the agent suspends, it suspends as data: the conversation, the plan, the pending waits, the idempotency keys, all of it, serialized. When the wake event arrives, the run continues in any process anywhere. The process becomes disposable. The run becomes immortal, or close enough.

Process #1 executes steps one and two, checkpoints the run, dispatches the slow work, and is then killed by a routine deployment. Hours later the wake event arrives. Process #2 — a different machine, a different version of the code — loads the run state and continues from step three. Nothing is lost, nothing is re-derived, and no human ever knows a restart happened. The process died. The run did not.

Design the waits first

The practical inversion is this: design the waits before designing the work. For every step in the agent's graph, ask what it waits on, and design that wait as deliberately as the prompt. Waits on the world become events: webhooks, completion callbacks, subscriptions — anything that lets the run sleep instead of pace. Waits with no event source become timers, and timers are not hacks but first-class citizens: they bound every wait, turn silence into a decision point, and give the escalation path a place to live. Waits on humans become queues with owners, service levels, and a timeout policy that decides what happens when nobody answers — because a run that waits on a human forever is a run that was never really designed, only launched.

The teams that grasp this stop measuring their agents in intelligence and start measuring them in wall-clock time to done, percent of waits that are event-driven, runs lost to restarts, and hours burned in queues nobody owns. These metrics are unglamorous. They will never appear in a launch video. But they are the difference between an agent that impressed everyone in the demo and an agent that finishes the work on Thursday. Thinking is now a commodity. Waiting is the craft. Waiting is not what happens between the work. Waiting is the work.
