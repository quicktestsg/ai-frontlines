The Harness Outlives the Model

Every six months a new model lands and the team throws out its agent. The team that wins is the one whose harness survives the swap.

A model ships, and for a few weeks it is the best model. Then another ships, and it is better, and the first is obsolete. This cycle is not slowing down — it is accelerating. What is strange is how teams respond. Each new model triggers a rewrite. The prompts are redone, the tool schemas reshaped, the control loop refactored. Six months of engineering evaporates, and the team is back where it started.

On the left, the default: each model gets a bespoke harness, and each harness is thrown away when the model it was built for is replaced. Nothing compounds. On the right, the alternative: one harness, built to survive model swaps, accumulating improvements while models cycle through it. The model is a replaceable component. The harness is the asset.

What a harness actually is

The word harness is doing a lot of work, so it helps to be precise. The harness is everything between the raw model API and the behavior the user sees. It is the control loop that decides when the model is called, when a tool is called, when the loop stops. It is the set of contracts that the tools and the model agree to speak. It is the retrieval system that decides what context enters the prompt. It is the guardrails that catch the model when it produces something invalid. It is the logging that records every step. And it is the eval suite that scores the whole thing.

None of these components care which model is running underneath. A control loop is a control loop whether the model is a four-billion-parameter checkpoint or a four-trillion-parameter frontier system. This is the key insight that most teams miss: the harness is the part of the system that does not depend on the model. And the part that does not depend on the model is the part worth investing in, because it is the only part that survives.

The model is rented. The harness is owned. Only one of those compounds.

The seam that lets models swap

For a harness to survive a model swap, there must be a seam — a clean boundary where the model plugs in and the harness begins. Most agent systems do not have this seam. The prompts are written in the dialect of a specific model, tuned to its quirks, padded with instructions that compensate for its specific weaknesses. The tool schemas are shaped to match how one model prefers to receive arguments. The control loop branches on patterns that one model produces. Everything is welded to the model, and when the model changes, the welds break.

A welded system couples prompt, schema, and loop to the model's specific behavior. A swap breaks every weld. A seamed system inserts a thin adapter — the only layer that knows the model's dialect — and keeps everything behind the seam neutral. The model changes. The adapter changes. Nothing behind the seam does.

The seam is a thin adapter, and its job is translation. On one side is the model, with its own quirks. On the other side is the harness, which speaks a neutral, model-agnostic language. The adapter is the only component that knows the model's dialect, and it is the only component that needs to change when the model does. The seam is small. The seam is boring. The seam is the difference between a six-month rewrite and a one-day swap.

The eval suite is the only memory that matters

Of all the components in the harness, one deserves special attention because it is the part teams most reliably throw away: the eval suite. It is a set of test cases — real inputs, expected behavior, and a scorer that judges whether the agent produced it. When a team rewrites its agent for a new model, the eval suite is usually the first casualty, because it was written against the old model's output. So the team throws it out, and with it throws out the only record of what the old agent could and could not do.

A good eval suite never shrinks. Every model era adds cases — the failures the new model exposes — and every old case stays, because the old failure modes have a habit of returning in new models. After three model swaps, the suite contains every bug the team has ever found. It becomes the institutional memory of the agent. Throw it away, and the team is amnesiac.

The fix is to build the eval suite against behavior, not output. The suite does not ask whether the agent produced the exact string the old model produced. It asks whether the agent achieved the intended outcome. Behavior is model-independent; output wording is not. This distinction — score the behavior, not the bytes — is what separates a suite that compounds from a suite that evaporates.

The compounding team

There is a team that has been through four model swaps. Each swap, they change the adapter — a few hundred lines, a day's work — and run the eval suite. The suite has four hundred cases, accumulated across the swaps. Their harness has tools hardened over a year of production traffic. Their control loop has been refined through dozens of failure modes. Their replay infrastructure lets them reproduce any production failure in a minute. None of this depends on the model. All of it compounds.

There is another team, on the newest model, three weeks into their rewrite. They are rebuilding the control loop, because the old one was tuned to the previous model. They have no eval suite, so they are testing by feel. They are on a better model. They are behind. The first team is building a system. The second team is building a demo for a model that will not exist next year. The model is rented. The harness is owned. And the team that understands the difference is the team that is still standing when the model cycle has turned three more times.
