The Cheap Model Goes First

Somewhere in every agent codebase there is a line that names the model. Most teams write it once, name the biggest one they can afford, and never look at it again. That single line is treated as a configuration detail when it is actually the most expensive routing decision in the system. The teams that win at inference put a small, fast, cheap model in front, and make the big model earn its way into the request.

Start with the shape of real traffic. In any production agent, the distribution of request difficulty is brutally lopsided. A large fraction of turns are trivial: the user asks a follow-up about something already in the context, or the agent needs to reformat a tool result, or decide that no tool is needed at all. A small fraction of turns are genuinely hard. If every one of those turns goes to the frontier model, the team is paying frontier prices for the trivial majority — like chartering a freight helicopter to deliver every letter in the mail truck's route.

Every request enters at the small model. Most resolve there and return immediately — cheap and fast. The uncertain minority passes a confidence gate and escalates to the frontier model, carrying its work so far as context. The economics invert: cost now scales with difficulty, which is the only thing it should scale with.

Escalation is a signal, not a failure

The instinct in most codebases is to treat escalation as an error path — the small model 'failed', so the big model is the fallback. That framing gets the design backwards. When a small model declines to answer, or emits low confidence, or produces a draft the gate rejects, it is not failing. It is doing the single most valuable thing in the whole cascade: identifying, at small-model prices, exactly which requests deserve frontier compute.

This reframing changes what gets built. If escalation is signal, then the confidence gate becomes a first-class component with its own evals, its own threshold tuning, its own dashboards. The gate's job is not to be clever — it is to be calibrated. Calibration is measurable: take a labeled set of requests, sort by the gate's confidence score, and look at where the errors actually land. Most teams never run this analysis. They pick a threshold that feels right, ship it, and wonder why quality is inconsistent — never realizing the threshold, not either model, is the component actually governing quality.

The question is never 'which model is better.' The question is 'which requests does the cheap model get wrong, and how cheaply can those requests be found.' Answer the second question and the first one stops mattering — the system routes around it.

The gate is the product

Here is the uncomfortable observation from systems that run cascades in production: over time, the gate matters more than either model. Models are swapped every few months; the cascade absorbs these changes with a threshold nudge. But the gate's machinery — the signals it reads, the way it combines them, the calibration loop that keeps it honest — is the durable asset. Each signal is a few lines of code and pennies of compute. Together they decide where every token of expensive compute is spent.

The gate reads cheap signals from the small model's turn — self-reported uncertainty, tool failures, conflicts between draft and context, the risk history of the request type — and combines them into one calibrated score. Below threshold, the cheap answer ships. Above it, the request escalates with everything it has gathered so far. The signals cost pennies; the decision they steer costs dollars.

The two ways a cascade fails

A cascade has exactly two failure modes, and they pull in opposite directions. Under-escalation: the gate lets a request through that the small model answers badly — quality failure, invisible until it isn't. Over-escalation: the gate sends work up that the small model would have handled fine — the answer is still good, but the economics quietly rot. The tragedy is that both failures are usually tuned by the same single threshold, so teams yo-yo between them. This oscillation is not a tuning problem. It is the signature of a gate with one dial when it needs several.

Under-escalation ships wrong answers at bargain prices. Over-escalation ships right answers at frontier prices with frontier latency. Both look like 'the models' in incident reviews, but both live in the gate. The fix is calibration per request type, and separate dashboards for each failure mode, so improving one can be verified without silently worsening the other.

The deeper pattern is that the cascade turns a model-purchasing decision into a systems-design decision. Buying 'the best model' is a one-line answer that outsources the hard part to the vendor's pricing page. Designing a cascade is a claim: that the team knows its traffic, knows where the difficulty lives, and is willing to build the metering layer that proves it. When the next model generation arrives, the team with the cascade adjusts two numbers and keeps its margin. The team with the one-line model name gets to find out what the new default costs.

None of this argues against frontier models. They are the best tools ever built for the hard tier, and the hard tier is where products are won. The argument is against the routing default. Difficulty is not uniform. Traffic is not uniform. Stakes are not uniform. A system that prices every request as if they were is not simple; it is uninstrumented. Put the cheap model first. Make the expensive one a destination that requests must qualify for. Then measure the one number that matters: how often the cheap answer was wrong, and how little it cost to know.
