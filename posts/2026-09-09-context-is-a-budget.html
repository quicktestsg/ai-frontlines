Context Is a Budget

Every agent treats the context window like free memory: append the tool result, append the observation, append the whole file because it might be relevant later. But context is not memory. It is attention — a finite resource that every step spends and no step refunds.

There is a number that silently decides the fate of every long-running agent, and almost nobody puts it on a dashboard. It is not the model's benchmark score. It is not the tool count. It is the token count of the working context at step N. When that number grows without bound, three things happen in sequence. First, cost inflates. Second, latency inflates. Third — and this is the part that survives even in a world of infinite cheap inference — quality degrades. Attention dilutes. The instruction that mattered at step three is now buried under two hundred tool outputs, and the model reliably forgets it. Bloat is not a cost problem that hardware will solve. It is an attention problem that architecture must solve.

A well-architected agent looks less like a tape and more like a cache hierarchy: a small, fiercely-guarded working context; a tier of distilled episodic summaries that can be re-injected when relevant; and an unbounded external store holding everything raw. Moving data down a tier is cheap. Keeping it in the top tier is the most expensive decision in the system.

The window is not memory. It is attention.

The instinct to append everything comes from a reasonable place: in conventional software, memory is cheap and reading it again is free. The context window breaks this intuition completely. A value that enters the window is not stored — it is attended to, on every forward pass, competing with every other token for the model's focus. Two hundred tokens of irrelevant tool noise do not sit quietly in a corner. They actively tax the model's ability to follow the instruction that matters. The information is technically in the window. Availability is not the same as salience, and salience is what the budget buys.

Three policies, one task. The append-everything agent pays quadratically over the run and forgets its instructions at the top of the curve. The compaction agent sawtooths: it grows, summarizes itself back down, and repeats. The budgeted agent enforces a ceiling from step one: every insertion forces an eviction decision, and the context stays flat for the whole run. Flat context means flat cost, flat latency, and instructions that stay salient at step sixty exactly as they were at step one.

An eviction policy is a design decision, not a cleanup script

The hard question, of course, is what to evict. And this is where most teams reach for the wrong tool: they ask the model to summarize its own context whenever it gets long. Self-summarization is better than nothing, but it is a blunt instrument. The stronger move is to make eviction a typed, explicit operation in the harness. A tool result is not the same kind of object as a plan, or a user instruction, or an error trace. Each class deserves its own retention rule, its own destination tier, and its own recall trigger. The transcript is never deleted. It is demoted.

When an insertion would push the context past its ceiling, the harness does not panic-summarize. It classifies the block by type and applies the retention rule for that type: instructions are pinned, tool outputs are mined for structured facts before their payloads are demoted to storage, and superseded plans leave behind only a delta. Every demotion writes an address, so a later step that needs the full detail can recall it — one hop down the hierarchy instead of permanent loss.

A context window is a theater with a fixed number of seats. Every token is an audience member the model must watch simultaneously. The append-everything agent fills the seats with extras who will never speak, and wonders why the performers can no longer hear each other. Budgeting is not about fitting more in — it is about deciding who deserves a seat, and being willing to walk anyone who does not.

Pay for what changes the next token

The budget itself is not arbitrary — it falls out of one question, asked ruthlessly about every candidate token: will this change what the model does next? A tool result from three steps ago, already extracted into the working state, will not. An error message whose lesson has been written into the constraint list will not. Conversely, the things that always pass the test: the current goal, the active constraints, the state of the world the agent has learned, and the precise outputs of the most recent step. Notice how short that list is. Long tasks stop being expensive when the working context stops being an archive and becomes a live index of everything the archive holds.

None of this is glamorous. There is no model upgrade in it, no benchmark jump, no demo moment. It is plumbing — the kind of engineering decision that shows up only in the shape of a cost curve and in whether the fiftieth step of a run is as sharp as the fifth. But this is what harness engineering is: the discipline of building the structure around the model so that the model's intelligence actually arrives at the destination. Windows will keep getting bigger, and every enlargement will be advertised as the end of context engineering. It never is. The teams that answer it deliberately run agents for a thousand steps on a flat budget. The teams that don't, run them until the transcript eats the task.
