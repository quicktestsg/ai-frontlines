Agents Need Save Files

An agent run is a long, expensive, failure-prone batch job — and most harnesses still treat it as a single uninterrupted process. When the run dies at step 27 of 40, the default retry policy is to start over. Mainframes solved this with checkpoints sixty years ago, and the discipline ports cleanly: journal the transcript, ledger every tool call, make resume a first-class code path.

Run the failure arithmetic every operations team runs, except on tokens instead of requests. A serious agent task is forty steps on a good day. Each step is a network round-trip to a model that can rate-limit, refuse, time out, or return malformed JSON. Each tool call touches a filesystem, an API, or a database that can hiccup at the worst moment. Multiply the per-step failure probabilities out and a forty-step run has a meaningful chance of dying in the middle — at step 27, where twenty-six steps of paid tokens and half the deliverable already exist and exist nowhere else. The process dies, the memory dies with it, and the queue schedules a retry that begins at step one. That is the archaic part: the retry policy for the most expensive computation most teams run is 'do everything again, and hope.'

The old answer is the checkpoint, and it is worth revisiting why it worked. A checkpoint is a durable, self-sufficient snapshot of a computation's continuation: everything needed to pick up exactly where the work stopped, written to storage that survives the death of the process. Batch systems, databases, and games converged on it independently, because they all faced the same condition — work in progress worth more than the uptime of the thing doing it. Agent runs now meet that condition emphatically. What differs is what must be saved. A game saves the world state; a database saves the pages; an agent must save a conversation, a ledger of effects on external systems, and the version of the machine that produced both. The save file for an agent is not a memory dump. It is a contract about how the past can be safely reconstructed.

The same crash at step 27, under two retry policies. The naive harness restarts at step 0 and re-pays the entire run; the checkpointed harness loads the save from step 20, replays the recorded turns from the ledger at negligible cost, and re-runs only the seven steps that never completed. Committed side effects are recognized by their idempotency keys and skipped.

What goes in the save file

The save file has five residents. First, the transcript: the full byte-exact message history. It is the cheapest resident and the most valuable — a resumed run can rebuild its entire working context from the transcript alone, and if the provider's prefix cache still remembers the head, the replay is close to free. Second, the tool ledger: every call with arguments, result, and — critically — an idempotency key generated before the call was issued, not after. The key separates 'this effect already happened' from 'this effect might have happened,' and that distinction is the entire difference between a safe resume and a double-charged credit card. Third, the environment state: what the agent changed outside itself — files, branches, records — as a snapshot or a diff. Fourth, the sampling state: seeds and retry counters, so a resumed run behaves like a continuation rather than a stranger in the same history. Fifth, the version stamp: the hash of the prompt, tool definitions, and harness code that produced the run.

The save file's five residents, sorted by what resume trusts: transcript and ledger form the replay zone — bytes are truth, replay is nearly free. Below the line, environment, sampling, and the version stamp govern the journaling zone — records are truth, effects are never re-executed blindly. The version stamp is the guard: a save from a different harness version needs a migration before it can be replayed at all.

Replay is not re-execution

The resume path is where homegrown attempts go wrong: it conflates two operations that must stay separate. Replay feeds the recorded bytes back into context so the model continues as if nothing happened — no new inference, no new billing. Re-execution actually performs a step again in the world. The rule that keeps them apart is purity. A recorded model turn is a pure fact about the past: replay it. A read-only tool call is pure with respect to the world: replay or re-run. A write — a payment, a deploy, a sent message — is not pure, and the ledger earns its keep: on resume, the harness walks the ledger and checks every write for a commit record with the same idempotency key. Committed, skip. Uncommitted, execute with the same key, so a crash between 'sent' and 'recorded' is caught by the receiver's deduplication. This is the saga pattern wearing an agent costume. The insight age of the idea is the point: none of this is new, and all of it is missing.

A checkpoint is not a backup. A backup answers 'what did we lose?' A checkpoint answers 'where exactly do we continue?' — and only the second question has a running system around to ask it.

The resume walk. Every ledgered step receives one of three verdicts: model turns replay from bytes at zero inference cost; pure tools replay or re-run when freshness matters; side effects consult commit records — committed keys are skipped, uncommitted keys re-execute under the same idempotency key, so a crash between request and record is absorbed by the receiver's deduplication, not the user.

The version stamp is the migration problem

The fifth resident deserves its own argument, because it bites silently. A save file serializes a running system, and running systems change. The harness gets patched, a tool schema gains a field, the prompt gets rewritten — and the deploy lands at 18:00 while an eight-hour run is at hour six. The resumed run continues under a harness that would never have produced the recorded history: tool names changed, reasoning style shifted mid-stream, transcript assumptions subtly contradicting the new instructions. The failure is not a crash; it is a quietly incoherent continuation, which is worse, because it produces output that looks like success. The defense is the one databases use: version the save format, refuse replay across versions without a migration, and test 'can old saves load' at build time. Teams usually get this wrong once — the format drifts, old saves become unreadable or, more dangerously, misreadable — and then learn what schema engineers have known forever: serialization without a version is a time bomb, and the fuse is the next deploy.

None of this is exotic, which is the closing observation. The entire mechanism — checkpoints, write-ahead ledgers, idempotency keys, versioned serialization, replay semantics — is standard equipment from batch processing and distributed systems, predating the transformer by decades. What is new is the subject: the checkpointed thing is now a conversation, and the side effects land on the open internet rather than inside a transaction. The economics have moved too: when a unit of work cost a cent, restart-from-zero was a rounding error; when a single run can consume more compute than an entire batch job from that earlier era, restart-from-zero is a policy choice with a line item. Teams that treat agent runs as disposable processes will keep paying for the same tokens three times. Teams that treat them as durable continuations will spend one dull afternoon writing a save format and then quietly never think about it again — which is exactly how you know an infrastructure primitive has arrived. A save file is a small thing. So is a checkpoint. Games shipped them because players refused to lose their progress. An agent's progress deserves the same refusal.
