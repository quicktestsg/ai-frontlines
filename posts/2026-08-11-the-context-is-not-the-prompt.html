The Context Is Not the Prompt

Teams obsess over the prompt — the static string they author, version, and A/B test. But the prompt is a fraction of what the model sees at decision time. The real artifact is the context.

Open the source of almost any agent codebase and look for where the context is assembled. In most codebases, it is not a function with a name. It is a list that grows by appending — the system prompt goes in first, then each turn of conversation, then the result of each tool call, then maybe a retrieved document if retrieval was configured, all concatenated and shipped to the model as a single flat sequence. Nobody designed it. It accumulated.

By step eight of a typical task, the context has ballooned to tens of thousands of tokens. The system prompt — the part the team authored, versioned, and debated — is roughly one percent of it. The rest is conversation history, tool results, retrieved documents, and scratchpad state that accumulated without a single design decision. The model's behavior at step eight is determined by all of it.

The prompt is not the program

For seventy years, the program was the source of truth. The code a developer wrote was exactly what the machine executed, line for line, character for character. The agent era inherits this instinct and misapplies it. The prompt feels like code — it is text, it is version-controlled, it is iterated on. But the prompt is not what the model executes. The model executes the context, and the context is assembled by code that nobody reads.

Consider the implication. A team spends two weeks refining a system prompt, tuning every instruction, getting the tone exactly right. They ship it. On the first real task, the agent retrieves three documents, calls four tools, accumulates thirty thousand tokens of history — and then, buried in a tool result at token twenty-eight-thousand, a value contradicts an instruction in the system prompt. The model follows the value in the tool result. The instruction loses.

The model is a reasoner, not a follower. It does not execute the prompt the way a CPU executes bytecode. It reads the entire context — every token, every source — and synthesizes a response from all of it simultaneously, weighting by recency, by salience, by repetition, by position. The system prompt is one voice in a room of fifty thousand tokens, and it is not always the loudest.

Context is assembled, not authored

The right mental model is not a document but a pipeline. At every step of the agent loop, multiple sources compete to enter the context: the system prompt provides standing instructions, the user message provides the goal, the retrieval system provides relevant documents, the tool layer provides results of actions taken, the conversation history provides what has already been said and done, and the state layer provides variables that persist across steps. The assembly layer decides which of these get in, how much of each, in what order, and which get compressed or dropped entirely.

Five sources flow into a context assembly layer at every step of the loop. That layer makes a set of decisions — inclusion, proportion, ordering, compression, eviction — that together determine what the model actually sees. In most codebases, these decisions are not made explicitly. They are the emergent product of a list's append order, a framework's default truncation, and a retrieval system's top-k value that nobody tuned.

The context is a budget, and every token is a tax

The second thing teams miss is that context is zero-sum. The context window is finite, and more importantly, the model's attention is finite. It does not read fifty thousand tokens with equal care. It attends to some regions densely and others barely — and the regions it attends to are influenced by position, repetition, and the structure of the surrounding text. Every document added to the context dilutes every other document. Every tool result that is included in full, when a summary would have sufficed, steals attention from the thing that actually matters.

This is why exclusion is harder and more important than inclusion. The instinct is to add: add more documents, add more history, add more instructions, add more examples. But a context that contains everything contains nothing, because the model cannot distinguish the critical instruction at token four hundred from the boilerplate at token forty thousand. The discipline is to remove. Compress the conversation history into a running summary instead of replaying every turn. Truncate the tool result to the fields the model needs instead of dumping the full JSON.

The model does not attend to the context uniformly. Regions near the start — the system prompt, the task framing — and regions near the end — the most recent turns, the immediate question — receive dense attention. The middle, where most tool results and retrieved documents land by default, is the low-attention zone. A critical fact placed at token twenty-eight-thousand, sandwiched between two tool outputs, may as well not be in the context at all.

Context engineering as a discipline

The teams that ship agents which behave predictably have stopped thinking in terms of prompts and started thinking in terms of context. They have a named assembly layer — a function, a module, a service — whose job is to take the raw sources and produce the context the model will see, and that layer is tested, observed, and version-controlled with the same rigor as any other code. They compress aggressively: conversation history becomes a running summary, tool results become structured excerpts, documents are ranked and only the top survivors enter. They budget explicitly and they order deliberately.

Prompt engineering asks: what should I write? Context engineering asks: what should the model see? The first question is about authorship. The second is about assembly, budget, and position. The teams still asking the first question are polishing one percent of the input and wondering why the agent ignores it.

The program is the context

The deepest shift is this: in the agent era, the prompt feels like the program, but it is not. The program is the context — the full, assembled, dynamic artifact that the model reasons over at every step. And like any program, it must be written deliberately, understood completely, and changed with awareness of its consequences. The team that ships a prompt into a context it does not control is the team that ships a one-line script into an environment it has never read, and then is surprised when the environment overrides the script. The context is the environment. The context is the program. Engineering it is not an optimization. It is the entire job.
