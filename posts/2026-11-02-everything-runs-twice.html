Everything Runs Twice

There is a property of distributed systems that agent engineering has quietly inherited without inheriting the discipline that comes with it: everything runs twice. Not by design — by accident. A tool call times out at the client while succeeding at the server, so the harness retries it. A crashed run resumes from a checkpoint and replays the last step. A load balancer duplicates a request. A subagent races its parent and both call the same API. None of these are exotic. The question is never whether an agent's actions will be executed twice. The question is whether the second execution is harmless.

Classic software mostly dodged this problem by being slow and supervised. A human clicked the button; if the page froze and they clicked again, the double charge was a support ticket, an apology, and a refund. The blast radius of one duplicated action was one customer. Agents change the arithmetic in two ways at once. First, they act without a human in the loop, so the duplicate is not caught at the moment of commission — it is discovered downstream, in the data. Second, they act at machine cadence: an agent that fires a thousand actions per hour with a one-percent duplication rate is generating ten quiet little incidents every hour it runs. The errors do not announce themselves. They accumulate, like sediment, until the system's state no longer matches anyone's intention.

The tool succeeded, but the response never made it back before the client's timeout. The harness — doing exactly what a resilient harness should do — retried the call. The tool, having no memory of the first invocation, executed it again. Each component is individually correct. The composition is a defect. This is the defining failure mode of agent systems that act on the world: correctness at every layer, disaster at the seam.

Reads are safe. Effects are not. Classify accordingly.

The first move is a taxonomy, and it is embarrassing how few agent codebases have one. Every tool in the toolkit belongs to one of four classes. Reads fetch information and change nothing — safe to run any number of times. Creates bring something into existence that did not exist before — running them twice brings two things into existence, which is the purest form of duplication. Mutates change something that already exists — running them twice is sometimes harmless (setting a status to 'processed') and sometimes destructive (appending a line, decrementing a balance). Destroys remove something — running them twice usually fails loudly, which is accidental safety, not design. The discipline is to tag every tool with its class at definition time, and let that tag drive policy.

Left of the divider: actions whose second execution is benign or self-announcing. Right of the divider: actions that silently duplicate or compound when run twice — the entire danger zone. The policy falls out of the geometry. Reads need nothing. Destroys verify first. Creates carry an idempotency key so the server can recognize a replay. Mutates are rewritten as absolute target states — 'set status to shipped', never 'add one to shipped' — so that running them any number of times converges on the same result.

The idempotency key: teaching the server to recognize a replay

An idempotency key is a small idea with a large consequence. Before executing a create, the caller generates a key — any unique token tied to the logical action, not the physical attempt — and sends it with the request. The server records the key alongside the effect it produced. When a request arrives whose key has been seen, the server does not execute again; it returns the recorded outcome of the first execution. The retry vanishes into a lookup. What was an accidental duplicate becomes an intentional no-op. The beauty of the pattern is that it requires no coordination, no distributed locks, no agreement between the racing parties. The key is the coordination. The ledger is the memory.

Three physical attempts, one logical action, one key. The first attempt executes and records its result. The second and third — whether born of a timeout retry, a replayed checkpoint, or a resumed run — strike the ledger, find the key, and receive the recorded result without touching the world again. Retry policy and correctness stop being in tension: the harness can be maximally aggressive because the ledger makes aggression free.

An agent action is not a function call. A function call that happens twice in a process nobody watches is invisible. An action that happens twice in a database, a payment processor, a customer's inbox, or production infrastructure is a fact about the world — and the world does not have an undo button. Design every effect as if the retry is guaranteed, because in a system that runs long enough, it is.

The harness owns the key, not the model

One subtlety decides whether the pattern works or collapses: the idempotency key must be derived deterministically from the logical action, and it must be generated by the harness — not by the model. A model asked to invent a unique key will invent a different one on every attempt, and a different key defeats the ledger entirely; each retry looks like a fresh action and executes fresh. The key belongs to the same layer that owns retries, checkpoints, and replay, because it is part of the same contract: the harness knows which physical attempts correspond to the same logical action, and only the harness knows. Derive the key from stable elements of the intent — the run's identifier, the step, the target entity, a hash of the action's arguments — and stamp it onto the call before the tool ever sees it.

There is a larger lesson hiding in that subtlety, and it applies far beyond idempotency. The boundary between what the model decides and what the harness guarantees is the most important line in agent architecture. Models decide intent: which action, on what target, with which arguments. Harnesses guarantee mechanics: exactly-once delivery, bounded retries, checkpoints, cancellation, and the memory that makes replays safe. Every time a safety property is delegated to the model — 'please do not call this twice', 'please remember you already sent this' — it is delegated to a component that is probabilistic, stateless across attempts, and one bad prompt away from forgetting. Safety properties belong in the deterministic layer. Intelligence belongs in the probabilistic one. Idempotency is just the clearest instance of the rule, because it is the one where the failure is visible in a database the next morning, in rows nobody can explain.

The payoff for getting this right is not merely the absence of duplicate rows. It is freedom everywhere else in the stack. Once every effect is safe to replay, retries can be tuned for speed instead of caution. Checkpoints can be taken anywhere, because resuming is no longer a gamble. Tests can replay real transcripts against production-shaped tools without fear. Long-running agents can crash — and they will — and resume as if nothing happened, because at the level that touches the world, nothing did. Idempotency is often filed under reliability's fine print, a detail for payment systems. In agent engineering it is closer to a foundation: the property that converts a clever loop into a system that can be trusted to run overnight, unattended, on things that matter. Assume every action runs twice. Build so that it doesn't matter. Then let the harness retry as hard as it wants.
