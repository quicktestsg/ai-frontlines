Your Agent Will Be Interrupted

Every agent that runs longer than a coffee break will be interrupted. Not might be — will be. A deploy will recycle the pod mid-thought. A rate limit will sever a request at the knees. The only question is whether an interruption is an ordinary event, or a catastrophe.

There is a fantasy buried in the architecture of most agent systems, and it is the same fantasy: the uninterrupted run. The loop starts, the model thinks, tools fire, results return, the answer emerges, the loop ends — all inside one process, one memory space, one glorious unbroken session. Web engineers unlearned this decades ago. Agent engineers inherited the single-process mental model at precisely the moment their workloads outgrew it.

Left: the assumption most agent code makes — the run and the process are the same object, so killing one destroys both. Right: the architecture production demands — steps persist as durable state, workers are ephemeral and replaceable, and the chain survives every individual death.

The process is not the run

The confusion at the root of all of this is a category error: treating execution and the unit of work as the same thing. The run is a logical unit of work. The process is one attempt at advancing that work. A run may be advanced by many processes in sequence. Once these two concepts are separated, everything else follows: the run becomes a durable, addressable record; the process becomes a cheap worker that pulls a run, advances it, appends what happened, and dies without ceremony.

The run is an event log, not a row

How should the durable run be represented? The instinct is a row: serialize the state, overwrite it every step, restore it on boot. This works until it does not. The better representation is older than agent frameworks and will outlive all of them: an append-only event log. Every step appends an immutable event. State is not stored — state is derived, a fold over the log. Resume becomes mechanical. Audit becomes mechanical. None of these capabilities can be bolted onto a mutable state row later.

Every step appends an immutable event. State is a fold over the log — computed, not stored — which means any worker, on any machine, at any time, can replay the log, rebuild the state exactly, and continue the run. The checkpoint is not a dump of memory; it is a position in the log plus the side-effect ledger.

A checkpoint that cannot be resumed is a postcard from the crash. The test of durability is not whether state was saved before the process died — it is whether a different process, on a different machine, minutes or hours later, can pick up the run and do the right thing.

The side-effect window

Here is the part that makes agent interruption genuinely hard: the agent does not merely think, it acts. Losing a thought is cheap — the log rebuilds it. Losing track of an action is not. The gap between 'the agent decided' and 'the effect was confirmed' is the side-effect window, and everything expensive or dangerous in an agent system lives inside it. State management protects the agent's memory. The side-effect window is about the world's memory, and the world does not roll back.

The dangerous interval is between dispatch and confirmation — a crash there leaves the outcome unknowable, and a naive resume duplicates the effect. The fix is not to pretend crashes will not happen; it is to make every mutating tool accept an idempotency key derived from the run, so the tool server can recognize a replay and return the remembered result instead of acting twice.

Exactly-once execution does not exist. It is a story distributed systems tell around campfires. What exists — in payment rails and message queues for decades — is at-least-once delivery combined with idempotent operations, which behaves like exactly-once. Every mutating tool takes an idempotency key derived from the run, the step, and the arguments. Reads need no key. Writes cannot live without one. And for the genuinely irreversible tools, the honest alternative is compensation: check before acting, and route to a human when the check cannot answer.

Resume is a behavior, and it must be tested

Three resume modes cover almost every case. Restart clean — correct for cheap, read-only work; negligent for a run that burned forty minutes of retrieval. Resume from checkpoint — the default. Compensate — when a side effect half-landed, resolve the world first. And none of it counts as engineered until it is tested: kill the process at every step index and assert the run converges, with no duplicated effects. Chaos engineering, applied to the loop.

The deeper point is about what an interruption is allowed to mean. In a system built the naive way, an interruption is data loss and a support ticket. In a system built this way, an interruption is a scheduling detail. Deploys stop requiring ceremony. Crashes become footnotes in the log. An agent system is not defined by what it does while everything is up. It is defined by what survives when things go down — the run, the log, and the ledger of effects. Build those to be immortal, and every process becomes what it deserved to be: cheap, replaceable, and unafraid.
