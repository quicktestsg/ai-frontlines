The Hidden Prompt

The prompt you wrote is not the prompt the model reads. A team writes eight hundred words of careful instruction, ships it, and assumes behavior flows from those words. But the real prompt is often fifty times longer, and almost none of it was reviewed.

Start with an exercise that most teams have never done. Take a production agent, freeze a single run mid-task, and dump everything in the context window. Then take out the part the team wrote. What remains is the hidden prompt. It is enormous — tool schemas, error strings, file trees, search results, truncated outputs, compactor notes. Every one of those tokens influences the next one the model produces.

The written prompt is a small, carefully governed artifact. The hidden prompt is everything else in the window — schemas, errors, listings, leftovers — and it is usually one to two orders of magnitude larger. The model reads it all with equal attention. It has no way to know which tokens were reviewed and which were accidental.

The model cannot tell governed text from garbage

There is a comfortable fiction in agent engineering: that instructions live in the system prompt, and everything else is just data. In practice no such distinction exists. To a language model, context is context. A tool description is an instruction. An error string is an instruction. A file named DRAFT_DO_NOT_SHIP.txt is an instruction. The model does not weigh these by provenance — it weighs them by salience, recency, and repetition.

This is why agents so often behave in ways that baffle their creators. The team investigates a run where the agent refused a perfectly good tool, or called a deprecated one, or insisted on a workflow the system prompt explicitly forbade. The prompt looks innocent. The behavior looks insane. Nobody checks the tool's own description — generated months ago from an outdated README, still claiming to be 'the preferred path for all imports.' The bug was never in the prompt. The bug was in the hidden prompt.

Treat every byte that can reach the context window as part of your prompt — because the model already does. An error message you did not write is still an instruction you gave. A directory listing you did not curate is still an example you showed. The harness does not merely transport context. It authors it.

The five surfaces of the hidden prompt

The hidden prompt enters through surfaces, and there are five that matter. Tool surface: every schema and field description, written once and never revised. Failure surface: every error string and retry artifact — a zero-shot instruction delivered at the moment of maximum model attention. Environment surface: file trees, timestamps, metadata — facts about the world the model will condition on. Memory surface: injected summaries and compactor digests that read as authoritative history. Ordering surface: repetition reads as emphasis, recency as priority.

Five surfaces feed one window, and inside the window there are no labels marking what was governed and what leaked in. The model's attention allocates by salience and repetition, not by authorship. Whichever surface shouts loudest wins — and error surfaces, by nature, shout.

Consider the failure surface more closely, because it deserves special fear. When a tool call fails, what enters the context next? In most harnesses, it is the raw exception: a stack trace, an error code, a wall of defensive logging. The model reads this at the exact moment it is most motivated to act, and treats the text as a specification of what to do next. Every error path in the harness is an unwritten branch of the system prompt — and most teams have never read their own error strings from the model's side of the window.

Audit the window, not the file

The corrective is not more prompt review. It is a different unit of governance. Most teams version their system prompt the way they version code — correct, and insufficient, because the file is two percent of the window. The unit of governance should be the assembled context itself: freeze real runs, dump the full window, and read it the way the model does — linearly, every token. Teams that do this for the first time are uniformly shocked.

The audit treats the assembled window as the artifact under review. Freeze runs, dump context, read every token, and when behavior smells wrong, look for the surface that said so — then fix the surface, because adding prompt text to fight leaked context is a race that salience will always win.

From the audit, practical rules follow. Write error messages for models, not just logs: short, factual, actionable, never speculative. Treat tool descriptions as living documentation with owners and review cadence. Curate environment surfaces — filter file trees, normalize timestamps, strip metadata that reads as instruction. Validate injected memory against the current run. And watch repetition: a warning that appears many times in a window is not noise — it is the loudest instruction the model is receiving.

The deeper point is about where the product actually lives. A team that thinks its agent's behavior is defined by the system prompt has confused the map with the territory. Behavior is defined by the window — everything in it, every time, all at once. The system prompt is merely the only part that is convenient to edit. The harness around it is silently authoring the rest. The teams that internalize this stop asking 'what should the prompt say' and start asking 'what does the window say' — and once that question is asked, it can never be unasked.
