You Can't Debug What You Can't Replay

For seventy years, a bug meant a stack trace — a deterministic, reproducible arrow pointing at the exact line that failed. Run it again, it fails the same way, at the same place. An agent has no stack trace. Every run is a unique path through a probabilistic space, and the path it took to disaster is gone the instant the response is returned. A bug report that says "the agent gave the wrong answer" is not a bug report. It is a ghost story.

Here is the foundational difference between the software everyone learned to build and the software everyone is now trying to build. In the old world, execution was deterministic. The same input produced the same output, the same output produced the same error, and the same error produced the same stack trace. Reproduction was free — you ran the thing again, and the bug walked itself back into the room, sat down, and waited to be inspected. The entire discipline of debugging rested on a single, quiet assumption: that the failure could be summoned on demand. That assumption is now false.

An agent does not execute a program. It samples one. Every invocation draws a different trajectory through the model — a different chain of thoughts, a different set of tool calls, a different ordering of the same steps. Feed the identical prompt to the identical agent twice and you will, very often, get two different answers, take two different paths, and fail in two different ways. The bug that appeared on Tuesday at 3pm — the one where the agent hallucinated a file path and then confidently read from a directory that did not exist — will not appear on Tuesday at 4pm. It may not appear for a thousand runs. And then it will appear again, ruin a production task, and disappear, leaving behind an output that looks almost correct and a team that has nothing to point at.

Deterministic code fails at a point you can revisit. A sampled agent fails along a path that exists once, then is gone. The path is the bug — and if the path was never recorded, the bug cannot be found.

The path is the bug

This reframes what a bug even is. In traditional software, the bug is a line — a defect in the code, a fixed location you can point to, isolate, and patch. The stack trace was a map from the symptom back to the line. In agent software, the code is usually fine. The model is usually fine. The tools are usually fine. What failed was a sequence — a specific ordering of reasoning steps, a specific tool call that returned a specific value that nudged the model toward a specific wrong turn, which compounded across the next four steps into a confidently wrong answer. The defect is not in any single component. It is in the trajectory, the path the run took through the space of possible executions. And a trajectory is not something you can grep for.

This is why teams report a maddening pattern. The bug appears in production. Someone reproduces the prompt by hand. The agent gives the right answer. They try again — right answer. They declare it fixed, or a fluke, or a data problem, and move on. Two weeks later, the same failure resurfaces, because nothing was fixed — there was nothing to fix, because the conditions that produced the failure (the exact sampling path, the exact intermediate tool outputs, the exact temperature-weighted token choices) were never captured. The team is debugging a rumour. They are chasing a failure that left no body, no fingerprints, and no fixed address. Without the record of the run, the run effectively never happened, and a thing that never happened cannot be fixed.

The bug is the cascade — a hallucinated tool argument, an empty result misread as signal, a confident pivot onto the wrong path. No single node is defective. The defect is the edge between them, and that edge only existed for the duration of one run.

A stack trace points at a line of code that is always there. An agent trace points at a path through a model that was there for three seconds and will never return in that exact form. One is geography. The other is weather. You debug geography with a map. You cannot debug weather with a map.

Record everything, or debug nothing

The conclusion is unforgiving and it is not optional. If the system did not capture the run, the run cannot be debugged — full stop. There is no partial credit. A log line that says the request started and finished is not a trace. A token count is not a trace. A copy of the final prompt is not a trace, because the final prompt was assembled step by step across the run, and seeing only the final version reveals nothing about how the agent arrived there. What is required is a full-fidelity recording: every model call in order, with its exact input, its exact output, its sampled tokens, its tool-call arguments and tool-call results, the timestamps, the latencies, the temperature and seed if any, and the branching decisions — every point where the agent chose one path over another. This is not logging. This is cinematography. The trace must be a complete film of the run, frame by frame, such that the run can be replayed and inspected at any depth.

And here is the property that makes the investment worth it, the one that turns tracing from a debugging tool into the core engineering primitive of the agent era. A recorded run is not just a postmortem. It is a laboratory. Once the full path is captured, the run can be replayed — but not merely replayed identically. It can be replayed with mutations. Branch at step three, swap in a different tool result, change the system prompt, raise the temperature, and re-run from that point forward. The trace becomes a tree: the original run as the trunk, and every mutation a branch that explores what would have happened if a single variable had changed. This is how agent behavior is actually understood — not by re-running the whole thing blindly and hoping the failure returns, but by replaying a known-bad run and isolating the exact step where a different choice would have produced a different outcome. The replayable trace is the experimental apparatus. Without it, every change to the system is a guess fired into the dark.

Replay the recorded run to its branch point, mutate one variable — the tool result — and re-run forward. If the failure disappears, the cause is isolated. If it persists, branch again. The trace is no longer a postmortem. It is the experiment that finds the fix.

The teams that internalize this build differently from the start. Tracing is not a feature bolted on at the end, after the agent works. It is a property of the harness, designed in from the first commit, because it is impossible to bolt onto a system whose runs were never structured to be captured. They treat every model call, every tool invocation, every intermediate reasoning step as a first-class, addressable, replayable object — not a side effect of execution that vanishes when the function returns. They give every run an identity, so a failure can be linked, shared, opened, stepped through, and branched from, exactly the way a failing test case can be linked and reproduced in the old world. The discipline sounds heavy until it is compared to the alternative: an agent in production, failing intermittently, with no record of how, and no way to ever know.

The old world bequeathed a single, load-bearing idea: that software is debuggable because it is reproducible, and reproducible because it is deterministic. The agent world inherits none of that for free. Determinism is gone. Reproduction is gone. What remains is a choice — to record the runs, or to ship ghosts. The trace is the bridge between a failure and its cause, and without that bridge, every agent in production is a system that fails in ways its own builders cannot see, cannot summon, and cannot fix. You cannot debug what you cannot replay. And an agent whose runs are not recorded is, for the purposes of ever understanding it, an agent that never ran at all.
