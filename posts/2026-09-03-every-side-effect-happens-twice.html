Every Side Effect Happens Twice

A chat agent that only produces text can fail gracefully. The moment an agent starts touching the world — sending emails, writing files, charging cards, deploying code — the rules change.

There is a reason the most reliable software ever built — payment networks, database engines, distributed queues — treats "this operation will run more than once" as a law of nature rather than an edge case. That reason has nothing to do with bugs. It is arithmetic.

Three independent mechanisms, one shared destination. The network retries because responses get lost. The model retries because it cannot see that its first action landed. The queue redelivers because at-least-once delivery is the only delivery guarantee that survives crashes. None of these is a bug. All of them produce duplicates.

The model is the new source of duplication

Start with the classic case, because it frames everything else. An agent calls a tool that charges a customer. The tool executes; the payment goes through; the response travels back and dies somewhere in a timeout. The harness — doing exactly what it was designed to do — retries the failed call. The charge happens again.

That second part is where agent systems break. The model sees no confirmation, so it reissues the call — a fresh attempt from inside its context, a duplicate charge from outside. The fix has to be structural.

Making retries impossible is not an engineering goal — it is a fantasy. The goal is that the second execution of anything is a no-op. Design for the duplicate, and the duplicate becomes harmless. Deny the duplicate, and it becomes an incident.

The idempotency ledger

The pattern that works is small and boring: every side effect gets wrapped in a coordinator that owns a stable key, the operation state, and the stored result. Retries hit the lookup, not the world.

The first attempt executes and records its key, state, and result. Every later retry resolves against the ledger and receives the cached outcome. The side effect touches the world exactly once, no matter how many times anything tries again.

What makes a good key

The entire scheme rests on one question: when a retry arrives, can the system recognize it as the same logical operation? That is entirely a function of the key — and keys are easy to get wrong.

Left: the two most common key strategies, both broken. Right: the key that works is built from the system's own stable structure — so that every road to the same side effect lands on the same identifier.

Recovery without a ledger

There is a second discipline, for the systems where a ledger is not available. Write-ahead intent, post-hoc reconciliation: duplicates become detectable and reversible rather than impossible. Strictly worse than idempotency. Infinitely better than the default.

The habit of asking one question

None of this requires a framework. It requires a question, asked relentlessly at design time: if this runs twice, what breaks? Reads cost only latency. Some effects self-heal. The rest need a key before they are ever wired into an agent's hands.

Models are probabilistic. Harnesses are resilient. Networks are lossy. Given all of that, exactly-once execution is an emergent property the whole system must be arranged to produce. Every side effect will be attempted more than once — the systems that thrive assumed it from day one, gave every effect an identity, and made the second attempt free.
