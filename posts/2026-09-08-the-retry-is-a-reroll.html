The Retry Is a Reroll

Every engineer inherits a reflex from classical systems: when a call fails, retry it. The reflex assumes the call is deterministic. But a model call is not. A retry is a fresh sample from a distribution.

The retry is the oldest trick in distributed systems. A network blips, a database times out, a service is briefly overloaded — retry with backoff, and the problem goes away. The trick works because the thing being retried is a function: deterministic, stateless, identical on every invocation. This assumption survives the transition to agent systems without anyone pausing to check it.

Left: the world the retry reflex was built for. The call is a function; a retry replays it exactly. Right: the world agent engineers actually live in. The call is a sampler; a retry draws a new sample, walks a new path, and can land anywhere the distribution allows — including somewhere worse.

A model call has no fixed point to return to

The completion endpoint takes a prompt and returns a token sequence, but it is not computing a function in the classical sense. It is drawing a sample from a conditional distribution. The second attempt is not the first attempt repeated. It is a different trajectory through the same space.

Retrying a deterministic call asks the world a question it already knows the answer to. Retrying a model call asks the model a different question, in a different mood, and hopes the mood changed. That is not a reliability strategy. That is prayer with extra steps — and a per-token bill.

Classify the failure before you retry it

The fix is not to abandon retries. It is to stop treating all failures as if they were the same failure. Transient failures deserve classic retry. Deterministic failures will recur on every sample — the response is repair. Capability failures call for escalation. Blind retry logic collapses three different engineering responses into one.

A failed attempt is a signal, and the signal has three possible meanings. The channel broke: retry. The output was invalid: repair. The task exceeded the model: escalate. Blind retry logic answers all three meanings with the same move.

Retry at the node, never at the run

The second discipline is about scope. When an agent run fails at step forty of fifty, the worst response is to re-run the whole thing. The re-run is not the same run: different tools, different branches, failure somewhere else entirely. The correct scope for a retry is the node — inputs preserved, attempts counted, bounded retries, and an escalation edge when the budget is spent.

Top: the run-level reroll — a failure at step forty sends the whole execution back to the start, and the new run diverges immediately. Bottom: the node-level retry — upstream work frozen, the failing call replays with identical inputs, an escalation edge fires when the budget is spent.

There is one more consequence teams learn the hard way: retries multiply. A retry at the model-call layer, another at the tool layer, a third at orchestration, plus a supervisor restart — a single request quietly fans out into dozens of model calls. Retries must be owned by exactly one layer, the attempt count must be visible in the trace, and the total re-roll budget must be explicit.

None of this argues against retries. The argument is against the unexamined inheritance — the reflex that treats a sampler as a function, a re-roll as a replay, a variance-driven lucky pass as reliability. The strongest systems classify failures before responding, scope retries to the node, make every re-roll countable — and when the budget runs out, the answer is never another throw. It is a different move.
