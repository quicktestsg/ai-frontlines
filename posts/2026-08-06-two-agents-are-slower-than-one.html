Two Agents Are Slower Than One

A team splits its agent into a planner, a coder, and a reviewer, expecting specialization to bring gains. It brings a tax instead.

The instinct is reasonable, and that is what makes it dangerous. A single agent is doing everything — planning, searching, writing code, reviewing its own work — and it looks unfocused. So the team splits it. One agent plans. Another executes. A third reviews. Each is simpler, each is specialized, and each gets a shorter, cleaner prompt. The architecture diagram looks beautiful. Then they ship it, and it is slower, more expensive, and more brittle than the single agent it replaced. The specialization was real. The tax it introduced was larger.

On the left, a single agent keeps everything in one context window. Its state lives inside the loop and never has to be translated. On the right, three agents must serialize their state into text, hand it to the next agent, which must parse it back into understanding. Each arrow is a point where information is lost, latency is added, and a new failure mode is born.

The handoff is where the money leaks

Consider what happens when the planner hands off to the coder. The planner has spent several turns reasoning about the problem. It has explored dead ends and marked them. It has formed intuitions about which approach will work. All of this lives in its context window — thousands of tokens of hard-won understanding. Now it must hand off. The coder cannot receive the planner's context window. It can only receive text. So the planner summarizes. The summary is a lossy compression of everything the planner learned, and the coder receives the compression, not the original. The coder starts its work with a thinner understanding than the planner had, and it will make mistakes the planner would not have made — because the planner knew things that did not survive the summarization.

Every handoff is a serialization. Every serialization is a lossy compression. Every lossy compression is a mistake waiting to happen.

Then there is the latency. Each handoff is a full round trip: the planner finishes, the harness serializes the result, the harness starts a new completion with the coder, the coder reads the handoff, the coder begins reasoning from scratch. None of that time is spent doing the task. With three agents and two handoffs, the team has added two full model round trips to every task — two intervals where the system is waiting, not working. The single agent never waits for itself. Its next thought begins the instant the previous one ends, because the context is already there.

A single agent spends nearly its entire budget on productive work. A multi-agent fleet spends a large fraction on coordination: serializing state, waiting for the next agent to spin up, and re-parsing context that was already understood by the previous agent. The fleet does the same useful work but pays a tax the single agent never pays — and the tax grows with every agent added.

The specialization is usually fake

The team split the agent because they believed specialization would help. The planner only plans, so it should be better at planning. The coder only codes, so it should be better at coding. This would be true if the model were a specialist — if different weights drove different skills. But the team is using the same model for every agent. The planner and the coder share the same neural network. The only difference is the prompt and the tools available. That is not specialization. That is the same generalist wearing different hats, and the hat-change costs a round trip and a context reset.

There is a deeper problem. Planning and execution are not separate activities — they are entangled. A plan is tested by execution, and execution reshapes the plan. The single agent holds both in one mind: it plans, acts, sees the result, and revises the plan in the same breath. The fleet cannot do this. The planner makes a plan without touching reality, hands it over, and goes to sleep. The coder executes and discovers the plan was wrong — but the coder is not the planner, so it either follows the broken plan or improvises without the planner's reasoning. The feedback loop between planning and doing, which is the most important loop in agentic work, is severed the moment the agent is split in two.

When the split is actually worth it

This is not an argument that multi-agent systems are never useful. It is an argument that they are useful far less often than teams assume, and that the default should be one agent until a specific, named bottleneck forces the split. There are three situations where the split genuinely pays for itself, and they all share a common shape: the single agent has a structural limit that more tools and a better loop cannot fix.

The decision to split should be forced, not chosen. Start with one agent. Add a second only when a specific bottleneck appears: the subtasks are genuinely parallel and independent, the work requires isolation of untrusted code, or the context genuinely will not fit in one window. If none of these are true, the split is adding a tax for a benefit that does not exist.

The first case is genuine parallelism. If the task decomposes into independent subtasks — search four different databases, evaluate five different approaches — then multiple agents can work simultaneously and the wall-clock time drops. This is the only case where the coordination tax is outweighed by a speedup, and even here the subtasks must be truly independent. If agent B's work depends on agent A's result, there is no parallelism — there is only a pipeline, and a pipeline is a single agent with extra steps.

The second case is isolation. If one part of the task involves running untrusted code, the team may want a separate agent with restricted permissions so a compromise stays contained. This is a security boundary, not a specialization argument, and it is legitimate — but it should be framed as sandboxing, not as a multi-agent architecture. The team is not splitting for intelligence. They are splitting for blast radius.

The third case is context overflow. When a task genuinely requires more working memory than a single context window holds — a deep debugging session that needs every log line, a large refactor that needs the whole codebase — the team may split to distribute the context load. But this is a workaround for a context limit, not an architecture choice. As context windows grow, this case shrinks, and the agents that were split to fit the limit collapse back into one. The teams that built around a single agent from the start simply get a bigger window and keep going.

The fleet that came back to one

There is a team that built a five-agent system. A coordinator, a researcher, a writer, a fact-checker, and a formatter. Each was a separate prompt, a separate context window, a separate model call. The system worked, in the sense that it produced output. It also cost five times as much, took three times as long, and produced results that were subtly inconsistent — because the fact-checker did not have the researcher's full context and could not tell which claims were findings and which were the writer's embellishments. The team spent two months debugging the handoffs, tuning the serialization format, adding retry logic for dropped messages. Then a new model shipped with a larger context window, and someone tried putting the whole task in a single agent. It was faster, cheaper, and more consistent. The five-agent system was quietly retired. The months spent building it were not recovered.

The lesson is not that this team was foolish. The instinct to specialize is sound, and in most engineering disciplines it is correct. The trap is that the model is already a generalist, and splitting a generalist does not make it a specialist — it makes it a generalist with worse context. The leverage in agent engineering comes from giving one capable agent better tools, a tighter loop, and richer context, not from dividing one mind into fragments that must shout at each other through a serial link. Two agents are slower than one, not because the model is weak, but because the seam between them is expensive. The team that wins is the one that minimizes seams, not the one that maximizes boxes on the architecture diagram.
