Context Is a Budget, Not a Bucket

Most teams treat the context window as a bucket: pour everything in — the full history, every tool output, entire files — until it overflows, then truncate from the top and hope. But every token in the window is competing for the same finite attention.

There is a number on every model card that everyone treats as the headline: the context window. Two hundred thousand tokens. A million tokens. The number implies a container, and containers invite a particular style of engineering — the style of the bucket. If it fits, it goes in. The system prompt grows a paragraph every week. The full conversation history is replayed on every turn, because replaying is simpler than deciding what to keep. Tool outputs are pasted verbatim, headers and boilerplate and all. Entire files are inlined because retrieval is a second system and inlining is zero systems. The bucket fills. The agent still works — for a while.

On the left, the bucket: the window fills with whatever happened to occur, truncates when it overflows, and the model quietly degrades. On the right, the budget: the window is partitioned into named segments — a pinned kernel, a state object, a working set, retrieved material, and deliberate headroom — and every segment is an explicit allocation decision that can be argued about, tested, and tuned.

Attention is the scarce resource, not tokens

The bucket mentality survives because the failure is statistical, not binary. A full window does not throw an exception. The model still produces fluent, confident, grammatical output. What changes is the distribution of its attention — and attention is not divided the way disk space is. A token in the middle of a long context is demonstrably less attended than a token at the beginning or the end; the literature calls it the lost-in-the-middle effect, and every practitioner has met its symptoms: the agent that re-asks a question answered an hour ago, the edit that violates a style rule stated in the very prompt it can still technically read. Adding more window does not fix this. A million-token window with 900,000 tokens of stale transcript is not a smarter agent; it is the same dilution at a larger scale, with a bigger invoice.

A token in the window is not free. It is rented space in the model's attention, and the rent is paid by every other token in the window. The question is never "does it fit?" The question is "what does it displace, and was that trade worth it?"

Once attention is treated as the scarce resource, the design falls out almost mechanically, and it looks exactly like a memory hierarchy — the oldest trick in computer architecture. Chips did not solve the speed gap between the CPU and main memory by building everything out of the fastest memory; they built tiers, with an explicit policy for what lives where and what moves between them. Agent context deserves the same treatment. At the top tier sits the pinned kernel: identity, hard rules, the commitments the agent has made — never evicted, never summarized, checked into version control. Below it, the working set: the last N turns of genuine dialogue, kept verbatim because recency and fidelity both matter there. Below that, a relevance cache: older material kept only while a cheap score says it still relates to the current task. And at the bottom, the external store: everything else, retrieved on demand.

A context hierarchy, borrowed from half a century of memory design. The pinned kernel never leaves the window. The working set holds recent turns verbatim and evicts by recency. The relevance cache keeps summarized older material until a decay score says otherwise. The external store holds everything else, and retrieval promotes material back into the window exactly when a turn needs it. The policy — what lives where, what moves when — is the actual design work.

Compaction is garbage collection — and most teams do it wrong

Eventually every long session must compact: fold the old into a summary so the new can breathe. Most implementations ask the model to "summarize the conversation so far" and splice the result in place of the history. This is garbage collection with no liveness analysis — it frees memory by sweeping whatever is oldest, with no regard for what is still referenced. And the failures are predictable. The summary faithfully captures the theme of the discussion and silently drops the identifier of the record being edited. It preserves the narrative arc of a debugging session and loses the one constraint the user said was non-negotiable. It keeps the plot and discards the commitments.

The fix is to make compaction lossy about the right things. What must survive every compaction is small, structured, and enumerable: the decisions that have been made and the reasons they were made; the constraints the user has stated, verbatim where possible; every identifier, handle, path, and version number the task depends on; the errors already encountered so they are not re-attempted. What may be discarded is everything else — the phrasing, the dead ends, the three failed drafts, the social lubricant of a long conversation. The cleanest way to enforce this is to stop compacting into prose entirely and compact into a state object: a small structured document that is the contract between the past and the future of the session.

Good compaction is lossy about chatter and lossless about commitments. If the agent can forget the flavor of the conversation but never the promises inside it, the window can shrink without the trust shrinking with it.

Compaction as garbage collection done right: extract the live commitments into a structured state object — decisions and their reasons, verbatim constraints, identifiers, seen errors, open questions — then rebuild a fresh window from kernel, state object, and recent turns. The raw transcript is discarded aggressively because nothing the future needs lives only in the transcript.

None of this requires new infrastructure. It requires a posture change: treating the context window the way a good team treats a budget — every resident token justified, every eviction deliberate, every compaction auditable. The teams that get this right notice something counterintuitive: their agents get sharper as sessions get longer, not duller, because the window increasingly contains exactly what matters and nothing else. The model was never the bottleneck. The window was a swamp, and the intelligence drowned in it.
