Errors Are Prompts: Tool Messages Written for a Reader Made of Weights

Somewhere between the demo and production, every agent system discovers the same thing: its most frequently read document is its own error output. An error message is not UI copy anymore — it is a prompt injected into the loop at the exact moment the agent is deciding what to do next.

An agent in a tool-use loop emits a call, the harness executes it, and the result is appended verbatim to context. The engineer who wrote the tool's error string has more influence over the agent's next move than the engineer who wrote the system prompt. The system prompt speaks once, diluted by everything after it; the error message speaks last, right before the decision.

A bad error converts a decision problem with an obvious answer — stop, fix this field, wait these seconds — into an open-ended generation problem. Open-ended generation is the most expensive thing a language model does. Opaque errors burn tokens, latency, and money on failures a two-line message would have closed.

The error message re-enters context verbatim and conditions the very next action — making it the most recent instruction the model receives, at the point of maximum attention. Opaque errors turn the next turn into open-ended generation; steering errors hand the agent a closed-form move.

Anatomy of an error an agent can use

The pattern has four slots: a stable machine-readable category, one specific sentence naming the field, an imperative next step, and a retry-safety verdict with an idempotency token on write paths. 'Validation failed' is a shrug; the structured version is a plan. The cheapest capability upgrade in most stacks is not a better model — it is better error strings on the twenty tools the current model already calls.

Every error should classify itself: transient versus permanent, idempotent versus destructive. Transient and idempotent means retry with the stated backoff; permanent means the error must say so in words the model cannot misread. The dangerous quadrant — destructive and uncertain — has one honest answer: an idempotency key. Teams that skip it eventually meet an agent that double-sent an invoice and then helpfully tried a third time.

Every tool error should place itself on this grid and say so. Transient and retry-safe: retry with stated backoff. Permanent: name the field and forbid retries. Write paths live in the dangerous lower half, where the only scalable answer is idempotency keys. The quadrants convert the model's hardest in-flight judgment into a one-turn lookup.

Stable structure beats eloquent prose

A subtle failure bites teams who upgrade errors enthusiastically: the text becomes so good that engineers keep editing it — and every polish silently invalidates what the agent and harness had learned. Treat the error contract like a schema: category keys that never rename, fixed field order, human-readable detail quarantined and labeled ignorable, a version marker for migration. The loop wants a shape it can parse in one glance.

The same logic extends to success paths. A tool returning an enormous unsorted payload forces the model to spend turns searching — and every search turn is a chance to hallucinate. Pagination with continuation tokens, filtered queries, counts in summaries: this is context-budget engineering on the read path. Tool results are the system's most expensive prompts, on both paths.

Write every error message as if it were the only instruction the agent would receive that turn — because mechanically, it is. If the message does not contain the next move, the model will invent one, and you will have shipped the invention.

The error ledger: failures as free tooling feedback

Every error an agent receives in production is a datum about the tooling. Record them, rank categories by frequency, and the top of that list is the tool roadmap — a measurement of where the loop bleeds. Each fix removes an entire class of turns from every future run. Error design is the rare discipline where the compassionate option for the model, the cheap option for the budget, and the robust option for the product are the same option.

The error ledger turns failures into a tooling roadmap: mine error frequency from production, fix where the loop wastes turns, and each fix removes an entire class of failures from every future run. Compassion for the model, budget discipline, and robustness turn out to be one dial.

Most agent systems run with a steering surface nobody designed: thousands of error strings written for human eyes, now landing in the attention of a reader that takes them literally and improvises when they say nothing. That surface is already a prompt — the only question is whether it is authored or accidental. The error contract is the quietest large surface in the stack, waiting to be written on purpose.
