Stop Calling the Model

Every agent team optimizes the same thing: the model. But the highest-leverage optimization is not a better model — it is not calling the model at all.

Open the dashboard for any production agent and count the model calls per completed task. Not per user request — per task the user would recognize as one unit of work. The number is almost always shocking. A user asks a simple question. The agent calls the model to understand the intent. Calls it again to decide which tool to use. Calls the tool. Calls the model to interpret the result. Calls it again to format the response. Calls it once more to check its own work. Six model calls for a question whose answer was sitting in a cache the entire time.

The default agent architecture routes every step through the model. Each box labeled 'model' is a billable, latent, non-deterministic operation. The question the user asked may have been asked a thousand times before — the answer identical each time — yet the agent pays the full cost every single run.

The call that did not need to happen

A model call is three things at once, and teams usually only see one of them. They see the cost — the tokens in, the tokens out, the line on the invoice. They do not see the latency, which is not just the time to first token but the entire round-trip: the prompt assembled, the request serialized, the network hop, the queue, the inference, the deserialization, the response parsed. They also do not see the inconsistency. The same input does not produce the same output. A model call is a sample from a distribution, and the distribution has width.

This reframes the problem. If every model call costs money, adds seconds, and introduces variance, then the optimal number of model calls per task is the minimum that produces a correct result — not the maximum the architecture can justify. The cheaper options exist. They are called caches, and most teams have not built them.

A model call is the most expensive, slowest, least consistent operation in your agent. Treat it accordingly: as a last resort, not a default.

Three layers of not calling the model

There are three layers of caching that sit between a user request and a model call, and each one eliminates a different class of unnecessary invocation. The first layer is prompt-prefix caching, and the provider may already be doing it — but whether it benefits you depends entirely on how you structure your prompts.

Each layer intercepts a different class of request before it reaches the model. The response cache eliminates identical repeats. The tool-result cache eliminates redundant data fetches. The prefix cache reduces the cost of every call that does get through. Stacked together, they can eliminate the majority of model calls in a production agent.

The second layer is response caching. If two users ask the same question, and the answer does not depend on who is asking, the second call should never reach the model. A production agent that answers thousands of queries a day is answering the same few hundred questions in a thousand different phrasings, and every one of them is paying full model price for an answer that was computed yesterday.

The third layer is tool-result caching, and it is the least obvious but often the highest-impact. Agents call tools, and tools call APIs, and APIs return data that changes slowly or never. An agent without a tool-result cache will re-call the same tool with the same arguments, get the same result, and then call the model to interpret a result it already interpreted five minutes ago.

What changes when the model is the last resort

When a team builds these three layers and routes every request through them before the model, something shifts. The calls-per-task metric drops. The latency drops, because a cache hit returns in milliseconds what a model call returns in seconds. The variance drops, because cached responses are deterministic. And the cost drops, sometimes by an order of magnitude, because the expensive operation happens once and the cheap operation happens a thousand times.

The same task, before and after caching. On the left, every step is a model call. On the right, the response cache catches the repeat, the tool-result cache supplies the data, and a single model call produces the answer. The output is identical. The invoice can tell the difference.

There is a deeper consequence. When the model is the last resort, the cases that reach it are the hard cases. The model is no longer wasted on work a hash table could do. A team that was running a cheaper model to save money on high-volume trivial calls can now afford a stronger model for the calls that actually matter. Caching does not just save money — it reallocates the budget toward the work where model quality actually makes a difference.

The reason most teams never build these layers is not technical difficulty. The reason is that building a cache is invisible work. It does not demo well. No one gathers around a screen to watch a cache hit return in two milliseconds. A smarter model, by contrast, demos beautifully. So the team invests in the visible thing and skips the invisible thing that would have made the model investment unnecessary for ninety percent of the traffic. The model is the engine. Caching is the flywheel. Most teams never build the flywheel, and then wonder why the engine is always running, always burning fuel, always one hard question away from stalling.
